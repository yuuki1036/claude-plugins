# Issue 設計判断ルール

Issue を書くときの判断軸。9 セクションテンプレ（`template-9sections.md`）の「決定事項」「判断ポイント (open)」を正しく書き分けるための規範。記法非依存。

> このファイルは linear-workflow / indie-workflow 両方に byte-identical で複製される正本。
> 編集したら両プラグインに同じ内容を反映すること。

---

## ルール1: 決定 vs 判断(open) の境界

確定事項とオープン論点を混同しない。境界は「根拠がどこで完結するか」で引く。

| 区分 | 定義 | 仕分けの問い |
|------|------|------------|
| **決定** | Issue 内で根拠が完結する。このファイルを読めば *なぜそうしたか* が分かる | 「今ここで根拠を書き切れるか？」→ YES |
| **判断 (open)** | Issue 外で確定する（PdM レビュー / 別 ADR / 実装してみないと分からない） | 同上 → NO |

- 決定事項に「たぶん」「要検討」が混ざっていたら、それは open に移す
- open を決定事項に紛れ込ませると、根拠の無い確定事項ができて後で揉める

## ルール2: 「現時点の方向性」マーカー

open でも放置しない。各 open 論点に「現時点ではどれが有力か + 理由」を添える。

- Before（悪い）: 「キャッシュ戦略は未定」
- After（良い）: 「現時点では (a) TTL ベースが有力。理由は実装が単純で要件を満たすため。(b) は要件過剰」

これにより open の意味が **「思考停止・未決」から「検討中・方向性あり」** に変わる。読み手は次に何を考えればいいか分かる。

## ルール3: 後続を双方向で書く

依存は前提（先行）だけでなく後続も書く。

- 先行のみ: この Issue は孤立した点に見える
- 先行 + 後続: Issue 群が有向グラフになり、「この次に何が起きるか」が追える

後続を書く習慣がないと、完了した Issue が宙に浮き、次のアクションが失われる。

## ルール4: 「確定タイミング」明示

各 open 論点に「いつ・どこで確定するか」を書く。

- Before（悪い）: 「API 設計は要検討」（いつ決まるのか不明）
- After（良い）: 「API 設計は設計レビュー（Step 3 着手前）で確定」

これにより open の意味が **「未決」から「予約済み」** に変わる。確定の場とタイミングが予約されていれば、open は不安要素ではなくスケジュール済みの論点になる。

---

## まとめ: open を「予約済みの論点」にする

ルール2・4 を合わせると、良い open は次の 3 点を満たす:

1. 選択肢が `(a)(b)(c)` で整理され pros/cons がある
2. 現時点の方向性（有力案 + 理由）がある
3. 確定タイミング（いつ・どこで）がある

この 3 点が揃った open は「未決」ではなく「検討プロセスが設計された論点」になる。
