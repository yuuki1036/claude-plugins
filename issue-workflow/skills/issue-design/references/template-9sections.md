# Issue 9 セクションテンプレート

Issue doc の標準構造。設計・リライト時はこの 9 セクションで構成する。
記法非依存（Linear / ローカル Markdown 共通）の普遍テンプレ。

> このファイルが正本（旧 linear-workflow への byte-identical 複製規約は ADR-20260722164106 で終了）。
> 編集したら両プラグインに同じ内容を反映すること（記法固有の要素はここに書かない）。

---

## セクション定義

### 1. Why — なぜやるか + 上位目的への紐付け

背景と目的を統合する。この Issue が解決する課題、放置した場合のコスト、どの上位目的（プロジェクト目標 / 親 Issue）に貢献するかを書く。

- 書くこと: 課題 / 放置コスト / 上位目的との接続
- アンチパターン: 「〜を実装する」とだけ書いて *なぜ* が無い（What だけで Why が無い）

### 2. 成果物 — ファイル / 位置づけ / 寿命 / 利用者と用途 / 既存 doc との関係

何が生成・変更されるか、それがどこに置かれ・誰がいつ使うか、寿命（一時的 / 恒久 / 段階統合予定）、既存 doc との役割分担を書く。

- 書くこと: 生成物 / 配置 / 寿命 / 利用者と用途 / 既存資産との関係
- アンチパターン: 成果物が曖昧で完了判定できない

### 3. 対応内容 — 具体的な作業ステップ

実際にやる作業を列挙する。順序がある場合は番号付き、無い場合は箇条書き。

- アンチパターン: 抽象的すぎて着手できない（「対応する」だけ）

### 4. 完了条件 — 客観的に判定可能なチェックリスト

「終わったかどうか」を第三者が判定できる条件をチェックリストで書く。

- 書くこと: 検証可能な条件（テストが通る / ファイルが存在する / レビュー承認 等）
- アンチパターン: 「ちゃんと動く」「いい感じにする」など主観表現

### 5. 依存・ブロッカー — 前提（先行）+ 後続 の双方向

この Issue が始まる前提（先行依存）と、この Issue 完了後に動き出すもの（後続）の **両方** を書く。

- 双方向に書く理由: Issue が孤立せず有向グラフになる。後続を書くと「この次に何が起きるか」が見え、全体の流れを失わない
- 書くこと: 先行（これが終わってないと始められない）/ 後続（これが終わると次に動くもの）

### 6. 決定事項 — Issue 内で根拠が完結する確定事項

このファイルを読めば根拠が分かる確定事項を書く（決定 vs open の境界は `design-rules.md` 参照）。

### 7. 判断ポイント (open) — 未確定だが方向性のある論点

Issue 外で確定する論点を列挙する。各論点に以下を添える:

- `(a)(b)(c)` ラベルで選択肢を整理
- 各選択肢の pros/cons
- **現時点の方向性**（どれが有力か + 理由）
- **確定タイミング**（いつ・どこで確定するか）

詳細は `design-rules.md` の「現時点の方向性マーカー」「確定タイミング明示」を参照。

### 8. 参考資料

根拠となるリンク・ドキュメント・関連 Issue を列挙する。

### 9. スコープ外 — Issue Lead の自律範囲の明示

この Issue で **やらないこと** を宣言する。別 Issue 候補や、意図的に除外する範囲を書く。

- 書く理由: スコープ外を明示すると Issue Lead が安心して自律判断できる。「やらない」の宣言が越境を防ぐ

  - 確定タイミング: {いつ・どこで}
