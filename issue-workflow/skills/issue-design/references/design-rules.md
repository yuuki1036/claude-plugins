## ルール1: 決定 vs 判断(open) の境界

確定事項とオープン論点を混同しない。境界は「根拠がどこで完結するか」で引く。

| 区分 | 定義 | 仕分けの問い |
|------|------|------------|
| **決定** | Issue 内で根拠が完結する。このファイルを読めば *なぜそうしたか* が分かる | 「今ここで根拠を書き切れるか？」→ YES |
| **判断 (open)** | Issue 外で確定する（PdM レビュー / 別 ADR / 実装してみないと分からない） | 同上 → NO |

- 決定事項に「たぶん」「要検討」が混ざっていたら、それは open に移す
- 出典の無い決定も open に移す。決定の出典は、会話でユーザーが決めたこと・ADR・仕様・他 Issue の決定事項のどれか。書き手が推測で補った「決定」は、誰も決めていない
- open を決定事項に紛れ込ませると、根拠の無い確定事項ができて後で揉める

## ルール2: 「現時点の方向性」マーカー

open でも放置しない。各 open 論点に「現時点ではどれが有力か + 理由」を添える。

- Before（悪い）: 「キャッシュ戦略は未定」
- After（良い）: 「現時点では (a) TTL ベースが有力。理由は実装が単純で要件を満たすため。(b) は要件過剰」

これにより open の意味が **「思考停止・未決」から「検討中・方向性あり」** に変わる。読み手は次に何を考えればいいか分かる。

## ルール3: 後続を双方向で書く

依存は前提（先行）だけでなく後続も書く。

- 先行のみ: この Issue は孤立した点に見える
- 先行 + 後続: Issue 群が有向グラフになり、「この次に何が起きるか」が追える

後続を書く習慣がないと、完了した Issue が宙に浮き、次のアクションが失われる。

## ルール4: 「確定タイミング」明示

各 open 論点に「いつ・どこで確定するか」を書く。

- Before（悪い）: 「API 設計は要検討」（いつ決まるのか不明）
- After（良い）: 「API 設計は設計レビュー（Step 3 着手前）で確定」

これにより open の意味が **「未決」から「予約済み」** に変わる。確定の場とタイミングが予約されていれば、open は不安要素ではなくスケジュール済みの論点になる。

## ルール5: open は grill で詰める（独断列挙で終えない）

ルール2 の「現時点の方向性」やルール4 の「確定タイミング」は、スキルが独断で埋めると主観的な open になりがち。コミット前に **1 問ずつ grill して詰める**ことで、選択肢の網羅性とユーザー合意を担保する（Brooks の design tree / mattpocock/skills の "grill-me" に由来。Copyright (c) 2026 Matt Pocock / MIT License、許諾文は repo 直下の NOTICE）。

grill の 3 原則:

1. **事実は自分で調べ、決定はユーザーに委ねる** — 「この open は実は既存 ADR / 他 Issue の決定事項 / knowledge の決定で決着済みでは？」を先に `Grep` /（knowledge があれば）`knowledge` /（adr-keeper があれば）`adr` で調べる。明示的な決定記録が直接答えていれば open ではなく決定事項に移す。**コードに前例があるだけなら決着済みとしない** — 前例は「現時点の方向性」の根拠にして聞く。ユーザーの説明とコードが食い違っていたら、該当箇所を示してどちらが正しいか聞く。書こうとしている決定が既存 ADR とぶつかるなら、ADR の id を挙げて明示する（黙って上書きしない）
2. **1 問ずつ、依存順に** — open 同士の依存（先行 open が決まると後続 open の選択肢が変わる）を踏まえ、上流から 1 つずつ確認する。前の回答で後続 open が解消・変形したら畳み直す
3. **各問いに推奨回答を添える** — `(a)(b)(c)` を出すときは「現時点の方向性（ルール2）」を推奨案として `AskUserQuestion` の先頭に置き理由を添える。ユーザーが「おまかせ」なら推奨で確定。無操作で自動継続した回答は「おまかせ」ではないので確定しない。「分からない」「他の人が決める」は推奨で埋めず、open のまま残してルール4 の確定タイミング（いつ・どこで・誰が）を書く

これにより open の選択肢は「スキルの独断列挙」から「調査 + 対話で詰めた合意」になる。**過剰質問は避ける**: open が 1〜2 個かつ方向性が明確なら 1 回の提示にまとめてよい。

## ルール6: 分割は縦に切る（vertical slice / expand–contract）

スコープ超過などで Issue を分割するときは、層（schema だけ・API だけ・UI だけ）で横に切らず、**完了時に単独でデモ・検証可能な縦のスライス**（tracer bullet）で切る（mattpocock/skills の to-issues（現 to-tickets）を翻案。Copyright (c) 2026 Matt Pocock / MIT License、許諾文は repo 直下の NOTICE）。

- 縦切りされた各 Issue は、それ単体で客観的な完了条件（動作確認）が書ける
- 分けたら各 Issue に「完了したら何をデモできるか」を問う。答えられない Issue は横切りになっている
- 実装を楽にする下準備のリファクタ（prefactor）があるなら、先行 Issue として先に切る（「変更を簡単にしてから、簡単な変更をする」）
- 横切りは「全部揃うまで何も動かない」Issue 群を生み、完了条件が主観的になり、途中で止まると価値ゼロの仕掛品が残る

**例外: wide refactor は expand–contract で切る。** リネーム・共有型の変更など、1 つの機械的変更の影響が全域に波及するもの（blast radius が全体）は縦切りできない。3 段に分解する:

1. **expand**: 新形式を旧形式と併存させて追加する（この時点では何も壊れない）
2. **migrate**: 呼び出し側をバッチ単位（パッケージ / ディレクトリ）で新形式へ移行する。各バッチを expand を先行依存とする個別 Issue にする
3. **contract**: 旧形式を削除する（全 migrate バッチを先行依存とする）

各段はルール3 の先行/後続で繋がり、どの段の完了時点でも壊れていない状態を保てる。

## まとめ: open を「予約済みの論点」にする

ルール2・4・5 を合わせると、良い open は次の 4 点を満たす:

1. 選択肢が `(a)(b)(c)` で整理され pros/cons がある
2. 現時点の方向性（有力案 + 理由）がある
3. 確定タイミング（いつ・どこで）がある
4. 事実と、決定記録で決着済みの問いは grill で除かれ、残りは推奨つきで合意されている

この 4 点が揃った open は「未決」ではなく「検討プロセスが設計された論点」になる。
