# living spec フォーマット仕様（正本 / SSoT）

living spec ファイル（`.claude/living-specs/<slug>.md`）の構造・語彙・採番規約の**正本**。

`init` / `oq` / `decision` / `spec` / `status` / `living-spec-maintain` は、ファイルを読み書きする前に必ず本ファイルを Read すること。ここで固定した語彙とスキーマが、maintain の段 1-3（表スキーマ違反 / 採番の連続性 / 相互参照の整合）の機械パースの入力契約になる。**書式が揺れると検知器が壊れる**ので、リテラルで固定する。

---

## 0. 対象ファイルの特定

`.claude/living-specs/` はフラットで **1 プロジェクト = 1 ファイル**。`oq` / `decision` / `spec` / `status` はどのファイルに対して実行するかを次の順で決める。

1. `--spec <slug>` が指定されていれば `.claude/living-specs/<slug>.md` を対象にする。不在なら「`<slug>` が見つかりません」と報告して**終了**（勝手に作らない。init の領分）
2. 指定が無く、`.claude/living-specs/*.md` が **1 件だけ**ならそれを対象にする
3. **複数件**なら AskUserQuestion で選ばせる（自動で推測しない。意図しないファイルを書き換える事故のほうが重い）
4. **0 件**なら「living spec がありません。`/living-spec init <slug>` で作成してください」と報告して終了

対象を確定したら、以降の Read / Edit は**そのファイルだけ**に行う。

## 1. セクション構成

H2 見出しは以下の固定文字列。順序も固定する。

```
## 現在地サマリ
## 仕様
## Open Questions
## Decision log
## 進め方フェーズ
## タイムライン
## 参照ソース
```

**機械パース対象は「仕様」「Open Questions」「Decision log」の 3 つのみ**。残りは散文セクションで、maintain は段 8（LLM 判断）でしか触らない。

パース対象セクションに書けるものは、セクションごとに次で固定する。**散文を混ぜない**（表やエントリの境界が曖昧になり、段 1 が偽陽性を出す）。

| セクション | 書けるもの |
|---|---|
| 仕様 / Open Questions | **表（2 節 / 3 節のスキーマ）と HTML コメントのみ** |
| Decision log | **4 節のエントリ形式（見出し + 固定順の 6 bullet）と HTML コメントのみ**（このセクションは表ではない） |

---

## 2. 仕様表スキーマ

| 項目 | 内容 | 確度 | since |
|------|------|------|-------|
| 認証方式 | OAuth 2.0 | 確定 | 2026-07-15 |
| セッション保持 | Redis | 方向性(仮) | 2026-07-10 |
| 権限モデル | - | 未定 | 2026-07-08 |

- ヘッダ行のセル名は trim して `["項目", "内容", "確度", "since"]` に**完全一致**すること
- 区切り行はセル数のみ検証する（ダッシュの本数は不問。厳格にすると偽陽性が出る）
- **`項目` はファイル内で一意**。重複は段 1 の Critical。`spec` サブコマンドが `項目` を更新キーにして行を引き当てるため、重複すると「どちらを更新したか」が非決定になり、更新されなかった側が実際は動いているのに stale 警告（偽陽性）を出し続ける
- 行の削除は許容する（項目自体の撤回）。これは OQ 台帳・Decision log と異なる点で、仕様表は「現在の確度の一覧」であって履歴ではないため

---

## 3. Open Questions 台帳スキーマ

| OQ# | 問い | status | 関連 D# | since |
|-----|------|--------|---------|-------|
| OQ1 | セッションストアに Redis を使うか | open | - | 2026-07-10 |
| OQ2 | 認証は OAuth か独自か | closed | D1 | 2026-07-15 |

- ヘッダ行のセル名は `["OQ#", "問い", "status", "関連 D#", "since"]` に完全一致
- `status` は `open` / `closed` の**半角小文字 2 値**
- **行の削除は禁止**。close しても行は残し、`status` を `closed` に更新して `関連 D#` を書く
- `open` → `closed` の一方向のみ。**reopen しない**（再燃時は新しい OQ を起票し、問いの中で旧 OQ を参照する）

---

## 4. Decision log スキーマ

表ではなく、見出し + **固定順の 6 bullet**。

```markdown
### D1: 認証方式は OAuth 2.0 を採用
- 日付: 2026-07-15
- 確信度: 高
- 根拠: 自前実装は失効・更新の扱いを持ち込むだけで、要件に対して割に合わない
- 出典: docs/auth-comparison.md / 2026-07-15 の設計会話
- 残: リフレッシュトークンの保管先は未定（OQ3）
- 関連 OQ: OQ2
```

- 見出しは `### D<数値>: <要約>`
- bullet の**キーと順序は固定**（`日付` / `確信度` / `根拠` / `出典` / `残` / `関連 OQ`）
- **append のみ**。既存エントリの編集・削除は禁止
- `確信度` は `高` / `中` / `低` の 3 値

---

## 5. 確度ラベル（3 値）

| ラベル | 意味 |
|--------|------|
| `確定` | 決まった。覆すには新しい Decision が要る |
| `方向性(仮)` | 有力案はあるが未確定 |
| `未定` | 検討していない / 決められていない |

- **括弧は半角** `(仮)`。全角 `（仮）` や `方向性（仮）` は表記ゆれとして段 1 の Critical
- この 3 値以外は段 1 の Critical
- **逆行（`確定` → `方向性(仮)`）は許容する**。決定が覆るのは正常な事象なので警告しない。`since` を更新するだけでよい

---

## 6. 採番規約

- `OQ<max+1>` / `D<max+1>` で採番する
- `max` は**既存 ID の数値の最大**（`closed` を含む。行の並び順ではなく数値で取る）。行が並べ替わっても壊れない
- 0 件なら `OQ1` / `D1`
- **欠番は埋めない。ID は再利用しない**（reopen 不許容と整合。履歴を線形に保つ）

---

## 7. 日付書式

- `since` / `日付` とも `YYYY-MM-DD`（ゼロ埋め必須）
- 取得は Bash の `date +%Y-%m-%d` のみ。**擬似日付を作らない**（adr-keeper / design-doc と同じ規律）

---

## 8. 空セル・複数参照・セル内の `|`

- 空セルは**半角ハイフン 1 文字** `-`。空文字・空白のみは段 1 の Critical。**`項目` / `内容` / `問い` のいずれも空にしない**（`内容` が未定なら `-`）
- 複数参照はカンマ + 半角空白で並べる（`D1, D3` / `OQ2, OQ5`）
- **セル内の `|` は `\|` にエスケープする**（Markdown の表内でリテラルのパイプを表す標準の書き方）。9 節の正規表現はエスケープを許容する。生の `|` はセルを分割してしまうので段 1 の Critical

> セル内 `|` を全角 `｜` へ置換する案は採らない。ユーザーが書いた問いの文字を機械が黙って変えることになり、`oq list` で原文と違うものが出る。エスケープなら情報が保たれる。

---

## 9. パース用正規表現（段 1-3 の入力契約）

**前処理（必須）**: 正規表現を当てる前に、**HTML コメント区間（`<!--` から `-->` まで、複数行にまたがるものを含む）を除去する**。1 節がパース対象セクションでの HTML コメントを許可している以上、コメント内に書かれた記入例や説明が正規表現に拾われると、実在しない D# / OQ# を採番・相互参照の対象にしてしまう。前処理を省くと段 2（採番の連続性）と段 3（相互参照の整合）が偽陽性を出す。

同じ理由で、**テンプレート・ドキュメントのコメント内に `### D1:` や `- 関連 OQ: OQ1` のような行頭一致する記入例を書かない**（前処理と二重の防御にする）。

セル本文は次の `CELL` で受ける。

```
CELL = (?:[^|\\\s]|\\.)(?:[^|\\]|\\.)*?
```

- **非空白**で始まることを要求する（先頭を `[^|\\\s]` に固定）。`\s*CELL\s*` の形で単に「1 文字以上」にすると、**空白 1 文字のセルが素通りする**（`\s*` が片方の空白を食い `CELL` が残りを拾ってしまう）。8 節が「空文字・空白のみは段 1 の Critical」と定めている以上、正規表現側でも通さない
- `\\.` を含むので 8 節の `\|` エスケープを許容し、**生の `|`（セルを分割する）は拒否**する
- セル前後の空白は `\s*` が吸うので、`CELL` の捕獲値に前後の空白は入らない

```
仕様表行:   ^\|\s*(CELL)\s*\|\s*(CELL)\s*\|\s*(確定|方向性\(仮\)|未定)\s*\|\s*(\d{4}-\d{2}-\d{2})\s*\|$
OQ 行:      ^\|\s*OQ(\d+)\s*\|\s*(CELL)\s*\|\s*(open|closed)\s*\|\s*(-|D\d+(?:,\s*D\d+)*)\s*\|\s*(\d{4}-\d{2}-\d{2})\s*\|$
Decision 見出し: ^### D(\d+): (.+)$
Decision bullet:
  ^- 日付: (\d{4}-\d{2}-\d{2})$
  ^- 確信度: (高|中|低)$
  ^- 根拠: (.+)$
  ^- 出典: (.+)$
  ^- 残: (.+)$
  ^- 関連 OQ: (-|OQ\d+(?:,\s*OQ\d+)*)$
```

`(CELL)` は上記の定義を展開して使う（実装では文字列結合でよい）。仕様表行の `内容` セルも `CELL` で受ける（空にしない。未定なら `-`）。

### 段 1（表スキーマ違反）の適用範囲

セクションごとに**判定対象の行が違う**。一律に当てると正しいエントリを Critical にしてしまう。

| セクション | 判定対象 | Critical にするもの |
|---|---|---|
| 仕様 / Open Questions | **ヘッダ行・区切り行・空行を除く全行** | 上記の「仕様表行」「OQ 行」に一致しない行 |
| Decision log | **`### ` で始まる行と `- ` で始まる行** | 見出しが「Decision 見出し」に一致しない / エントリ内の bullet が上記 6 パターンのいずれにも一致しない / 6 bullet が揃っていない / **4 節の順序どおりでない** |

- **空行と（前処理で除去済みの）HTML コメントは判定対象外**
- 一致しない行を黙って読み飛ばさない（壊れた行が恒久的に沈黙するため）
- **行が 0 件の表は正常**（`init` 直後の初期状態）。空の行を置いてはいけない

## 10. frontmatter

```yaml
---
phase: target                  # doc-freshness 契約（収束中 = target）
last-validated: 2026-07-15     # doc-freshness 契約。人が内容を確認した日
last_updated: 2026-07-15       # 機械更新。init / oq / decision / spec が書き込みのたびに更新
notion_page_id: null           # v1 未使用（予約）
sync: null                     # v1 未使用（予約）
---
```

| フィールド | 更新主体 | タイミング |
|---|---|---|
| `last_updated` | **機械**（init / oq / decision / spec が `date +%Y-%m-%d` で書く） | ファイルに書き込むたび |
| `last-validated` | **人**（`/living-spec-maintain` の実行＝内容を確認する行為とみなす） | maintain を回したとき。init 時は作成日で初期化する |

- `last-validated` を機械更新しないのは doc-freshness の規定（手動更新が原則、自動更新はアンチパターン）に従うため
- `append_only: true` は**付けない**。living spec は `phase: target` で収束させていく生きた文書で、鮮度を測る対象そのものだから（ADR とは逆）
- Shared State 契約フィールド（`shared_state_type` / `producer` / `consumers` / `schema_version`）と `source` は**持たない**。規約の対象は複数プラグインが読み書きするファイルで、living spec には現状 consumer がいない

## 11. なぜ「情報を move しない」か

OQ を close するとき、台帳から行を消して Decision へ移す設計にはしない。効き目の範囲は次のとおり:

- **情報の消失**（close した OQ が消える / 移動の途中で失敗して片方にしか無い）→ **構造的に起きない**。削除を含む操作が存在しないため、Edit がどう部分適用されても行は残る
- **参照の片側漏れ**（OQ に `関連 D#` が無い / Decision に `関連 OQ` が無い）→ **構造的には防げない**。表を書くのは LLM なので書き漏らしは起こりうる。これは maintain 段 3（Critical）と段 5（Warning）の事後検知で担保する

つまり move をやめることで消えるのは消失であって、不整合ではない。不整合の検知器を Critical で持つのはそのため。
