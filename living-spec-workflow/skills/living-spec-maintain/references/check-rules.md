# maintain 検証ルール（正本 / SSoT）

`/living-spec-maintain` の段 1-8 の判定内容・severity・修正方針の**正本**。

**入力契約は `../../living-spec/references/format-spec.md`**（表スキーマ・語彙・採番規約・パース正規表現）。本ファイルは「その契約が守られているかをどう判定するか」だけを規定する。**契約そのものを本ファイルに書き写さない**（二重管理になり、片方だけ更新されて検知器と契約がずれる）。

---

## ファネル構成

安価な機械判定を先頭に置き、意味判断を後段に回す。

| 段 | 判定 | 手段 | severity |
|---|---|---|---|
| 1 | 表スキーマ違反 | 機械パース | Critical |
| 2 | 採番の連続性（重複・欠番） | 機械パース | Critical |
| 3 | 相互参照の整合（双方向一致） | 機械パース | Critical |
| 4 | 「参照ソース」の外部 URL の死リンク | 機械判定（HTTP） | Warning |
| 5 | OQ の `status` と `関連 D#` の整合 | 機械パース | Warning |
| 6 | 確度ラベル stale | `since` と `date` の差分 | Warning |
| 7 | frontmatter `last_updated` の整合 | 機械判定 | Info |
| 8 | 現在地サマリが実態とずれていないか | LLM 判断 | Info |

**段 1-7 が機械判定、段 8 のみ LLM**。段 1-3 が 1 件でも出たらファイルは壊れているので、段 8 の LLM 判断には進まない（壊れた表を読ませて意味を論じさせても無駄）。

---

## 前処理（全段に先立つ・必須）

`format-spec.md` 9 節が要求する **HTML コメント区間の除去**を最初に行う。

```bash
perl -0777 -pe 's/<!--.*?-->//gs' "$F" > "$WORK"
```

除去を省くと、テンプレや説明コメント内の記入例を実在の行・ID として数え、段 2（採番）と段 3（相互参照）が偽陽性を出す。**以降の全段は除去後のテキストに対して判定する**。

---

## 段 1: 表スキーマ違反（Critical）

`format-spec.md` 9 節の「段 1（表スキーマ違反）の適用範囲」に従う。セクションごとに判定対象が違うので、一律に当てない。

| 対象 | 検出 |
|---|---|
| 仕様 / Open Questions | ヘッダ行・区切り行・空行を除く行が「仕様表行」「OQ 行」の正規表現に一致しない |
| Decision log | 見出しが「Decision 見出し」に一致しない / bullet が 6 パターンのいずれにも一致しない / 6 bullet が揃っていない / 4 節の順序どおりでない |
| 両方 | ヘッダ行のセル名が 2 節 / 3 節の定義と完全一致しない |

**行が 0 件の表は正常**（`init` 直後の初期状態）。0 件を違反にしない。

**fail-closed**: パース自体が失敗した（ファイルが読めない・frontmatter が壊れている・セクション見出しが見つからない）場合は、**Critical に倒す**。「判定できなかった」を「問題なし」と報告しない。

**修正方針**: 一致しない行を `format-spec.md` の該当節の書式に直す。確度ラベルの括弧が全角なら半角に、`since` が日付書式でなければ `YYYY-MM-DD` に。**空セルは `-`**（半角ハイフン 1 文字）。

---

## 段 2: 採番の連続性（Critical）

`format-spec.md` 6 節が正本。ID を数値として取り、**重複**と**欠番**を検出する。

| 検出 | 意味 |
|---|---|
| 重複（`OQ2` が 2 行ある / `D3` が 2 エントリある） | 採番が max+1 で行われていない。同時編集か手書き |
| 欠番（`OQ1, OQ3` で `OQ2` が無い） | **行が削除された**（`format-spec.md` 3 節・4 節が禁じている操作）。または採番が飛んだ |

**修正方針が他の段と違う**。6 節が「欠番は埋めない。ID は再利用しない」と定めているので、**採番し直して詰めてはいけない**。欠番は「消えてはいけない行が消えた」痕跡なので、直し方は次のとおり:

1. `git log -p` / `git diff` で削除された行を特定し、**元の ID のまま復元する**
2. 復元できない（履歴に無い・そもそも採番が飛んだだけ）なら、欠番のまま残してよい。ID の一意性は保たれており、後続の採番も max+1 で正しく続く
3. **重複**は別。同じ ID の 2 行が別の内容なら、後から書かれた方を新しい ID（max+1）に振り直す

> 欠番を Critical にしつつ「埋めるな」と言うのは矛盾に見えるが、Critical が指しているのは「欠番という状態」ではなく「**行が消えた事実**」。番号を詰めると、消えた事実そのものが見えなくなる。

### 検出できない削除がある（既知の限界）

欠番検出は「1..max の範囲で抜けている ID」を探す。したがって **max の ID を消した削除は原理的に検出できない**（残りが連続するため）。実測した境界:

| 状態 | 段 2 の検出 |
|---|---|
| `[1, 3]`（中間を削除） | 欠番 `OQ2` を検出 |
| `[3]`（1・2 を削除） | 欠番 `OQ1, OQ2` を検出 |
| `[1, 2, 2]`（重複） | 重複を検出 |
| **`[1, 2]`（元は 1,2,3。max を削除）** | **検出できない** |

max を消すと、次の `oq` / `decision` が `max+1` で**同じ ID を再採番する**（6 節が禁じている ID の再利用が起きる）。この経路は段 2 では塞げないので、**別の網で拾う**:

- **削除された ID を参照する Decision / OQ があれば段 3 が拾う**（「D1 が参照する OQ2 が存在しない」→ Critical）。再採番後も、新しい OQ2 は `open` / `関連 D#: -` なので段 3 が「片方向」として拾い続ける
- **どこからも参照されていない ID を max で消した場合は、ファイル内の情報だけでは検出できない**。次の 2 つが該当する（実測で確認）:
  - **`関連 D#: -` の open な OQ**（まだ決定に紐づいていない問い）
  - **`関連 OQ: -` の Decision**（既存の問いに対応しない決定）。`oq` を経由せず下された決定は普通に起こる（SKILL.md の Phase 5.3 が選択肢の先頭に「なし（OQ を close しない）」を置いているのはそのため）。**Decision log は append-only の履歴なので、消えたときに失われる情報は OQ より重い**

  どちらも `git log -p` で確認するしかない。

**この限界を前提に運用する**。そもそも行の削除は `format-spec.md` 3 節・4 節が禁じており、`oq` / `decision` は削除を含む操作を持たない（SKILL.md の W3）。段 2 は「規約違反が起きたときの事後の網」であって、削除を防ぐ機構ではない。**防ぐのは W3、拾えるところまで拾うのが段 2 と段 3**。

## 段 3: 相互参照の整合（Critical）

OQ の `関連 D#` と Decision の `関連 OQ` が**双方向で一致**するかを見る。片方向は Critical。

| 向き | 検出 |
|---|---|
| Decision → OQ | Decision の `関連 OQ` に挙がった `OQ<n>` が、OQ 台帳に存在し、`closed` かつ `関連 D#` に当該 `D<n>` を含むか |
| OQ → Decision | OQ の `関連 D#` に挙がった `D<n>` が、Decision log に存在し、`関連 OQ` に当該 `OQ<n>` を含むか |
| 存在 | 参照先の ID がそもそも存在しない（`関連 OQ: OQ9` だが OQ9 が無い） |

**これは `/living-spec decision` の Phase 5.6 が書き込み直後に自分で検証している項目**。ここで検出されるのは、(a) 手編集で片方だけ書いた、(b) decision が途中で失敗した、のどちらか。maintain は**事後の網**であって一次防御ではない。

**修正方針**: 欠けている側を書き足す。**どちらが正か**は Decision log 側を優先する（append-only で編集禁止なので改竄されにくい）。

## 段 4: 外部 URL の死リンク（Warning）

**対象は「参照ソース」セクションの外部 URL のみ**（`http://` / `https://`）。**内部の相対リンクは doc-freshness Phase 5 に委譲**する（二重に検証しない）。

```bash
curl -s -o /dev/null -w '%{http_code}' --max-time 5 -L "$url"
```

判定は結果で分ける。**ネットワーク不達を「死リンク」と断定しない**:

| 結果 | 扱い |
|---|---|
| 4xx / 410 | **Warning**（死リンク） |
| 2xx / 3xx | 問題なし |
| タイムアウト / DNS 解決失敗 / 5xx | **Info（未検証）**。「この worktree からは確認できなかった」と明記する |

> 段 1-3 の fail-closed（判定不能なら Critical）を段 4 に適用しない。パース失敗は「ファイルが壊れている」証拠だが、ネットワーク不達は「リンクが死んでいる」証拠にならない。ここで Warning に倒すと、オフラインで回すたびに全リンクが Warning になる。

---

## 段 5: OQ の `status` と `関連 D#` の整合（Warning）

同じ OQ 行の中での矛盾を見る（段 3 が「行を跨いだ」整合を見るのに対し、こちらは行内）。

| 検出 | 意味 |
|---|---|
| `closed` なのに `関連 D#` が `-` | どの決定で閉じたか分からない。`decision` を経由せず手で `closed` にした疑い |
| `open` なのに `関連 D#` が入っている | 決定が紐づいているのに閉じていない。`decision` が途中で失敗した疑い |

段 3 より弱い Warning にするのは、**行内の矛盾は情報の損失を伴わない**ため（どちらのフィールドが正かは人が読めば分かる）。段 3 の片方向参照は、参照先が本当に無いのか書き忘れなのかがファイルからは判別できない。

**修正方針**: `closed` + `関連 D#` 無しは、対応する Decision を探して紐づけるか、対応が無いなら `open` に戻す（**これは reopen ではない**。close 自体が誤りだった訂正）。`open` + `関連 D#` 有りは `closed` にする。

---

## 段 6: 確度ラベル stale（Warning）

`方向性(仮)` / `未定` のまま **N 日**動いていない項目を検出する。`確定` は対象外（確定したものが動かないのは正常）。

**N は焼き込まない**:

```bash
CONFIG=".claude/doc-freshness.json"
N=$(jq -r '.thresholds.target // empty' "$CONFIG" 2>/dev/null || true)
[ -z "$N" ] && N=15
```

doc-freshness の閾値はプロジェクト側で上書きできる（`thresholds.md` が `"target": 30` / `60` を例示）ため、15 を固定すると上書きした環境で即座に二重基準になる。フォールバック 15 を持つことで **doc-freshness 未導入でも動く**（プラグイン独立）。

**確度の逆行（`確定` → `方向性(仮)`）は警告しない**（`format-spec.md` 5 節）。決定が覆るのは正常な事象。

**修正方針**: 塩漬けの項目は `/living-spec spec <項目> <確度>` で確度を見直す（変わらなくても `since` が更新され、「今日この確度で確認した」の意味になる）。決められないなら OQ に起票して論点を明示する。

---

## 段 7: frontmatter `last_updated` の整合（Info）

`last_updated` が、ファイル内の最新の `since` / Decision の `日付` より**古い**場合に検出する（書き込み時の更新漏れの痕跡）。

**`last-validated` は段 7 の対象外**。ファイル単位の鮮度（stale 判定）は doc-freshness の責務で、`last-validated` の更新は maintain の**完了処理**が扱う（SKILL.md の Phase 4）。ここで両方を見ると doc-freshness Phase 8 と二重になる。

**修正方針**: `last_updated` をファイル内の最新日付に更新する。ただし頻発するなら、`oq` / `decision` / `spec` のいずれかが W4（書き込んだら `last_updated` を更新する）を守れていない可能性を疑う。

---

## 段 8: 現在地サマリの実態とのズレ（Info / LLM 判断）

**段 1-3 の Critical が 0 件のときのみ**実行する（かつ `${CLAUDE_EFFORT}` が `high` 以上）。**段 4-7 の Warning / Info は段 8 を止めない**。

> 「段 1-7 を通過した場合のみ」とは書かない。ファネルの関門は Critical だけで、段 6 の Warning（未定項目が 16 日塩漬け＝ごく普通に起きる状態）や段 7 の Info で段 8 が skip されるのは設計意図に反する。止めるのは「表が壊れていて意味を論じても無駄なとき」だけ。

「## 現在地サマリ」の記述が、仕様表の確度・open OQ・Decision log の実態と食い違っていないかを読んで判断する。例:

- サマリが「認証方式は未定」と書くが、仕様表では `確定` になっている
- サマリが触れていない open OQ が積み上がっている
- サマリが言及する論点が、既に Decision で決着している

**severity は Info に留める**。サマリは人が書く散文で、多少の粗さは正常。**断定できるズレだけを挙げ、「もっと詳しく書けるのでは」のような好みは出さない**（過剰指摘の抑制）。

**修正方針**: サマリを実態に合わせて書き直す。ただしサマリは「判断の現在地」を書く場所で、数字は `status` が出すので、数字の同期を求めない。

## severity の意味

| severity | 意味 | 対応 |
|---|---|---|
| **Critical** | ファイルが `format-spec.md` の契約を破っている。後続の `oq` / `decision` / `spec` / `status` が誤動作する | 直すまで他の操作をしない |
| **Warning** | 契約は満たすが、運用上の矛盾・鮮度の劣化がある | 直すのが望ましい。放置しても壊れない |
| **Info** | 参考情報。判断は人に委ねる | 任意 |

**confidence は付けない**。段 1-7 は機械判定なので confidence は常に 100 で、フィールドとして持つ意味がない（`severity` だけで報告閾値が決まる）。段 8 のみ LLM 判断だが、Info 固定なので 2 軸にする必要がない。ルート CLAUDE.md「コスト×精度パイプライン設計指針」の原則 2（2 軸スコア化）を**あえて捨てている**のはこの理由。
