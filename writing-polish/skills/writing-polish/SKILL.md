# Writing Polish

文章を語句レベルで推敲・添削する。RFC / Issue / PR 本文 / コミットメッセージ / レビューコメントを対象に、冗長・曖昧・トーンのぶれを直す。校正ルール（何を直すか）の正本は `references/tone-guide.md`、提示・採否 UX（どう見せて採否させるか）の正本は `references/presentation-guide.md`。

## 中核原則（最優先・絶対）

文章生成ではなく**編集**として扱う。以下は tone-guide のどのカテゴリよりも優先する。出典は tone-guide「アンチパターン」節。

1. **最小・標的型の差分で直す**。全文を書き直さない。変更不要箇所はそのまま残す。
2. **過剰修正をしない**。文法的に正しく意図も通る箇所を、流暢性向上の名目で書き換えない。
3. **原文の声・個性を保つ**。書き手の口調やリズムを無難な「AI 文体」に均さない。
4. **構造を壊さない**。コミット prefix・PR テンプレート・Issue のセクション・コードブロック・リンク・固有名/API 名は変更しない。文面のみ推敲する。
5. **改善を説明できない修正は出さない**。「使用する↔利用する」のような意味の変わらない往復はしない。

## 1. 対象テキストの収集

引数の形に応じて対象を決める。

- **テキスト直接指定** → それを対象にする。
- **ファイルパス指定** → `Read` で読み込む。採用時は該当箇所のみ `Edit` で反映する。
- **省略** → 直近の自分（assistant）の生成テキストを優先し、無ければ会話で直前に話題になった文章を対象にする。両方が曖昧なら対象を 1 つに絞って確認する。

あわせて**文書種別**を判定する（コミット / PR description / Issue 本文 / RFC / ADR / レビュー返信）。種別が tone-guide の「文体メタルール」と「適用優先順位」を決める。`--tone <種別>` で明示された場合はそれに従う。

## 2. tone-guide に照らして候補を抽出

`references/tone-guide.md` を読み、対象テキストに該当する指摘を**カテゴリ単位**で集める。

- カテゴリ 1 冗長・密度 / 2 曖昧さ / 3 トーン・姿勢 / 4 AI っぽさ / 5 用語・正確性 / 6 英語（対象が英語のとき）/ 7 平易性・過剰抽象
- RFC / 設計ドキュメントは厳密層（文長・読点・係り受け）を強めに、PR/Issue/コミット/レビューは汎用層を中心に当てる。
- **確信の持てる指摘を優先**する。不確実な「気の利いた言い換え」は任意提案として最後に回す（tone-guide 適用優先順位 5）。

## 2.5 linter による決定的チェック（任意・textlint 導入時）

決定的に拾える観点（表記・文法・二重否定・助詞連続・確実な冗長構文「〜を行う→する」・文長/読点しきい値）は linter に委譲する。

- まず存在チェックする。

```bash
command -v textlint >/dev/null 2>&1
```

- **導入済みなら**対象テキストを textlint にかけ、JSON 結果の各 `ruleId` を tone-guide カテゴリにマップして候補に統合する。

```bash
printf '%s' "$TARGET_TEXT" | textlint --stdin --stdin-filename target.md \
  --config "${CLAUDE_PLUGIN_ROOT}/skills/writing-polish/references/textlintrc.json" \
  --format json
```

  - 実行結果の **stdout が valid JSON なら**正常。指摘をマップする。
  - **stdout が valid JSON でなければ**（ルール解決失敗。stderr のエラー文字列だけでなく、textlint v15 が欠落時に出す `== No rules found ==`＝stdout 非 JSON・stderr 空も含む）、textlint 本体はあるが config が参照するルールパッケージ（`@textlint-ja/preset-ai-writing` 等）が未解決で決定的チェックの一部が効いていない。**警告を一度出して** LLM フォールバックする（fail させない）。判定は **JSON 妥当性に一本化**する（stderr 文字列マッチは v15 の失敗形を取りこぼす）。判定手順・警告文・導入コマンド・退路は `references/linter-integration.md`「ルール解決失敗の検出」を参照する。

- **未導入なら**、silent に skip せず一度だけユーザーへ確認する（通知なしに決定的レイヤーが落ちたまま推敲が走るのを防ぐ）。`AskUserQuestion` で「導入する」／「LLM 判定のみで続行」を提示し、導入コマンドと mise/nvm 環境向けの PATH/shim 注意を併記する。
  - 「導入する」→ 導入コマンドと注意を案内する。今回の推敲は LLM フォールバックで続行し（install 完了はブロックして待たない）、次回実行から決定的チェックが効く。
  - 「LLM 判定のみで続行」→ skip して LLM 判定のみで続行する（fail させない）。
- 以下のいずれかでは確認を出さず即 skip する（退路確保）:
  - **embed モード（`--embed`）**: 終端 prompt を出さない原則を優先し、silent に LLM フォールバックする（採否は呼び出し元が集約するため）。
  - 環境変数 `WRITING_POLISH_SKIP_LINTER_PROMPT` が設定されている（「毎回聞かれるのは煩わしい」向けの恒久 opt-out）。
  - 同一セッションで既に「LLM のみで続行」を選んでいる（セッション内は再確認しない）。
- 確認フローの詳細・導入コマンド・mise/nvm 注意、`ruleId` → カテゴリのマッピング表は `${CLAUDE_PLUGIN_ROOT}/skills/writing-polish/references/linter-integration.md` を参照する。
- linter 指摘も**最小差分・採否フロー・over-correction 抑制**に乗せる。機械判定でも文脈で不要なら採用しない。
- 拡張余地: 現在は textlint（日本語）。他 linter は `linter-integration.md` の手順で追加可能。

## 3. 差分提示（提示の正本: presentation-guide.md）

採用前に、何をどう変えるかを**変更箇所だけ**示す。全文の書き直しは出さない。提示と採否の記法は `references/presentation-guide.md` が SSOT。骨子は以下。

1. **冒頭サマリ行**: 件数・カテゴリ内訳と全採用時の確定インパクト（字数差・最長文長 before→after）を 1 行で先出しする。
2. **確信度で 2 群に分ける**: 各指摘の行頭に `[確実]`（安全に採用可）/ `[任意]`（好み・文脈次第）を付け、確実群を先に並べる。意味が動きうる修正には `[要確認]` を併記する。行頭マーカーはこの 2 軸まで（出自・測定値・読者・効果は理由文に溶かす）。
3. **理由は効能で書く**: tone-guide のカテゴリ番号・内部語彙（density / negative parallelism 等）を出さず、「原文の何が読み手の負担か → 修正でどう分かりやすくなるか」を 1 行で。想定読者・測定値・誤読シナリオ・認知効果・出自は任意で理由文に溶かす。
4. **保全を明示する**: over-correction を誘いやすい箇所を最大 2〜3 件、「あえて直さなかった箇所」として 1 行ずつ示す。
5. 連続変更はインライン囲み `〔原文 → 修正〕` で最小差分を見せる（コード片を含む対象は縦並び引用にフォールバック）。

各指摘の基本形:

```
[確実][冗長] することができます → できます
理由: 意味は同じで短く読める
```

- 修正が 0 件なら 1〜5 を出さず、「推敲の必要なし（冪等到達。これ以上の最小差分改善は検出されず）」と返して終わる（冪等。過剰に直そうとしない）。
- 同一セッションで却下された任意提案は再提示しない（省いたら 1 行明示する）。

## 4. 採否フロー

### 通常モード（`--embed` なし）

`AskUserQuestion` で採否を確認する。1 件ずつ大量に質問してレビュー疲労を起こさない。選択肢は**リスク昇順（保守 → 積極）**で並べ、既定を保守側に置く（`references/presentation-guide.md` 節 7）。

- 選択肢の例: 「確実な直しのみ（推奨・安全）」「確実 + 曖昧の具体化まで」「任意の言い換えも含め全部」「却下（原文維持）」。指摘の実構成に存在する群だけを選択肢にする（任意提案が 0 件なら「全部」を出さない）。
- 採用分のみ、対象がファイルなら `Edit` で反映する。会話テキストは編集先が無いため、推敲済み全文を提示して完了する。

### embed モード（`--embed` 指定 / 他プラグインからの呼び出し）

他プラグイン（pr-creator / git-commit-helper / issue-design 等）が soft 委譲してきた合図。**終端の AskUserQuestion を出さず、結果だけ返す**。採否は呼び出し元が集約する。

返却フォーマット（記法は `references/presentation-guide.md` 節 10。サマリ行・確信度マーカー・保全は prompt ではないので embed と両立する）:

```
<!-- POLISH_RESULT_START -->
<推敲済みテキスト全文>
<!-- POLISH_RESULT_END -->

推敲サマリ: 計N件（...）｜ 全採用で約X字減
変更点:
- [確実][冗長] 原文 → 修正案（理由）
- [任意][要確認] 原文 → 修正案（理由）
- ...

あえて直さなかった箇所:
- 「...」: <保全理由>

[embed-mode: polish-only, no-prompt]
```

- 変更が 0 件なら推敲済みテキストに原文をそのまま入れ、「変更点: なし」を返す（呼び出し元が空 diff を skip 判定できる）。
- 呼び出し元の厳守ルール（コミットの prefix・PR の文体・Issue の構造）を壊す修正は**自分で破棄**し、結果に含めない。

## effort による深さの調整

`${CLAUDE_EFFORT}` に応じて精査の深さを変える。

- **low / medium**: 確信度の高い指摘（カテゴリ 1〜4。ただし構文 tell＝negative parallelism・三点強迫・総括宣言は除く）に絞り、まとめて提示する。速度優先。linter チェック（ステップ 2.5）は決定的で軽いため low/medium でも実行してよい（導入済みの場合）。
- **high / xhigh / max**: カテゴリ 5〜7 と構文 tell、係り受け・代替言い換えまで精査する。カテゴリ 7（平易性・過剰抽象）はこの層でのみ発火させ、over-correction リスクを浅い effort で暴発させない。重要箇所は複数の言い換え案を出し、tone-guide の「複数観点で一貫して支持される修正」を優先採用する。

`--aggressive` 指定時は effort に関わらず、任意提案（気の利いた言い換え）まで含めて広く出す。ただし中核原則 1〜5 は維持する。

## やってはいけない

`references/tone-guide.md` の「アンチパターン」節を厳守する。要点の再掲:

- 無意味な言い換え / 過剰修正 / トーンの平準化 / 専門用語の不正確な置換 / 構造の破壊。
- 絵文字・装飾記号を足さない（ユーザーが明示的に求めた場合のみ例外）。
