# 推敲結果の提示ガイド（writing-polish 提示の正本 / SSOT）

writing-polish が推敲結果を**人間に見せ、採否させる**ときの正本。
`tone-guide.md` が「何を直すか（校正判断）」の SSOT であるのに対し、本ファイルは「直した結果をどう提示し、どう採否させるか（提示・採否 UX）」の SSOT。
他プラグインから `--embed` で委譲されたときも、提示記法は本ファイルに従う（終端 prompt を出さない制約とは節 10 で両立させる）。

## 設計原則: 提示は軽く、情報は厚く

人間に分かりやすい修正とは「全体像を掴み → 各修正がなぜ良いか効能で分かり → どれが確実でどれが好みか分かり → 安心して採否できる」状態を指す。これを満たしつつ提示が重くならないよう、次を絶対制約にする。

1. **行頭マーカーは最大 2 軸**（確信度 ＋ 必要時のみ要確認）。これ以上マーカーを増やさない。
2. **出自(textlint)・測定値・想定読者・認知効果はマーカーにせず、理由文の自然言語に溶かす**。理由の素材が増えてもマーカーは増やさない。
3. マーカーの乱立は AI っぽさ（`tone-guide.md` カテゴリ 4 の過剰強調）に反する。**提示の見やすさそのものが校正対象**であることを忘れない。

---

## 1. 提示の全体構造（この順序で出す）

1. 冒頭サマリ行（節 2）
2. 確実群 `[確実]`（節 3）
3. 任意群 `[任意]`（節 3）
4. あえて直さなかった箇所＝保全の明示（節 6）
5. 採否フロー（節 7。通常モードのみ。embed では出さない）

修正が 0 件なら 1〜5 を出さず、冪等メッセージ（節 8）を返して終わる。

## 2. 冒頭サマリ行（全体像の先出し）

diff 列挙の前に必ず 1 行で全体像を出す。指摘が多いとき、人間が全 diff を読む前に規模とカテゴリ偏りで採否方針を決められる。

```
推敲サマリ: 計N件（冗長a / 曖昧b / トーンc / AIっぽさd / 用語e / 平易化f）｜ 全採用で約X字減・最長文 Y→Z字
```

- **確定値のみ**（件数・カテゴリ内訳・字数差・最長文長）。「読みやすさスコア」等の主観・推定指標は出さない（演出過多は hype＝カテゴリ 4 違反）。
- 0 件のカテゴリ内訳は省く。インパクトが測れないとき（字数増減なし等）は件数だけ出す。

## 3. 確信度マーカー（行頭・必須・2 段階）

各指摘の行頭に確信度を 1 つ付け、**確実群を先・任意群を後**に並べる。群内は文書の出現順。

- `[確実]`: 安全に採用してよい。判定軸は `tone-guide.md`「適用の優先順位」の確信度定義に従う＝**決定的（linter 由来）または複数観点が一貫して支持する修正**。
- `[任意]`: 好み・文脈次第。**単一観点の言い換え・カテゴリ 7 平易化・構文 tell**（negative parallelism / 三点強迫 / 総括宣言）。

カテゴリ名は**人間語**で書く（`[冗長] [曖昧] [トーン] [AIっぽさ] [用語] [平易化]`）。tone-guide のカテゴリ番号や内部語彙（density / negative parallelism / 軽動詞構文 等）は**提示に出さない**——それらは判定の語彙であって読み手の語彙ではない。

行の形:

```
[確実][冗長] することができます → できます
理由: 意味は同じで短く読める

[任意][AIっぽさ] 単なる設定変更ではなく根本的な再設計だ → 設定変更ではなく再設計だ
理由: 「単なる〜ではなく」の対比を外しても主張は同じで、一文が短くなる
```

## 4. 要確認マーカー（任意・必要時のみ）

採用すると**意味が動きうる修正**には、確信度マーカーの直後に `[要確認]` を付す。発火条件は `tone-guide.md` カテゴリ 5・カテゴリ 7 の保全境界に準拠する。

- 採用すると意味が変わりうる
- 固有名・API 名・ドメイン用語に隣接する、またはそれ自体を言い換える
- 能動/受動の変換で主語・行為主体が変わる

理由文に「何が変わりうるか／残す選択もある」を 1 句添える。

```
[任意][要確認][平易化] リトライ機構 → 再試行の仕組み
理由: 平易化だが、読者がエンジニアなら原語の方が短く正確。残す手もある
```

`[確実]/[任意]`（改善の確からしさ）と `[要確認]`（採用時の副作用リスク）は**直交する軸**。両立して付く。

## 5. 理由文の書き方（効能の言語化）

理由は「規範の言い切り」ではなく「**読み手にとっての効能**」で書く。緩い型（埋まる要素だけ使う。全要素を無理に埋めない）:

> 〔原文の何が読み手の負担か〕→〔修正でどう速く正確に読めるか／誰にとって〕

- before（内部語彙が漏れた例）: `理由: negative parallelism の濫用を是正`
- after（効能で書く）: `理由: 「単なる〜ではなく」の対比を外しても主張は同じで、一文が短くなる`

理由文に**マーカーにせず溶かしてよい素材**（節 1-2 の原則。いずれも任意・該当が明確なときだけ）:

- **想定読者**（`tone-guide.md` 文書種別表の「想定読者」列から引く）: 「後で読む一般開発者には範囲が伝わらない」
- **測定値**（手元にあるときのみ。無ければ省略し、全件付与は禁止）: 「この一文は 118 字・読点 4 個で係り受けを追いにくい（目安 100 字/読点 3 個）」。**しきい値は目安であり発火の絶対基準ではない**（`tone-guide.md` 冒頭注記）。100 字未満でも読みにくければ直し、120 字でも明快なら残す——測定値は理由の補強であって、数値を満たすためだけの機械的分割（over-correction）を誘発しない。
- **認知効果**（該当が明確なときのみ 1 フレーズ）: 「具体語は抽象語より速く正確に読める（concreteness effect）」。全件に研究名を貼らない（衒学化はカテゴリ 7 違反）。
- **出自**（textlint 由来のときのみ）: 「textlint が決定的に検出」。LLM 判定由来は何も足さない（**非対称表記**で視覚ノイズを抑え、機械が再現的に拾った指摘だけ識別できるようにする）。
- **誤読シナリオ**（係り受け・曖昧語で書けるとき）: 「『古い、データを削除した設定』とも『古いデータを、削除した設定』とも読める」。誤読例が書けない指摘は実は曖昧でない可能性が高く、**書けないなら出さない**（over-correction フィルタとして機能する）。

## 6. あえて直さなかった箇所（保全の明示）

`tone-guide.md` 中核原則「変更不要箇所を明示的に保全する」を**提示でも体現する**。直さなかった判断を軽く見せ、「見落とし」ではなく「意図的な保全」だと分かるようにする＝over-correction していない安心を与える。

- 末尾に**最大 2〜3 件**、1 行ずつ。over-correction を誘いやすい箇所を優先する（流暢性の名目で書き換えたくなるが意図は通る箇所／原文の声が出た口語／判断が割れたドメイン語）。
- **全列挙しない**（網羅すると提示肥大＝それ自体が分かりにくさになる）。保全が自明・該当なしなら節ごと省略してよい。

```
あえて直さなかった箇所:
- 「ざっくり言うと」: 砕けた書き出しは原文の声。曖昧語だが導入として機能している
- 「冪等性」: ドメイン用語。読者が開発者なので平易化せず温存
```

## 7. 採否フロー（通常モードのみ）

`AskUserQuestion` の選択肢は**リスク昇順（保守 → 積極）**で並べ、既定を保守側に置く。カテゴリ軸ではなく「どこまで踏み込むか」軸にする。

```
「確実な直しのみ（推奨・安全）」「確実 + 曖昧の具体化まで」「任意の言い換えも含め全部」「却下（原文維持）」
```

- 指摘の**実構成に存在する群だけ**を選択肢にする（任意提案が 0 件なら「任意の言い換えも含め全部」を出さない）。
- 既定誘導が保全側に働くことで、結果的に over-correction の実害が減る。
- 選択肢の「確実 / 任意」語彙は節 3 と一致させる（不一致は混乱の元）。

## 8. 冪等の可視化（無限に直し続けない信頼）

- **0 件再実行**: 「推敲の必要なし」を一歩進めて冪等到達を明示する。
  `推敲の必要なし（冪等到達。これ以上の最小差分改善は検出されず）`
- **却下を跨ぐ再実行**: 同一セッションで却下された任意提案と同型の提案を**再提示しない**。省いたら 1 行明示する。
  `（前回却下された任意提案 2 件は再提示していません）`
- 一度平易化・短縮した語をさらに直さない（`tone-guide.md` カテゴリ 7 冪等停止条件と整合）。

## 9. 連続変更の段落対比

`tone-guide.md` 最小差分原則を**見た目でも**伝える。段落丸ごとの二度書き（差分が埋もれる）を避ける。

- 変更が密な段落は**インライン囲み** `〔原文語 → 修正語〕` で最小差分を視覚化する。不変箇所はそのまま見せ、構造を壊していないことを目視できるようにする。

```
〔本機能を利用することにより → 本機能で〕ユーザーは〔設定を行うことが可能となります → 設定できます〕。既定値で動作します。
```

- 対象が**コードブロック / コード片を含む**場合は囲みを使わず、`原文:` / `修正:` の縦並び引用にフォールバックする（囲み記号 `〔 〕` とコード中の文字の衝突を避ける）。

## 10. embed モードでの提示

`--embed`（他プラグインからの soft 委譲）では:

- **節 7 の終端 `AskUserQuestion` は出さない**（採否は呼び出し元が集約）。
- サマリ行（節 2）・確信度マーカー（節 3）・要確認（節 4）・保全（節 6）は「変更点」セクションに含めてよい。これらは prompt ではなく**記法**なので embed 制約と両立する。呼び出し元はマーカーを見て採否を集約できる。

```
<!-- POLISH_RESULT_START -->
<推敲済みテキスト全文>
<!-- POLISH_RESULT_END -->

推敲サマリ: 計2件（冗長1 / 任意1）｜ 全採用で約12字減
変更点:
[確実][冗長] することができます → できます（意味は同じで短く読める）
[任意][AIっぽさ] ... → ...（対比強調を外しても主張は同じ）

あえて直さなかった箇所:
- 「冪等性」: ドメイン用語。読者が開発者なので温存

[embed-mode: polish-only, no-prompt]
```

## effort 連動

`${CLAUDE_EFFORT}` に応じて提示の厚みを変える（`SKILL.md` の effort 分岐と一致させる）。

- **low / medium**: サマリ（節 2）・確実群（節 3）・効能理由（節 5 の基本）・保全 1 件まで（節 6）。任意群 `[任意]`・`[要確認]`・誤読シナリオ・インライン囲み（節 9）・認知効果ラベルは**出さない**（浅い effort で over-correction と提示過多を暴発させない）。**例外: コードコメント種別の削除提案は low/medium でも出す**。コメント種別では what 削除が主目的で、削除は常に `[任意][要確認]` を付す設計のため、この抑制をそのまま適用すると既定 effort（medium）で機能が空振りする。削除提案だけはこの抑制対象から外す（`code-comment-guide.md`「提示・採否での扱い」「effort 連動」参照）。
- **high / xhigh / max**: 任意提案・測定値の精緻化・誤読シナリオ・認知効果ラベル・保全 2〜3 件まで含めて出す。
