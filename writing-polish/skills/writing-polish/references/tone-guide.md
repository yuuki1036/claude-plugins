# 文章添削トーンガイド（writing-polish 正本 / SSOT）

writing-polish が文章を推敲・添削するときに参照する校正ルールの**正本**。
他プラグイン（pr-creator / git-commit-helper / issue-design 等）から委譲されたときも、本ファイルが唯一の判断基準になる。

## 出典と位置づけ

校正カテゴリは以下の公開ルールセット・スタイルガイドを統合したもの。各カテゴリ末尾に出典を記す。

- textlint-ja: `preset-japanese` / `preset-ja-technical-writing` / `preset-ai-writing` / `preset-JTF-style`
- Vale（style-guide-as-code）: 11 種の固定チェックタイプ
- Google developer documentation style guide / Microsoft Writing Style Guide
- 過剰修正（over-correction）・最小編集に関する一次研究（arXiv 2512.12544 HyperEdit / 2502.13358 FineEdit）

> **しきい値は目安**: 「文長100字」「読点3個」等は textlint の configurable default 由来で、絶対的な hard cap ではない。文脈で逸脱を許容する。
> **適用範囲の注記**: 過剰修正の知見は元来 GEC（文法誤り訂正）研究のもの。PR/Issue/コミットの推敲への転移は妥当だが、論文が直接検証した範囲ではない。

## textlint / Vale 委譲境界（決定的検証 > LLM 判定）

判定は LLM が散文ルールを読んで行うが、観点には「機械的に確実なもの」と「文脈判断が要るもの」がある。決定的に拾えるものは linter に委譲する前提で設計し、LLM は文脈判断に集中する（リポジトリ方針「決定的 hook > LLM 判定」と整合）。将来 textlint/Vale を実行委譲する場合の棲み分け指針でもある。

**linter に委譲できる（決定的・誤検知が少ない）**
- 表記・スペース・記号（半角カナ / 機種依存文字 / 括弧対応 / 文末記号統一）
- 文法系（ですます/である混在 / ら抜き / 二重否定 / 助詞連続 / 同一語連続）
- 確実な冗長構文（「〜を行う」→「〜する」, `ja-no-redundant-expression` dict5/6, allows 付きで安全）
- しきい値（文長 / 読点過剰 / 連続漢字）
- 差別的表現ブラックリスト（alex 系）

**LLM が担う（文脈・行為主体・自然さの判断が必須）**
- 名詞化の良性/悪性判定（given-new 結束は温存、動作隠蔽のみ直す）
- 衒学語 → 平易語の文脈依存の言い換え（カテゴリ 7）
- ヘッジが「逃げ」か「正当な留保」か
- 翻訳調・AI っぽさの density 判断（1 個では問題なく、密度で判断する）

> textlint（日本語）は `references/linter-integration.md` の手順で**実行委譲する**（導入済み環境）。Vale（英語）は未実行（将来同型で追加）。**未導入の環境では、linter に委譲した観点も LLM が判定する**（決定性・再現性は劣るが検出は試みる）。導入済みなら linter の決定的判定を優先し、LLM はそれに乗らない指摘に集中する。

出典: リポジトリ CLAUDE.md「ルール配置の意思決定（決定的 hook > LLM 判定）」, textlint-ja 各 preset, Vale `vale.sh`

## 最上位メタルール: 文書種別で文体を使い分ける

文体（敬体/常体）は**文書の種別ごとに選び、1 文書内では混在させない**。これが他のすべてのルールに優先する。

| 文書種別 | 既定の文体 | 想定読者 | 補足 |
|---|---|---|---|
| コミットメッセージ | 常体・体言止め | 一般の開発者（後でログを辿る人） | `<type>(<scope>):` prefix と言語設定は変更しない |
| PR description | 常体・体言止め | 一般の開発者（レビュアー） | 一人称を省く |
| Issue 本文 | 敬体可（常体でも可。1 文書内で統一） | 一般の開発者（後で着手する人） | セクション構造は壊さない |
| RFC / 設計ドキュメント | 常体・断定形 | 当該分野の専門家 | 厳密層ルール（後述）を強めに適用 |
| ADR の決定事項 | 常体・断定形 | 当該分野の専門家 | 曖昧さを残さない |
| レビュー返信・コメント | 敬体 | 特定の相手 | 相手への配慮を残す |

- 敬体/常体の混在検出は textlint `no-mix-dearu-desumasu` に対応。
- 文体を**勝手に変換しない**。対象が既にどちらかに統一されていれば、その文体を保ったまま推敲する。
- **想定読者は理由文の主語に使う**（提示時。`references/presentation-guide.md` 節 5 で「誰にとって分かりやすくなるか」の根拠にする）。カテゴリ 7 の読者推定もこの「想定読者」列を参照する。

出典: textlint `preset-JTF-style`（JTF スタイルガイド 1.1.1「目的に応じて敬体・常体のどちらかに統一する」）, `no-mix-dearu-desumasu`

## カテゴリ 1: 冗長・密度（日英共通）

- **冗長表現を削る**。意味が変わらない範囲で語を減らす。
  - 例: 「することができる」→「できる」、「〜という点において」→「〜で」、「〜を行う」→「〜する」
  - これらは**例示であって網羅辞書ではない**。機械的な置換表として扱わず、意味が保たれるかを毎回判断する。
- **一文一義**。長い一文は分割を検討する（目安: 100 字、読点は一文に 3 個まで）。
- **filler を削る**。「基本的に」「ある意味」「しっかりと」など中身のない語。
- **空セクションを残さない**（「特になし」だけのセクションは削るか統合する）。

出典: textlint `preset-ja-technical-writing`（`sentence-length` / `max-ten` / `ja-no-redundant-expression`）, Vale `substitution`・`repetition`, `preset-ai-writing`（`ai-tech-writing-guideline`）
※ `ja-no-redundant-expression` の「冗長表現を 6 カテゴリの辞書に分類できる」という主張は本リサーチで refuted（0-3）。カテゴリ正本としては採用せず、上記のとおり例示にとどめる。

## カテゴリ 2: 曖昧さの除去

- **曖昧語を具体化する**。「ちょっと」「いい感じ」「ざっくり」「だいぶ」→ 数値・範囲・固有名に置き換える（例: 「だいぶ速い」→「約 3 倍速い」）。
- **弱い断定を精査する**。「かもしれない」「〜と思います」「たぶん」「〜のはず」は、根拠があるなら断定に、不確実なら不確実性の理由を添える。
- **係り受けを一意にする**。修飾語がどこに掛かるか複数解釈できる文を、語順や読点で一意化する。
- **誤読を言語化する**（提示時）。係り受け・曖昧語の指摘は、可能なら「誤った読み方 A / 意図した読み方 B」を理由に併記する（`references/presentation-guide.md` 節 5）。誤読例が書けない指摘は実は曖昧でない可能性が高く、書けないなら出さない（over-correction フィルタ）。

出典: textlint `ja-no-weak-phrase`（弱い断定）, `preset-ja-technical-writing`（係り受け・読点）

## カテゴリ 3: トーンと姿勢

- **過度な謝罪・卑下を避ける**。「申し訳ありません」「すみません」の連発、不要な前置きの謝罪を削る。
- **意見は和らげ、決定・事実は断定する**。
  - 異議・提案: 「それは違います」→「別の観点もあります」のように議論を閉じない。
  - 決定事項・仕様・事実: 曖昧さを残さず断定形で書く（ADR・spec はこちら）。
- **皮肉・受動攻撃・責任転嫁を避ける**。「言うまでもなく」「ご存知のとおり」「○○さんの責任で」等。
- **盲従表現を避ける**。「言われた通りにします」のように判断の理由が見えない表現。

出典: 一般的なコードレビュー・コミュニケーション作法（過度な謝罪回避・断定で議論を閉じない・皮肉回避）、設計文書の慣習（決定事項・仕様は断定形で書く）

## カテゴリ 4: AI っぽさの除去（構造を縛り、表現は縛らない）

特定の語彙を禁止するのではなく、**AI が生成しがちな構造パターン**を是正する。

- **過剰な箇条書き**を避ける。因果・背景・流れのある内容は散文で書く。並列情報だけ箇条書きにする。
- **過剰な太字強調**を避ける。太字は本当に強調すべき箇所のみ。
- **hype 表現**を避ける。「劇的に」「圧倒的に」「シームレスに」等の中身のない誇張。
- **重複した前置き**を削る。「まず最初に」→「まず」、「あらかじめ事前に」→「事前に」。
- **絵文字・装飾記号を使わない**（✅❌🤖 等を含む）。ユーザーが明示的に求めた場合のみ例外。
- **対句の濫用（negative parallelism）**を避ける。「〜ではなく、〜だ」「単なる X ではなく Y」を多用しない（1 回は修辞、連発は AI tell）。
- **三点強迫**を避ける。必要のない第 3 要素まで強迫的に並べない（「高速・堅牢・柔軟」のような埋め草）。
- **総括の宣言**を避ける。「結論として」「まとめると」と明示しなくても結論が伝わる構成にする。

出典: textlint `preset-ai-writing`（`no-ai-list-formatting` / `no-ai-emphasis-patterns` / `no-ai-hype-expressions` / `ai-tech-writing-guideline`）, リポジトリ規約・グローバル設定（絵文字回避）, Wikipedia「Signs of AI writing」(https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing)

## カテゴリ 5: 用語と正確性

- **用語の一貫性**。同一概念に複数の語を使わない（「ユーザ」「ユーザー」混在、「ログイン」「サインイン」混在等）。
- **能動態を基本にする**。受動態は主語をぼかすときだけ。「修正された」→「修正した」。
- **抽象を具体に**。「高速な処理」→「50ms 未満の処理」のように測れる表現にできるなら置き換える。
- **専門用語を不正確に置換しない**（アンチパターン参照）。意味が変わる言い換えはしない。
- **理由には認知的効果を添えてよい**（提示時・任意）。具体化の指摘は「具体語は抽象語より速く正確に読める（concreteness effect）」のように、なぜ読み手の負担が減るかを 1 フレーズで示せる（`references/presentation-guide.md` 節 5。全件に研究名は貼らない）。

出典: Vale `consistency`, textlint `ai-tech-writing-guideline`, Google / Microsoft style guide（能動・簡潔・具体）

## カテゴリ 6: 英語技術文書（日英両対応）

英語テキストには Vale の 11 チェックタイプのうち以下を当てる。

- `existence`（禁止語・不要語の検出）, `substitution`（冗長句→簡潔句）, `repetition`（連続重複）, `consistency`（用語一貫性）, `capitalization`（見出し・用語の大文字化）, `metric`（可読性 / Flesch-Kincaid）
- Google / Microsoft style guide の基本姿勢: **簡潔・能動態・二人称（you）・現在形**、長い名詞句の分解。

出典: Vale `vale.sh/docs/styles`, `developers.google.com/style`, `learn.microsoft.com/style-guide`

## カテゴリ 7: 平易性 / 過剰抽象（over-abstraction）

カテゴリ 4 が「構造」を、カテゴリ 5 が「測定可能性」を見るのに対し、ここは**語彙の抽象度**を見る。内容は正しいが過度に抽象的・衒学的で、平易語で書けるのにもったいぶった表現を、読者の認知負荷が下がる方向へ開く。

**方針: 固定対訳を正本に載せない**。文脈依存の言い換え（同じ抽象語でも文脈によって最適な平易語が変わるもの）は、`A → B` の対訳をここに刻まない。n=1 の事例への過適合で汎化せず、正本が辞書化して肥大し、未知の表現には無力だからである。正本が持つのは**発火条件と保全基準**のみで、言い換え案は LLM がその場の文脈から都度導く。例外として、文脈非依存の決定的変換（軽動詞構文。textlint dict5/6 由来）だけは例示してよい。

**用語の操作的定義（判定の土台）**
- **抽象名詞**: 指示対象を観察・実測・コード参照で確かめられない名詞。目安は「〜性」「〜論」「〜観」「〜化」等の接尾辞を持つ漢語や、多義で動作が見えないサ変名詞。
- **具体語**: 固有名・API 名・数値・ファイル名、または観察可能な事象（「null を返す」「タイムアウトする」「3 回リトライする」等）。

**発火条件（構造シグナル。単独の語の存在では発火させない）**

以下のいずれかの**構造**に該当したときのみ発火候補とする。
1. **束ね位置の抽象漢語（共起シグナル）**: 同一文脈に具体語・具体的事象が 2 つ以上列挙され、それらを要約・分類する位置に立つ語**だけ**が抽象漢語のとき。列挙の具体度と束ね語の抽象度の落差が大きいほど確信度を上げる。判定の決め手は**置換テスト**: 束ね語を「こうした挙動」「これらの問題」等の平易な指示表現に置換しても情報が失われないなら、列挙が情報を担っており束ね語は飾りなので発火する。
2. **動作を隠す名詞化（軽動詞構文。決定的変換なので例示可）**: サ変名詞 + 形式動詞で動作主体が埋もれるとき。
   - 例: 「最適化を図る」→「最適化する」、「検討を行う」→「検討する」、「〜の実現」→「〜する」
3. **借り物の荘厳さ（prestige metaphor）**: 具体的関係を説明する代わりに荘厳な比喩語で代替しており、**その語を消しても文の情報量が減らない**とき（消去テスト）。英 tapestry / landscape / realm、和文の「世界観」「文脈」の安易な多用が典型。
4. **density 判定**: 一文に抽象名詞が 3 つ以上連なり、かつ具体語が 1 つもないとき。抽象名詞が多くても具体語が併存していれば発火しない（具体で裏打ちされた抽象は正当）。

**判定手順（再現可能な手続き）**
1. 候補文の名詞を操作的定義に従って抽象/具体に仕分ける
2. 構造シグナル 1〜4 のどれに該当するか特定する（該当なしなら発火しない）
3. 保全基準（下記 1〜3）に当たらないか確認する（当たれば残す）
4. 通過した場合のみ、言い換え案を**その文脈から**生成して提示する。理由には該当した構造シグナルを明記する

**言い換える / 残すの判断（over-correction 回避。満たさないものは保全する）**
平易化は「専門用語を抜く」ことではない。保全基準は**その語が文中で情報を担っている場合**に適用する。構造シグナル 1 の置換テストが成立する（平易な指示表現に置換しても情報が失われない）束ね語は、語自体が正当な専門用語であっても**その文では飾り**なので保全しない。情報を担っている語のうち、次のいずれかに当たるものは**残す**。
1. 読者がその語彙を共有しており、かつ**その分野の定義どおりの意味で使われている**（その分野で平易語より短く正確）。定義から外れた緩用・比喩的転用（学術用語を「雰囲気」で借りているだけの使用）は保全せず、構造シグナルに照らして判定する。読者が語彙を共有するかは**文書種別から推定**する（最上位メタルールの文書種別表「想定読者」列を参照。README も一般の開発者とみなす）
2. 精度が要求され、正確な等価語がない
3. 平易語に置換すると曖昧さが生じる

AI 頻出の抽象語（「実現」「対応」「サポート」、英 delve / leverage / utilize 等）は**人間も使う**（AI linguistic imprinting）ため、単語の存在を証拠にしない。density・共起・文脈で判断する。これらは**例示であり辞書ではない**（カテゴリ 1 末尾注記と同じ扱い）。

**理由の効果ラベル（提示時・任意）**: 平易化の指摘は「具体語は処理が速い（concreteness effect）」等、認知負荷が下がる方向を 1 フレーズで添えてよい（`references/presentation-guide.md` 節 5）。該当が明確なときのみ。全件貼りは衒学化なので避ける。

**冪等の停止条件**: 一度平易化した語をさらに平易化しない。原文がすでに具体的なら推敲不要とする。

出典: plainlanguage.gov「avoid jargon ≠ remove necessary terms」(https://digital.gov/guides/plain-language/principles/avoid-jargon), nominalization / zombie nouns（H. Sword, TED-Ed: https://ed.ted.com/lessons/beware-of-nominalizations-aka-zombie-nouns-helen-sword）, concreteness effect（具体語の想起・処理速度優位: https://pmc.ncbi.nlm.nih.gov/articles/PMC6687846/）, AI 過剰語彙（excess vocabulary: https://arxiv.org/html/2406.07016v1）, textlint `ja-no-redundant-expression` dict5/6（確実な構文のみ委譲: https://github.com/textlint-ja/textlint-rule-ja-no-redundant-expression）

## やってはいけない（アンチパターン）

校正そのものを劣化させる失敗。**これらに該当する修正は提案しない**。

1. **無意味な言い換え**: 意味も明瞭さも変えず語だけ差し替える（「使用する」↔「利用する」のような往復）。改善が説明できない修正はしない。
2. **過剰修正（over-correction）**: 文法的に正しく意図も通る箇所を、流暢性向上の名目で書き換える。慎重なプロンプトでも残存する現象なので、**変更不要箇所は明示的に保全する**。保全は内部判断に留めず**提示でも明示する**（`references/presentation-guide.md` 節 6「あえて直さなかった箇所」。見落としではなく意図的な保全だと分かるようにする）。
3. **トーンの平準化**: 書き手の口調・個性・リズムを、無難で均質な「AI 文体」に均してしまう。原文の声を保つ。
4. **専門用語の不正確な置換**: ドメイン用語・API 名・固有名を、一般語に置き換えて意味を壊す。
5. **構造の破壊**: コミット prefix、PR テンプレート、Issue のセクション構造、コードブロック、リンクを変更する（文面のみ推敲し、構造は触らない）。

出典: 過剰修正・最小編集の研究（arXiv 2512.12544 HyperEdit「difference-aware regularization で過度な編集を防止」/ 2502.13358 FineEdit「precise and targeted text modifications」）

## 適用の優先順位（迷ったとき）

1. 構造・コード・固有名を壊さない（最優先・絶対）
2. 文書種別の文体に合わせる
3. 意味を変えない範囲で冗長・曖昧を削る
4. トーン・AI っぽさを整える
5. 平易化（カテゴリ 7）・「気の利いた言い換え」は最後。確信が持てる場合のみ、任意提案として出す（high/xhigh/max effort 限定）

> 不確実な修正を多数出すより、**明確に改善する少数の修正**を出す。妥当な修正ほど複数の観点で一貫して支持されやすい（過剰修正研究の知見。本リサーチでは関連 arXiv 番号の実在を確認できなかったため一般原則として記す）。

### 確信度の判定（確実 / 任意）

提示時に各修正へ付ける確信度マーカー（`references/presentation-guide.md` 節 3）の判定軸。これが「どこまで安全に採用してよいか」の SSOT。

- **確実**: 決定的（linter 由来）、または複数の観点が一貫して支持する修正。意味を変えず改善が一意。優先順位 1〜3 に対応する修正が典型。
- **任意**: 単一観点の言い換え、平易化（カテゴリ 7）、構文 tell（negative parallelism / 三点強迫 / 総括宣言）。好み・文脈次第で、却下されても改善は損なわれない。優先順位 5 に対応。

> 妥当な修正ほど複数観点で一貫して支持される＝確実に倒れやすい。確信度はこの経験則の提示側ミラーで、人間が「確実分はまとめて採用、任意分だけ吟味」という二段採否をできるようにするためのもの。
