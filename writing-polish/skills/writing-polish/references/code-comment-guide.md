# コードコメント校正ガイド（writing-polish / code-comment サブ正本）

対象が**コードコメント**種別のときに参照する追加正本。散文の正本は `tone-guide.md`、提示・採否 UX の正本は `presentation-guide.md`。本ファイルはコメント固有の観点（what 削除・残す情報フィルタ・subtype 別保全境界）だけを持ち、冗長・AI っぽさなど散文と共通の観点は `tone-guide.md` を併用する（薄く保つ＝二重管理を作らない）。

## なぜ散文と処理を分けるか

散文校正は「語句をどう言い換えるか」（言い換え中心）。コメント校正は「**このコメントは要るか**（残す / 凝縮 / 削除）」の判定が先に立つ。ベクトルが違うため、散文カテゴリをそのまま当てても最重要の観点（コードから自明な what を削る）が拾えない。

## コメントの subtype 分類（保全境界の土台）

校正対象と保全対象を subtype で仕分ける。ここを外すと over-correction でコメントを壊す。

| subtype | 例 | 扱い |
|---|---|---|
| インラインコメント | `//` `#` の行末・行頭 | **校正・削除の主対象** |
| ブロックコメント | `/* */` の複数行 | 校正対象。段落説明は散文として tone-guide も併用 |
| docstring / API doc | `"""..."""` / `/** */` / `///` | **what 削除の対象外**（API 契約なので what を書くのが正当）。冗長・簡潔のみ当てる |
| TODO / FIXME / HACK / XXX / NOTE / WARNING | `// TODO: ...` | **保全**。意図的マーカーは削除しない |
| ライセンス・著作権ヘッダ | ファイル冒頭の SPDX 等 | **保全**。触らない |
| 区切り・見出しコメント | `// ===== Auth =====` | **保全**。構造マーカー |
| コメントアウトされたコード | `// return oldValue` | **対象外**。削除是非は実装判断／code-review の領分で、文章校正が触る範囲でない |

## 観点 A: what コメントの検出（コメント固有・最重要）

### 判定手順（単体自明性テスト）

コメント**単体**を見て、それが被コメント行の**機械的な言い換え**に閉じているかだけを判定する。「コメントとコードが**矛盾**しているか」（正しさの検証）には踏み込まない — それは code-review の領分であり、ここで越境すると別プラグインの再発明になる。

1. コメントの記述を、被コメント行だけ見れば復元できる情報（what）と、コードに現れない情報（why / 制約 / gotcha / 意図 / 背景）に仕分ける。
2. コメント全体が what のみ＝コード行の逐語訳なら削除候補にする。
3. why / 制約 / gotcha / 意図が**少しでも**混じるなら保全する。混在時は what 部分だけ凝縮する提案に留め、why は必ず残す。

### 発火条件（厳格・fail-closed）

削除候補にできるのは、次を**すべて**満たすときだけ。

- コメント全体が被コメント行と 1:1 対応する（`i++  // i をインクリメント`、`return null  // null を返す`）。
- why（なぜこの実装・順序・値か）・制約・gotcha・意図・背景を一切含まない。
- docstring / TODO 等の保全 subtype でない。

一つでも満たさない、または判断が割れるなら**保全側に倒す**（fail-closed）。「一見 what だが実は非自明」を消す事故を防ぐことを、検出漏れを減らすことより優先する。

削ってはいけない例（what に見えて why を含む）:

- `// 昇順でソート（後段の二分探索が前提）` — 昇順は `sort` から自明でも「二分探索の前提」という why を含む。
- `// あえて await しない（fire-and-forget）` — コードから意図は復元できない。

## 観点 B: 残す情報のフィルタ

コメントに残す価値があるのは、コードから復元できない情報に限る。

- **why**: なぜこの実装・順序・値なのか
- **制約・前提**: 外部 API のバグ回避、順序依存、スレッド・並行性の前提
- **gotcha**: 直感に反する挙動、踏みやすい罠
- **意図**: fire-and-forget、意図的な no-op、暫定対応の理由

これら以外（what の逐語訳）が観点 A の削減対象。

## 観点 C: 冗長・簡潔・AI っぽさ（tone-guide 併用）

コメント文脈の冗長は `tone-guide.md` カテゴリ 1、AI っぽさ（装飾絵文字・hype・過剰強調）はカテゴリ 4 に委譲し、本ファイルで辞書化しない。コメント特有の適用ポイントだけ挙げる。

- コメントは 1 行で足りることが多い。中身のない前置き（「ここでは〜」「〜しています」）を削り、体言止め・簡潔形に寄せる。
- ただし原文の声・チーム慣習は保つ（中核原則 3）。均質な機械コメントに均さない。

## over-correction ガード（コメント版）

- 削除は**不可逆度が高い**。散文の言い換え却下は原文維持で無害だが、コメント削除の誤採用はコード上の情報損失で、後段の読者を困らせ、`Edit` で実ファイルが変わる。確信が持てないコメントは残す。
- 判断が割れたら削除でなく**凝縮**を提案する。

## 提示・採否での扱い（presentation-guide 準拠）

- コメント削除提案には `[確実]` を付けない。**常に `[任意][要確認]`** に倒す（削除は意味が動く＝副作用が不可逆）。
- 削除は新アクションを足さず、`presentation-guide.md` の既存採否フローで「修正案＝削除」として表現する。段落対比（節 9）はコード片を含むため `原文:` / `修正: （削除）` の縦並び引用にフォールバックする。
- 削除提案には保全明示（節 6）を必ずセットにし、「なぜ消してよいと判断したか（コード行と 1:1・why 無し）」を理由に書く。

## effort 連動

`${CLAUDE_EFFORT}` に応じて深さを変える（`SKILL.md` の effort 分岐と一致させる）。

- **low / medium**: 観点 A（発火条件を満たす明白な what 逐語訳の削除）＋明白な冗長のみ。確実分だけ。削除提案は `[任意][要確認]` を付すが、**presentation-guide の low/medium 抑制の例外として出す**（コメント削除が主目的で、抑制すると既定 effort で機能が空振りするため。`presentation-guide.md`「effort 連動」参照）。
- **high / xhigh / max**: 観点 B の why 言い換え・凝縮、ブロックコメントの再構成まで。

## やってはいけない（コメント固有のアンチパターン）

1. 判断の割れる what を機械的に削る（発火条件違反）。
2. docstring / JSDoc の what を削る（API 契約）。
3. TODO / FIXME / ライセンス / デッドコードに触る。
4. コメントとコードの**正しさ**（整合・不整合）を判定する（code-review の領分。単体自明性テストを越えない）。
5. コメント内のコード識別子・型名・API 名を言い換える（構造破壊。中核原則 4）。
