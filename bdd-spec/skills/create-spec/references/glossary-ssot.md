`{featuresDir}/all_spec.md` のテンプレートと用語 SSoT 運用ルール。

```markdown

# 用語 SSoT

このプロジェクトで使う用語の Single Source of Truth。
全 epic.md / spec.md は **この辞書に従う**。別名・略称・表記揺れは禁止。

## ドメイン用語

| 用語 | 定義 | 別名禁止リスト | 関連 |
|------|------|---------------|------|
| 契約書 | 顧客との合意内容を記録した法的文書 | 契約 / 契約文書 / Contract → 全て「契約書」に正規化 | [契約管理者] |
| 契約管理者 | 契約書の作成・承認・廃棄を行う権限を持つロール | 管理者（曖昧） / Contract Admin → 「契約管理者」 | [契約書] |
| 一括承認 | 複数契約書を 1 回の操作で承認する機能 | バルク承認 / Bulk Approve → 「一括承認」 | [契約書] |

## ステータス語彙

| ステータス | 意味 | 遷移可能先 |
|----------|------|-----------|
| draft | 下書き | review |
| review | レビュー待ち | approved / rejected |
| approved | 承認済み | （終端） |
| rejected | 差戻し | draft |

## 数量・閾値

| 名前 | 値 | 根拠 |
|------|-----|------|
| 一括承認上限件数 | 100 件 | UI の表示パフォーマンス確保 |
| セッションタイムアウト | 30 分 | OWASP 推奨 |

## 別名禁止メタルール

1. **同義語を見つけたら左カラムに正規形を残し、右カラムに別名を列挙**
2. epic.md / spec.md 執筆時、別名を使った時点で `bdd-spec-evaluate`（Phase 2）が warning を出す
3. **新規用語は spec.md / epic.md の「用語」セクションで導入** → 確定後に all_spec.md へ昇格

## 用語追加フロー

```
1. epic.md / spec.md の「用語」セクションにローカル用語として書く
2. レビューで概念が確定する
3. all_spec.md にエントリ追加（別名禁止リストも同時に整備）
4. 該当 spec.md の「用語」セクションから該当行を削除
```

## 設計判断

### 用語 SSoT を `features/all_spec.md` に置く理由

- BDD spec は **用語の食い違い** で破綻しやすい（「契約書」と「Contract」が混在する等）
- 1 ファイル SSoT にすると LLM agent が読みに行く先が明確
- `features/` 直下に置くことで story ごとの spec.md と相対パスで近い

### 別名禁止リストを表に組み込んだ理由

- 「正規形だけ」を書いた辞書だと、別名を見つけても「これは別物では？」と判断が揺れる
- 別名禁止リストを明示することで「これは正規形 X の別名なので置換する」判断ができる

### 「ステータス語彙」と「数量・閾値」を切り出した理由

- ドメイン用語と混ぜると一覧性が落ちる
- ステータス遷移 / 閾値根拠は spec.md の Scenario 設計に直接影響するため、辞書に近い場所で参照したい
