# ADR-20260529143012: API は URL パスにメジャーバージョンを含める

## ステータス

accepted（2026-05-29）

## コンテキスト / 背景

公開 REST API を提供しており、破壊的変更時に既存クライアントを壊さない仕組みが必要。
バージョニング方式として URL パス / ヘッダ / クエリパラメータの 3 案があった。

## 決定

すべての公開エンドポイントを `/v1/...` のように URL パスにメジャーバージョンを含める形式とする。
マイナー変更は後方互換を保ち、バージョンを上げない。

## 影響 (Consequences)

- **良い影響**: URL を見ればバージョンが自明。キャッシュ・ルーティングが単純
- **悪い影響**: バージョン跨ぎの共通ロジックでパス分岐が増える
- **トレードオフ**: ヘッダ方式の「URL を変えずに済む」柔軟性を捨て、可視性・運用単純さを取った

## 適用方法 (Enforcement)

機械強制できる。
- ルーティング定義の test で、全公開エンドポイントのパスが `^/v[0-9]+/` にマッチすることを assert する
- CI に「`/v` プレフィックス無しの公開ルートを追加したら fail」する lint を追加
- これにより「うっかりバージョン無しエンドポイントを生やす」事故を決定的に防ぐ

## 検討した代替案

- **ヘッダ方式（`Accept: application/vnd.api.v1+json`）**: URL が安定する利点があるが、ブラウザから叩きにくく可視性が低いため不採用
- **クエリパラメータ（`?version=1`）**: キャッシュキーが汚れ、省略時の挙動が曖昧になるため不採用

## 関連

- 関連 Issue: #123
- 関連 knowledge: [[api-design-principles]]
```

# ADR-20260520091500: 設計判断は ADR に記録してからコードを書く

## ステータス

accepted（2026-05-20）

## コンテキスト / 背景

「なぜこの設計にしたか」が口頭で消え、後から理由を辿れない問題が頻発していた。

## 決定

アーキテクチャに影響する判断は、実装着手前に ADR を 1 件起こす。

## 影響 (Consequences)

- **良い影響**: WHY が永続化され、後任者が辿れる
- **悪い影響**: 軽微な判断まで ADR を起こすと過剰になる
- **トレードオフ**: 記録コスト vs 後からの追跡可能性。「アーキテクチャに影響する」を閾値にして balance を取る

## 適用方法 (Enforcement)

機械強制できない。
「アーキテクチャに影響するか」の判定は文脈依存で、自然言語理解が必要なため lint / hook では表現できない。
代わりにレビュー時のチェックリスト項目（self-review skill）に「設計判断に ADR があるか」を含め、人手判断で担保する。

## 検討した代替案

- **PR テンプレに ADR リンク欄を必須化**: 強制力はあるが「該当なし」記入で形骸化するため、必須ではなく推奨に留めた

## 関連

- 関連 ADR: [[ADR-20260529143012]]
```

---

## Enforcement 欄の書き方の指針

- **まず「機械強制できるか」を問う**。決定的検証（exit code / 文字列 / スキーマ / ファイル存在）で表現できるなら、その手段を具体的に書く
- **できる場合**: どの lint ルール / どの test / どの hook で、どう検出するかを 1〜2 文で
- **できない場合**: なぜできないか（文脈依存・例外多数・自然言語判断が必要）を明記し、代替の人手担保（レビュー観点など）を添える
- この欄を空にしない。空欄は「死に文書化した ADR」の予兆
