### 7. 読み合わせの締め（最後の精読の後）

**`HIDE_GUIDE=1` の回は、1. より先に** `review-guide-format.md` の「ガイド非表示の締めの前置き」（精読ごとに何をして何で確かめたか・入れた修正の要旨と確かめ方・副作用）を出す。利用者は解説を見ていないので、1. の「まだ答えの無い確認」の各行には根拠 `file:line` と選択肢の要旨（`このまま` を含む）を添え、聞く 1 問には選択肢ごとの帰結を添える（聞かれずに「残った確認」へ回った問いも、中身が利用者に届くように）。1.〜5. の進め方は同じ。

1. **精読の外で気になるところを挙げ、直せるものは直してから、まだ答えの無い確認と並べる**: 流し読み（上限超えの精読候補を含む）・横断で見えた関係・テスト対応表の「なし」・doc や CHANGELOG の追随漏れから、気になる点を自分で挙げる（各 1〜2 行・根拠 `file:line`。無ければ「特になし」）。各点は Step 6 の 4. と同じ線で振り分ける: `FIX_OK=1` で、`WALKTHROUGH=1` か利用者が直すよう言っていて、直し方が 1 つに決まり、この diff の範囲で閉じる修正は**聞く前に直し**、行に「直した」と変更前後の要旨を添える（対応するテストがあれば走らせて結果を、挙動を変える修正には確かめ方と副作用も添える）。直し方が複数ある・仕様の判断が要る・diff の外へ広がる・新しい仕組みが要る・`FIX_OK=0`・直すよう言われていない（`WALKTHROUGH=0`）の点は直さず、行に「対応を聞く」と付ける。あわせて、控えに残っている**持ち越した確認**と**未確認の点**（解説に書いた「要確認」を含む）を各 1 行で一覧にする（選択肢や理由は解説に書いたので繰り返さない。`HIDE_GUIDE=1` の回は上の段落のとおり添える）。そのうえで**1 問だけ**聞く（1 回に 1 問。まとめて聞かない）: 持ち越した確認があれば、答えで直すかどうかが変わり影響が大きいものを 1 つ（選択肢は解説に書いたもの）、無ければ「対応を聞く」の点のうち影響が大きいものを 1 つ、対応するかを聞く（選択肢は `直す`（直し方の要旨。直し方が複数あれば案ごとに分ける）/ `別チケット候補にする` / `このまま`。`このまま` は外さない。`FIX_OK=0` の点は手元で直せないので `直す` を出さず、`別チケット候補にする` / `このまま` にする）。聞くのは `AskUserQuestion`（選択肢ごとの帰結を description に書く）で、選択肢は 4 個まで（ツールの上限）— 直し方の案や持ち越した確認の選択肢が収まらなければ、案を 2 つまでに絞って残りを description に並べ（利用者は自由記述で選べる）、`このまま` は必ず残す。使えない環境では通常のメッセージで選択肢を並べてターンを終える。無操作の自動続行（`askUserQuestionTimeout`）の回答は利用者が選んだものとみなさず、直さずに「残った確認」へ回す。返信の扱いは Step 6 と同じ（`別チケット候補にする` は 5. の「別チケット候補」に積む）で、返信ごとに次の 1 問へ進む。持ち越した確認も「対応を聞く」の点も無い回は、`AskUserQuestion` を使わず「ほかに精読の外で気になるところがあれば書いてください」と通常のメッセージで聞いてターンを終える。聞くものが尽きるか利用者が「締めて」と返したら 2. へ。切り上げで来た回は、直せるものを直したうえで一覧だけ出し、聞かずに 2. へ。答えが返らなかった確認と、聞かずに終えたか答えが返らなかった「対応を聞く」の点は、5. の締めの「残った確認」に残す（黙って消さない）
2. **self-review 以降の変更を確かめる**（base モードのみ。PR モードは「不明（PR モード）」）。diff を今の作業ツリーで取り直し、直近のレビューの記録と突き合わせる:

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/triage-signals.sh" --base "<base_branch>" > /dev/null
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/detect-recent-review.sh"
   ```

   出力の明細のうち**最も新しい `code-review:self-review` の行**で決める: `[完全一致]` → `なし` / `[ファイル集合のみ]` → `あり` / self-review の行が無い（出力が空を含む）→ `不明（直近の self-review の記録と突き合わせられなかった）`。`不明` には、記録が 24 時間より古い・明細の 5 件から外れた、のほか、self-review の後に変更ファイルの集合が変わった回（ファイルを足した・集合の外を触った）も入る — どちらのキーも一致しないため。呼び出し元は読み合わせで修正を入れたかで決める。diff は 3 本（コミット済み・staged・unstaged）を連結したバイト列で比べるので、中身が同じでも self-review の後の commit や `git add` でファイルの並びが変わると `あり` になる。2 回目の self-review を勧める側に倒れるので、そのまま出す
3. **次の一手を決める**（GitHub issue #304）: `review-guide-format.md` の「回し直すかの判断」で、2. の値と self-review 以降の変更の中身から決める。`あり` を `self-review をもう一度` に直結させない — 変更をすべて挙げられ、どれも解説で確かめ（`HIDE_GUIDE=1` の回は締めの前置きに変更前後を出したもの）、実行時の挙動を変えないなら `決定的な検証` にする。どの条件で決めたかを理由に書く
4. **変異テストを提案するかを決める**（GitHub issue #307）: `review-guide-format.md` の「変異テストの提案」で、まず要るか（core の変更がソースの言語の式・文として分岐・境界・検証ロジックを触ったか（SQL・設定値などの文字列の中にだけある分岐は数えない。正規表現のリテラルと宣言のある回は例外 / GitHub issue #505）、その振る舞いがテスト対応表で「あり」か）を決め、要るときだけ `bash "${CLAUDE_PLUGIN_ROOT}/scripts/detect-mutation-tool.sh"` で道具を探す。値と理由を `変異テスト:` の行に書き、`提案する` には回し方と所要の目安を添える。**この skill からは回さない** — 変異 1 個ごとにテストを 1 回回すので長い（道具によっては、変異体を作業ツリーのファイルへ直接書き込みながら回る）。回すかは呼び出し元か利用者が決める
5. **締めを出す**: `review-guide-format.md` の「読み合わせの締め」の形式で、入れた修正の一覧・残った確認・持ち越した前提・別チケット候補と、**`self-review 以降の変更:` と `次の一手:` の 2 行**を出す。この 2 行は呼び出し元（issue-workflow の軽量フロー・feature-dev の Phase 7・dev-workflow の git-commit-helper の 1.5）が 2 回目の self-review を回すかの判断に使う契約なので、値と `次の一手:` の先頭の文言を変えない。あわせて `変異テスト:` の行を `self-review 以降の変更:` の前に出す。呼び出し元が変異テストを提案するかに使う契約なので、先頭の `提案する` / `不要` / `道具なし` を言い換えない

**完了基準**: `HIDE_GUIDE=1` の回は締めの前置きを出した。精読の外の点のうち 1. の「聞く前に直す」条件（`FIX_OK=1`・`WALKTHROUGH=1` か利用者の指示・直し方が 1 つ・diff の範囲）に当たるものは、聞く前に直してある。精読の外の点と、まだ答えの無い確認（持ち越した確認・未確認の点）を一覧にし、1 問ずつ聞いた（切り上げの回は一覧だけ）。精読の外の点の対応可否には `このまま` を含む選択肢がある。答えが返らなかった確認は「残った確認」にある。`変異テスト:` が `提案する` / `不要` / `道具なし` のどれかで始まり、理由が付いている（`提案する` には回し方と所要の目安がある）。`self-review 以降の変更:` が `あり` / `なし` / `不明（理由）` のどれかで出ている。`次の一手:` が `self-review をもう一度` / `決定的な検証` / `コミットへ` のどれかで始まり、理由が付いている。この skill からは self-review も決定的な検証も変異テストも commit も起動していない（次の一手と変異テストを回すかは呼び出し元か利用者が決める）。
