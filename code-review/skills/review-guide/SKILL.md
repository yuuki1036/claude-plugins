# review-guide

PR を**読む人間**を支援する skill。指摘を出す（review / self-review）でも付いた指摘に応える（review-triage）でもなく、**diff のどこをどの順で読めばよいか**を案内する。主用途は自分の PR を後から理解すること、副用途は他者 PR に review を回した後の学習。もう 1 つの用途が**コミット前の読み合わせ**（`--walkthrough`）: self-review の後に精読を 1 件ずつ解説し、利用者が変更を理解しながら、解説の中で見つかった修正をその場で入れる。

正本設計: `.claude/designs/20260916-code-review-review-guide-skill.md`。

## review / self-review / review-triage との違い

- review / self-review は severity 付き findings を**出す**。本 skill は findings を出さない。「レビュー観点」は「このファイルで何を見るか」の問いであって判定ではない。読み合わせ（Step 6）では、その問いに自分で答えた結果を解説に添える（判定の一覧は作らない）
- 出力は**セッション内のみ**。ファイルを書かない・コメントを投稿しない。コードを直すのは読み合わせの中だけ（Step 6・7。条件は絶対厳守ルール）。他の書き込みは base モードの読み順の記録 1 件だけ（Step 5）
- 全ファイルは解説しない。精読は**精読に値するものだけを 1〜5 件**選び（`--top N` で上限を下げられる）、数合わせで埋めない。残りは 1 行で流し読み / 不要に振る

## 絶対厳守ルール

- **書き込みは 2 つに限る**。ファイル作成・コメント投稿・push・commit・Issue 起票は一切しない。許される書き込みは次の 2 つだけ:
  1. base モードの Step 5 で `guide-order.sh` が git dir（作業ツリーの外。diff にも status にも出ない）に書く読み順の記録 1 件。`/guide-diff`（code-review の mod）の入力になる。毎回上書きし、mods が無い環境では読まれないだけ
  2. 読み合わせ（Step 6・7）で入れるコードの修正。`--walkthrough` で起動した回か、利用者が解説の途中で直すよう言った回に限り、**対象が今チェックアウトしている作業ツリーの変更のとき**だけ Edit で直す（Step 0 の `FIX_OK`）。直してよい範囲と、直さずに聞くものの線引きは Step 6
- **各主張に `file:line` を添える**。「この PR で何をした」「難点」「主張 vs diff」に書く事実は、確認した `file:line` を根拠にする。確かめられないことは書かない（「難点: 特になし」を許す）。記録・コミットメッセージ・PR 本文の主張をそのまま採用せず、diff とコードで確かめる。例外は同じセッションでユーザーが伝えた前提・決定で、根拠を「セッション中の決定」と書く（Step 1.5）。コードの事実の根拠をこれで置き換えない
- **精読を数合わせで埋めない**。上限（既定 5）は読み手の負担の上限であって目標ではない。精読に値するものが 2 件なら 2 件で出す（Step 2）
- **精読の上限で切っても core を落とさない**。上限で core は流し読みに落ちても「不要」には落とさない

## コスト×精度パイプライン設計（採用/不採用）

ルート CLAUDE.md の 10 原則のうち **採用: 1（ファネル = triage-signals の分類で精読を 1〜5 件に絞ってから agent を当てる）/ 3（段階予算 = `${CLAUDE_EFFORT}` で explorer 0/2/3 体）/ 4（モデルルーティング = explorer は `sonnet`・統合は `opus`＝メインコンテキスト）/ 5（暴走ガード = explorer 体数上限・精読の上限 5）/ 9（構造化受け渡し = diff はパス渡し、explorer は事実のみ返す）**。**捨てた**: 2・10（severity / confidence を付けない。判定ではなく説明）/ 6（蓄積しない。永続化なし）/ 7（反証レイヤーなし。説明文の根拠を `file:line` で強制し、無い主張は書かない。読み合わせで入れた修正は利用者が解説と並べて確かめ、Step 7 の判断で 2 回目の self-review か決定的な検証に回す）/ 8（静的な読解に機械判定オラクルが無い。読み合わせの締めで変異テストを提案するが、提案だけで回すのは呼び出し元なので捨てたまま）。

## 実行手順

### 0. 入力確定と diff 収集

引数を解析する。**`--base <ref>` の値を `BASE_REF`、`--top N` の値を精読の上限 N（省略時 5）、`--walkthrough` の有無を `WALKTHROUGH`、残りの非オプション引数（PR 番号）を `PR_ARG` に入れる**。`--base` があれば base モード、無ければ PR モードに入る。N は 1〜5 に収める（範囲の外なら近い方の端に寄せ、数でなければ 5 に戻す。寄せたときはレポート冒頭に 1 行で書く）。

```bash
# PR モード（既定）: PR_ARG（省略時は現ブランチの PR）を解決する。--base 指定時は PR モードに入らない
if [ -z "$BASE_REF" ]; then
  META=$(gh pr view ${PR_ARG:+"$PR_ARG"} --json number,title,url,headRefName,headRefOid,baseRefName,body 2>/dev/null) \
    && PR_NUMBER=$(printf '%s' "$META" | jq -r '.number') || PR_NUMBER=""
fi
# base モード（--base 指定 / PR が特定できない）: base branch を決め、origin から取り直す。
# 決め方は 引数 → このブランチを作ったときの reflog（統合ブランチから切ったなら統合ブランチ）→ default branch
# （正本: scripts/lib/base-branch.sh / GitHub issue #274）。ローカルの base は早送りできるときだけ進める
if [ -z "$PR_NUMBER" ]; then
  BASE_OUT=$(bash "${CLAUDE_PLUGIN_ROOT}/scripts/lib/base-branch.sh" --refresh ${BASE_REF:+"$BASE_REF"})
  printf '%s\n' "$BASE_OUT"
  BASE_REF=$(printf '%s\n' "$BASE_OUT" | sed -n 's/^base_branch=//p')
fi
```

- `FATAL:` が出たら（PR も base も決まらない）、base branch を指定して呼び直すよう案内して終了する
- 出力の `base_branch=` / `base_source=`（`arg` 引数指定 / `reflog` このブランチを作った起点 / `default` default branch へのフォールバック）/ `base_refresh=` は Step 5 のレポート冒頭の「base」行と読み順の記録にそのまま使う

- **PR モード**（`PR_NUMBER` あり）: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/triage-signals.sh" --pr "$PR_NUMBER"` で diff 収集とシグナル出力を得る
- **base モード**（`BASE_REF` あり）: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/triage-signals.sh" --base "$BASE_REF"`。この場合 Step 1 の PR コンテキストは無い。`## meta` の `diff_base=`（分岐点のコミット）と、stderr の `WARN: ⚠️ base:` をレポート冒頭の「base」行に使う
- **diff 全文をメインコンテキストに載せない**。`triage-signals.sh` が diff をファイルへ保存し、`## meta` の `diff_file=` にパスが出る。**このパスの実値を控える**（シェル変数は Bash 呼び出し間で消える）

出力の各セクション（`## files` = 分類 + 行数 / `## red-flags` `## surface` = リスク信号 / `## hunks` = core の関数コンテキスト / `## focus-signals` = 観点判定ヒット）を読む。**diff 全文の Read はしない**。

**読み合わせで直してよいか（`FIX_OK`）を決める**。Step 6・7 で修正を入れてよいのは、diff の対象が今の作業ツリーそのものの回だけ:

- base モード → `FIX_OK=1`（diff は分岐点から今の作業ツリーまで）
- PR モード → 今の `HEAD`（`git rev-parse HEAD`）が `META` の `headRefOid` と一致するときだけ `FIX_OK=1`。diff は PR head のものなので、ブランチ名が同じでも手元が head と違えば（別のマシンから push して手元が古い・未 push のコミットがある・fork の同名ブランチ）、解説したコードと Edit する作業ツリーが食い違う。一致しない回は `FIX_OK=0` で修正は提案に留め、理由（HEAD が PR head と違う）をレポート冒頭に 1 行で書く

**完了基準**: `diff_file` の実パス・`size_tier`・見出しに使う `## size` の値（`total_files` / `total_added` / `total_deleted` / `core_files` / `core_lines`）・`## files` の分類済みファイル一覧・PR/base モードの別・`WALKTHROUGH` と `FIX_OK` が確定している。PR モードでは `META` の `baseRefName` と `headRefOid` の実値を控えている（Step 7 の 4. で変異テストの `<ref>` を手元の `HEAD` ではなく PR head から求める。シェル変数は Bash 呼び出し間で消える）。`## size` の `total_files` が 0 なら「変更なし」で終了。

### 1. PR コンテキスト（PR モードのみ）

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/fetch-pr-context.sh" "$PR_NUMBER" --save
```

出力パスの markdown を Read し、**PR 本文（body）**と既存コメント（issue コメント・レビューサマリ・行コメント）を把握する。本文は Step 4 の「主張 vs diff」に、既存コメントは「人間の判断が効く箇所」に使う。

**同一セッションに review レポートがあれば**、その `🔁 報告閾値を割った指摘` を控える（Step 4 で「人間の判断が効く箇所」に載せる）。無ければ何もしない（この取り込みは前提にしない）。

base モードではこの Step を skip し、「主張 vs diff」「人間の判断が効く箇所」を Step 5 で「対象なし（ローカル diff）」と明記する（silent skip しない）。

**完了基準**: PR モードなら本文と既存コメントを読んだ。base モードなら skip を記録した。

### 1.5 セッション中に伝えられた前提・決定（PR / base モード共通 / GitHub issue #291）

この skill を呼ぶ前のやり取りも含め、**同じセッションでユーザーが伝えた内容**を集めて控える。解説を diff とコードの読解だけから作ると、確定済みの論点を未決のように書いたり、仕様どおりの実装を「修正が必要」と読める言い方で書いたりして、ユーザーが同じ前提を説明し直すことになる。集める対象:

- 仕様の背景・将来の拡張予定（「後のフェーズでこの値も取れるようになる」）
- 別のセッション・別の Issue で扱っている範囲（「その件は別セッションで対応中」）
- 他の画面・経路での補正の有無（「別の画面では保存時に直される」）
- 相談して決まったこと（「仕様のセッションに相談して、現状どおりで確定」）

1 件ずつ、要旨・確定か未決か・関係しそうなファイルや論点を控える。会話に無いものを推測で足さない。何も無ければ「なし」と控えて先へ進む。

**完了基準**: セッション中の前提・決定を列挙した（「なし」を含む）。

### 2. 重要度スコアと 3 段振り分け（メインコンテキスト・agent なし）

`## files` の各ファイルに score を付ける（`## files` は 80 件で打ち切られる。超える大規模 PR では `bash "${CLAUDE_PLUGIN_ROOT}/scripts/diff-slice.sh" "<diff_file>" --list` で全件を引いてから振り分ける）:

```
score = 分類（core=3 / test=2 / doc=1 / gen=0）
      + red-flags・surface の代表ファイルに +2
```

`## files` の 1 列目のラベルは core / test / doc / gen の 4 種（lockfile・生成物はすべて `gen` に畳まれる）。

- **red-flags / surface の加点は「代表ファイル」にのみ**。`triage-signals.sh` の digest は 1 signal につき代表 1 ファイル（`<key>\t<hit数>\t<代表根拠ファイル>`）しか出さないため、全該当ファイルへは配れない。代表ファイル以外は分類スコアのみ（設計判断 F2）
- **fan-in（被参照数）や行数帯は初版では使わない**。分類だけで core・test・doc の順が確定し、精読 N の選抜には足りる。独自 Grep で被参照を数えると `triage-signals.sh ## explorer-signals` が持つ誤カウント対策（3 文字未満 basename 除外・`-lwF` 固定文字列 word 一致・自己除外）を捨てて過大カウントする（設計判断 F1）。将来足すときは独自 Grep を新設せず `## explorer-signals` 出力を再利用する

3 段に振り分ける。score は**見る順**で、精読にするかは下の「精読に値するか」で決める（**同点は core 優先**でタイブレークし、core を上位から落とさない）:

- **精読**: score の高い順に見て、**精読に値するものだけ**を取る。上限 N（既定 5）。gen 以外のファイルが 1 件でもあれば、最低 1 件は精読にする
- **流し読み**: 残りの core・test・doc（何が変わったかを 1 行で書けるもの）
- **不要**: gen（生成物・lock）・rename のみ・機械的置換（import 差し替え等）。**各 1 行の理由を付ける**

**精読に値するか**の線は、「流し読みの 1 行では、読み手がこの変更の正しさを判断できない」かどうか:

- **値する**: 分岐・状態・順序・境界値を変えた / 他ファイルとの約束（引数・戻り値・出力の形式・規約の文言）を変えた / スレッドの入口か、流れの向きが変わる箇所
- **値しない**: 呼び出し側の機械的な追従（引数を 1 つ足しただけ等）/ 定型の追記（CHANGELOG・版の更新）/ 実装の精読をなぞるだけのテスト / 変更の主題でない doc
- **red-flags・surface の代表ファイルは候補に留める**（GitHub issue #303）: +2 は見る順を上げるだけで、それだけでは値しない。signal は正規表現なので、文字列リテラルやテストデータの語にも当たる。代表ファイルの hunk（`diff-slice.sh`。パスはシングルクォートで囲む）を見て、signal が指す処理（db-write なら書き込み、money-numeric なら数量・金額の計算や永続化、authz なら認可の判定、red-flags ならその危険な呼び出し）をこの diff が変えているかを確かめ、変えていれば上の「値する」で決める。当たったのが文字列リテラル・テストデータ・story や fixture の値・コメントだけなら流し読みに回し、その行に外した理由を書く（黙って落とさない。書き方は `review-guide-format.md` の流し読み）
- **テストは実装の精読に畳む**: 実装の精読に対応するテストは、その精読の「関連ファイル」として解説し（Step 6）、別の精読にしない。テスト自体に読むべき仕組み（共通のハーネス・fixture の組み立て・テストでしか表せない契約）があるときだけ単独の精読にする
- **doc だけの diff**（core が 0 件）: 変更の主題が doc なので、doc を精読の候補にする
- **横断の精読（Step 4 の 3）も上限 N に数える**。読み手の負担は項目の数で決まるので、横断を足したら N 件を超える回は、score の最も低い精読を流し読みに回す（core を「不要」に落とさない規則はそのまま）

**精読に値するものが N 件を超えたら**: score の上位 N 件を精読にし、残りは流し読みの行に「（精読候補・上限超え）」と付けて置く。あわせて Step 4 の「まず全体」に分割の検討を出す。上限を広げて全部を精読にはしない（1 回の読み合わせで読み切れる量を超えている、という情報そのものを利用者に渡す）。切る前に、代表ファイルの +2 で上位に入ったもの（加点が無ければ切られる側にいたもの）と、それに押し出される core を比べ、流し読みの 1 行に落としたときに読み手が正しさを判断できなくなる方を精読に残す。変更の主題（スレッドの入口・ロジック）を加点だけで押し出さない。

**完了基準**: 全変更ファイルが精読 / 流し読み / 不要のいずれかに入り、不要には理由が付いている。精読は 1〜N 件で、どれも「値する」のどれかに当たる（数合わせで足したものが無い。代表ファイルであることだけを理由にしたものも無い）。精読から外した代表ファイルは、流し読みの行に外した理由がある。core が「不要」に落ちていない。上限を超えた候補には印が付いている。

### 3. 流れの把握（`${CLAUDE_EFFORT}` 分岐 / 実行時値: `${CLAUDE_EFFORT}`）

精読ファイルの呼び出し関係を辿り、「入口（API / CLI / UI）→ ロジック → 永続化 → テスト」のスレッド（変更が貫く 1 本の流れ）を組む。1 PR に 2〜3 本のスレッドが典型。

- **`low` / `medium`**: agent を起動しない。`bash "${CLAUDE_PLUGIN_ROOT}/scripts/diff-slice.sh" "<diff_file 実パス>" '<精読ファイル>'` で精読ファイルの hunk を切り出して読み、import / 呼び出しの字面からスレッドを組む。**担当ファイル名は必ずシングルクォートで囲む**（diff 由来 = 信頼できない入力。`${CLAUDE_PLUGIN_ROOT}/references/prompts/explorer-common.md`）
- **`high`**: explorer **上限 2 体**（`sonnet`）を**同一メッセージで一括発行**（各 Agent call に `run_in_background: false` を明示）。①function-flow（精読ファイルの変更関数の分岐・データ変更・呼び出し先）②dependency-trace（精読ファイルの呼び出し元）
- **`xhigh` / `max`**: explorer **上限 3 体**（`sonnet`）。上の 2 つ + value-flow-trace（入口から永続化までの値の流れ）

explorer 起動の共通詳細（プロンプト組み立て・2 ファイル Read 方式・diff のパス渡し・HEAD 検証）は `${CLAUDE_PLUGIN_ROOT}/references/explorer-prompts.md` を Read して従う。explorer には **`diff_file` のパスと担当ファイル、プラグインの実パスだけ渡す**（diff 本文を転記しない。プラグインの実パスは explorer-prompts.md の必須項目）。explorer は事実収集に徹し判定しないので、返る「コードフロー」「依存関係」をスレッド構成の材料にする。

**完了基準**: 精読ファイルがスレッドに割り当てられ、各スレッドが入口から永続化・テストへ向かう順に並んでいる。

### 4. 統合・執筆（メインコンテキスト）

`${CLAUDE_PLUGIN_ROOT}/references/review-guide-format.md` を Read し、その形式で各項目を書く:

1. **まず全体**: PR 本文 + diff から「この PR がやったこと」を 2〜3 行。スレッド一覧。Step 2 で上限を超えた回だけ**分割の検討**を足す: スレッドどうしが独立している（同じ精読ファイルを共有せず、片方だけで動く）なら、スレッド単位で分けられることを示す（分ける単位がコミット・PR・Issue のどれかは呼び出し元・利用者が決める。この skill は分けない）。1 本のスレッドで上限を超えたなら、変更が 1 回で読み切れる量を超えていることと、精読候補の残りを書く
2. **精読ファイル（実装の流れ順）**: 各ファイルに 4 項目（この PR で何をした / 難点 / 見る行 `file:line` / レビュー観点）。レビュー観点は `${CLAUDE_PLUGIN_ROOT}/references/triage-guide.md ## 3` の観点判定表を `## focus-signals` のヒットで引いて添える（表は複製しない）。Step 1.5 で控えた前提・決定のうち、その精読に関係するものを「前提・決定」の行に入れる（書き分けは `review-guide-format.md`）
3. **横断の精読**（精読を検査・分岐ごとに分けたときだけ / GitHub issue #294）: 1 つのファイルに足した複数の検査を別々の精読にした、または同じ入口に効く検査が複数の精読に分かれたときは、それらの後に「横断」の精読を 1 項目足す。各精読はその検査単体の妥当性しか見ないので、検査どうしの関係（評価順・同時に成り立つときにどれが返るか・共有する前提）がどの精読にも入らない。横断の精読も上限 N に数える（Step 2）
4. **主張 vs diff**（PR モードのみ）: 本文の主張が diff にあるか / diff にあるが本文に無いか
5. **テスト対応**: 変更した振る舞いごとに対応するテストの有無と場所
6. **人間の判断が効く箇所**: 既存の行コメント（PR モード。`fetch-pr-context.sh` は解決状態を取得しないので「未解決」と断定せず、返信チェーンで著者が閉じていないものを緩く拾い「解決状態は不明」と留保する）と、同一セッションの review レポートの `🔁` 付録（あれば）

**各主張の根拠 `file:line` を必須にする**（絶対厳守ルール）。確かめられない主張は書かない。

**セッション中の前提・決定を黙って上書きしない**: 確定済みの論点は「確定（根拠: セッション中の決定 / 仕様の該当節 `path:line`）」と書き、未決の論点と混ぜない。仕様どおりと確定した箇所を「難点」に書くときは「仕様どおり（確定）」と明記し、修正が要ると読める言い方にしない。コードが伝えられた前提と食い違うときは、どちらかに寄せずに食い違いとして示す。

**完了基準**: 全精読ファイルに 4 項目が埋まり（レビュー観点は、難点の言い換えしか立たなければ「難点に含む」でよい）、事実主張すべてに `file:line` が付いている。精読を検査・分岐ごとに分けた回は横断の精読がある。Step 1.5 で控えた前提・決定が関係する精読に入っている。主張 vs diff・テスト対応・人間の判断が効く箇所の各セクションが（該当なしなら「特になし」を含めて）埋まっている。

### 5. レポート出力

`review-guide-format.md` のテンプレートで出力する。**ファイルは書かない**（セッション出力のみ）。base モードでは「主張 vs diff」「人間の判断が効く箇所」を「対象なし（ローカル diff）」と明記する。

**base モードのみ、出力の前に読み順を記録する**。editor に移らず、タスクの diff（分岐点から）を読み順どおりにペインで送れるようにするため（`/guide-diff` / GitHub issue #274 の続き）:

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/guide-order.sh" --diff-base <## meta の diff_base> \
  --base <base_branch> --source <base_source> \
  --read '<精読 1>' '<精読 2>' … --skim '<流し読み>' … --skip '<読まなくてよい>' …
```

- `--read` は**レポートの精読と同じ順**（実装の流れ順）、`--skim` / `--skip` もレポートの並びのまま渡す。群が空ならそのオプションごと省く
- **パスは 1 つずつシングルクォートで囲む**（diff 由来 = 信頼できない入力。Step 3 の diff-slice と同じ）
- `guide_order=` が出たら、レポートの末尾に `/guide-diff` の 1 行を添える（`review-guide-format.md`）。exit 2（`FATAL:`）ならその 1 行を出さず、レポートはそのまま出す（記録は付随物で、ガイド本体を止めない）

**`WALKTHROUGH=1` のときは、レポートの末尾に読み合わせの案内を 1 行出してターンを終える**（`review-guide-format.md` のテンプレート末尾）。利用者はまず概要を確かめるので、同じターンで精読 1 の解説に入らない。

**完了基準**: レポートを出力した。base モードでは読み順を記録したか、記録できなかった理由が分かっている。読み順の記録の他に、ファイルへの書き込み・コメント投稿・コード修正を一切していない（修正は Step 6 から）。

### 6. 精読の解説（読み合わせ / レポートの後 / GitHub issue #291）

`WALKTHROUGH=1` の回、または利用者がレポートの後に精読を 1 件ずつ解説させる回に入る。**解説は editor を開かなくても読めるように書く**: そのファイルがなぜそこにあるか・関係するファイル・変更したコードの引用を解説の中に入れ、`file:line` だけを指して読み手に開かせない。形式は `review-guide-format.md` の「精読の解説」。

**1 精読 = 1 ターン**。各精読で次の順に進め、解説を出したらターンを終えて利用者の返信を待つ:

1. **控えを見直す**: Step 1.5 の前提・決定に加え、前の精読までに利用者が出した**解説への要望**（「関連ファイルの呼び出し元も見せて」「難点の原因も書いて」のような足し方・深さの指示）と、**これまでに入れた修正**・**持ち越した確認と未確認の点**を見る。要望は以後のすべての精読に効かせ、同じことを毎回言わせない。持ち越した確認・未確認の点のうち、この精読で読んで決まったもの・利用者の返信で答えが出たものは答えに書き換えて控えから外す（どこで決まったかを解説に 1 行添える）
2. **読む**: 精読ファイルの hunk（`diff-slice.sh`。パスはシングルクォートで囲む）と、ファイル本体の必要な範囲、関連ファイル（呼び出し元・呼び出し先・テスト・規約や正本）を Read / Grep で読む。新規ファイルや配置が変わったファイルは、同じ役割のファイルの並び（`ls`）と規約の該当箇所も読む
3. **レビュー観点に答える**: レポートに書いた問いと、読む中で出てきた問いに、コードを読んで答える。答えは「問題なし」「直した」「直すべき（未修正）」「判断が要る」「未確認」のどれかで、問いを並べるだけで利用者に答えさせない。書き方は `review-guide-format.md` の「レビュー観点（確かめた結果）」:
   - **「判断が要る」と「未確認」の線**: 答えしだいでコードを変えるか変えないかが分かれる問いは、仕様が未決でも「判断が要る」にする。選択肢には **`このまま`（変えない）を必ず含め**、変える案に傾いていても外さない — 外すと、正しいコードに手を入れる前提で利用者に選ばせることになる。`このまま` の帰結は利点と欠点の両方を書く。「未確認」は、答えが分かっても直すかどうかに直結しない事実のうち、このリポジトリと手元で走らせられるものからは決まらないもの（リポジトリの外の呼び出し元が渡す値・実行環境や DB の種類・運用のデータ・作者の意図）に使い、何が分かれば・どこを見れば / 誰に聞けば決まるかを書く。未確認にする前に、手元で決められるか（リポジトリ内の呼び出し元の grep・関連テスト）を試す。決まらない問いを「問題なし」で閉じず、読めば決まる問いを未確認に逃がさない。絶対厳守ルールの「確かめられないことは書かない」は事実の主張についての規則で、確かめられなかったことを未確認と書くのはこれに当たらない
   - **何で確かめたかを書く**: 精読ごとに 1 回、走らせたコマンドと結果を書く。何も走らせていなければ「読解のみ」と、走らせなかった理由を事実で書く（走らせられるのに走らせなかったなら「走らせていない」とだけ書き、走らせられないとは書かない）。答えの行ごとには繰り返さず、走らせた答えと読解だけの答えが混ざるときだけ、読解だけの行に「読解のみ」と付ける
   - **難点の言い換えだけの問いは答えの対象から外す**: 答えが難点か問いの括弧書きにもう書いてある問い（難点の結論を問いの形にしただけのもの）。確かめても新しいことが分からない。レポートに載ったものは、解説で「言い換え（答えは難点）」と 1 行示し、その先の問い（同じ原因の別の経路はあるか・テストは変更の前後を区別できるか）に置き換える。その先の問いが立たなければ置き換えない。「問いすべてに答えがある」の対象にも入れない
4. **直すべきものを扱う**:
   - **直してから解説する**: `FIX_OK=1` で、`WALKTHROUGH=1` か利用者が直すよう言っていて、直し方が 1 つに決まり（仕様・設計の判断が要らない）、この diff の範囲で閉じる修正。直したら解説の「修正」に変更前後を引用し、その箇所に対応するテストがあれば走らせて結果を添える（走らせていなければ「未実行」）。**挙動を変える修正**（本命。1 精読に複数あればそれぞれ。利用者の指示や締めで入れたものも同じ）**には、確かめ方と副作用も添える**: 確かめ方は、利用者が直ったことを観測できる手順（直る前に失敗した入力と、直った後に期待する結果・ログ・戻り値。テストがあれば、そのテストが直す前後を区別できるか — 走らせて確かめていなければ「読解のみ」と書く）。副作用は、この修正で他に振る舞いが変わる経路（無ければ「無い」と、そう言える根拠）
   - **直さずに聞く**: 直し方が複数ある / 仕様の判断が要る / diff の外へ広がる / 新しい仕組みが要る（別チケット候補）/ `FIX_OK=0`。解説の最後に**1 問だけ**聞く（複数あれば、答えで直すかどうかが変わり、影響が大きいものから）。残りと、聞いたのに答えが返らなかった問いは、**持ち越した確認**として控えに積み、締めで聞く（利用者が「次」と返しても捨てない）
   - 前提・決定（控え）と食い違う直し方はしない。食い違いとして示して聞く
5. **解説を書く**: `review-guide-format.md` の「精読の解説」の形式。末尾に次の精読の名前と「次」で進めることを添える

**利用者の返信の扱い**: 質問 → 答える（答える中で直すべきものが出たら 4. と同じ扱い）/ 直す指示 → 直して結果を示す（挙動を変える修正なら確かめ方と副作用も）/ 確認への答え → 答えに書き換えて控えから外す。選んだ選択肢が `このまま` 以外で、`FIX_OK=1` かつ直し方が 1 つに決まるなら直す指示として扱い、決まらなければ 1 問で聞く / 前提の補足 → 控えに足して以後に持ち越す（補足で確定した論点を後の精読で未決のように書かない。後の精読のコードが補足と食い違うときは食い違いとして示す）/ 「次」→ 次の精読へ / 切り上げ（残りの精読を飛ばして終えたい）→ 残りの精読名を締めに並べて Step 7 へ。最後の精読の後も Step 7 へ。**どの終わり方でも Step 7 の締め（`self-review 以降の変更:` の行）を出す** — 締めを出さずに終えると、呼び出し元は読み合わせで入れた修正を 2 回目の self-review に回せない。

解説でもコードの事実には `file:line` を添える（絶対厳守ルール）。修正は絶対厳守ルールの 2. の範囲だけで、ファイルの新規作成・commit はしない。

**完了基準**（各精読）: 控えの要望が解説に効いている。レビュー観点の問いすべてに答えがある（言い換えとして外した問いを除く）。「判断が要る」には `このまま` があり、未確認には何が分かれば・どこを見れば決まるかがある。何で確かめたか（走らせたコマンド、または読解のみとその理由）が書いてある。直したものは変更前後の引用付きで、挙動を変える修正には確かめ方と副作用がある。聞くものは 1 問に絞られ、残りは持ち越した確認に積んである。

### 7. 読み合わせの締め（最後の精読の後）

1. **精読の外で気になるところと、まだ答えの無い確認を並べる**: 流し読み（上限超えの精読候補を含む）・横断で見えた関係・テスト対応表の「なし」・doc や CHANGELOG の追随漏れから、気になる点を自分で挙げる（各 1〜2 行・根拠 `file:line`。無ければ「特になし」）。あわせて、控えに残っている**持ち越した確認**と**未確認の点**（解説に書いた「要確認」を含む）を各 1 行で一覧にする（選択肢や理由は解説に書いたので繰り返さない）。そのうえで**1 問だけ**聞いてターンを終える: 持ち越した確認があれば、答えで直すかどうかが変わり影響が大きいものを 1 つ（選択肢はここで書く）、無ければ精読の外で気になるところ。返信の扱いは Step 6 と同じで、返信ごとに次の 1 問へ進み、聞くものが尽きるか利用者が「締めて」と返したら 2. へ。切り上げで来た回は、一覧だけ出して聞かずに 2. へ。答えが返らなかった確認は、5. の締めの「残った確認」に残す（黙って消さない）
2. **self-review 以降の変更を確かめる**（base モードのみ。PR モードは「不明（PR モード）」）。diff を今の作業ツリーで取り直し、直近のレビューの記録と突き合わせる:

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/triage-signals.sh" --base "<base_branch>" > /dev/null
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/detect-recent-review.sh"
   ```

   出力の明細のうち**最も新しい `code-review:self-review` の行**で決める: `[完全一致]` → `なし` / `[ファイル集合のみ]` → `あり` / self-review の行が無い（出力が空を含む）→ `不明（直近の self-review の記録と突き合わせられなかった）`。`不明` には、記録が 24 時間より古い・明細の 5 件から外れた、のほか、self-review の後に変更ファイルの集合が変わった回（ファイルを足した・集合の外を触った）も入る — どちらのキーも一致しないため。呼び出し元は読み合わせで修正を入れたかで決める。diff は 3 本（コミット済み・staged・unstaged）を連結したバイト列で比べるので、中身が同じでも self-review の後の commit や `git add` でファイルの並びが変わると `あり` になる。2 回目の self-review を勧める側に倒れるので、そのまま出す
3. **次の一手を決める**（GitHub issue #304）: `review-guide-format.md` の「回し直すかの判断」で、2. の値と self-review 以降の変更の中身から決める。`あり` を `self-review をもう一度` に直結させない — 変更をすべて挙げられ、どれも解説で確かめ、実行時の挙動を変えないなら `決定的な検証` にする。どの条件で決めたかを理由に書く
4. **変異テストを提案するかを決める**（GitHub issue #307）: `review-guide-format.md` の「変異テストの提案」で、まず要るか（core の変更が分岐・境界・検証ロジックを触ったか、その振る舞いがテスト対応表で「あり」か）を決め、要るときだけ `bash "${CLAUDE_PLUGIN_ROOT}/scripts/detect-mutation-tool.sh"` で道具を探す。値と理由を `変異テスト:` の行に書き、`提案する` には回し方と所要の目安を添える。**この skill からは回さない** — 変異 1 個ごとにテストを 1 回回すので長い（道具によっては、変異体を作業ツリーのファイルへ直接書き込みながら回る）。回すかは呼び出し元か利用者が決める
5. **締めを出す**: `review-guide-format.md` の「読み合わせの締め」の形式で、入れた修正の一覧・残った確認・持ち越した前提・別チケット候補と、**`self-review 以降の変更:` と `次の一手:` の 2 行**を出す。この 2 行は呼び出し元（issue-workflow の軽量フロー・feature-dev の Phase 7）が 2 回目の self-review を回すかの判断に使う契約なので、値と `次の一手:` の先頭の文言を変えない。あわせて `変異テスト:` の行を `self-review 以降の変更:` の前に出す。呼び出し元が変異テストを提案するかに使う契約なので、先頭の `提案する` / `不要` / `道具なし` を言い換えない

**完了基準**: 精読の外の点と、まだ答えの無い確認（持ち越した確認・未確認の点）を一覧にし、1 問ずつ聞いた（切り上げの回は一覧だけ）。答えが返らなかった確認は「残った確認」にある。`変異テスト:` が `提案する` / `不要` / `道具なし` のどれかで始まり、理由が付いている（`提案する` には回し方と所要の目安がある）。`self-review 以降の変更:` が `あり` / `なし` / `不明（理由）` のどれかで出ている。`次の一手:` が `self-review をもう一度` / `決定的な検証` / `コミットへ` のどれかで始まり、理由が付いている。この skill からは self-review も決定的な検証も変異テストも commit も起動していない（次の一手と変異テストを回すかは呼び出し元か利用者が決める）。
