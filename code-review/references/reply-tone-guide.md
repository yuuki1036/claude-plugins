# 返答トーンガイド

PR レビュー後の **コメント返答ドラフト** を生成する際のルール集。`review` skill の Step 7 から参照される。
返答対象は主に 3 種類:

1. **自分が受けた指摘への返答**（著者として、対応・釈明・据置判断）
2. **自分が発信した指摘の追補・確認**（レビュアーとして、対応コミットへの返信）
3. **承認メッセージ**（総合判定が Approve / Approve with nits のとき → 2.7）

ガイドの目的は「**トーンの一貫性確保** と **判断軸の明示**」であり、機械的な文面生成ではない。生成後は必ずユーザー確認を経る。

## 0. 必須ルール（投稿コメント全般 = 返答 + 承認）

このガイドが扱う「返答ドラフト」「承認メッセージ」の**すべて**に適用される最上位ルール。1〜5 章の個別パターンより優先する。

### 0.1 Claude の署名を付ける

- **Claude が作成したコメント（ドラフト含む）には、末尾に署名を 1 行付ける**。誰が読んでも「自動生成由来の文面」と分かるようにするため。
- 署名形式（**絵文字なし**・1.1 の規約に準拠。標準の `🤖 Generated with Claude Code` は使わない）:

  ```
  — Created by Claude
  ```

  この 1 行を**署名の正本**とし、**voice（レビュアー発信 / 著者発信）を問わず全文面の末尾で使い回す**（文面ごとに言い回しを変えない）。
- **「レビュー」と書かない**のが要点（v2.42.0 で旧署名「— Claude Code によるレビュー」から変更。GitHub issue #97）。このガイドが扱う文面の主対象は**レビューではなくレビューへの返答**（著者として対応・釈明・据置を返す文面）であり、「対応しました」の末尾に「レビュー」が付くと**誰が何をした文面なのか伝わらない**（実例: 著者としてレビューコメント 11 件に返答した際、全件で実態と署名が食い違った）。voice で署名を分ける案も検討したが、**分岐を増やすより中立な 1 本に寄せる**方を採った（レビュアー発信でも「レビューによる」と名乗る必要はない。voice はメタ行 0.5 か本文冒頭が示す — メタ行が付かない 2.7 承認・2.6 全面解決も本文自体が voice を明示している）。
- **リポジトリ側の規約が署名文言を定めている場合はそちらを優先する**。`CLAUDE.md` / `CONTRIBUTING.md`（ルート・`.github/` のどちらでも）に「PR レビューコメントには〈文言〉を必ず含める」のような規定があれば、リポジトリ規約が勝つ。**根拠は Step 2 のコンテキスト収集で実際に読んだ規約ファイルに限る**（読んでいないファイルを推測で根拠にしない。PR テンプレートは Step 2 の収集対象外なので、必要なら収集リスト側に追加する）。
- **条件**: Claude が文面を生成・投稿する場合、または Claude のドラフトをほぼそのまま投稿する場合は署名必須。**人間が文面を大幅に書き換えた場合は不要**（その文面はもう人間の発言なので）。迷う場合は付ける。

### 0.2 PR 作成者・他レビュアーへの敬意

- **PR 作成者・他コメント者には敬称を添える**（文中で言及するなら「さん」付けを基本とする。GitHub の `@user` 補完に任せる場合も同様の姿勢で書く）。
- **他レビュアーの指摘を否定しない**。重複・異論があっても「{別の観点} もあるかもしれません」「{論点} は別途整理させてください」と議論を立てる方向で書く（→ 1.3 禁則・2.5 と整合）。
- 自分の指摘が他レビュアーと食い違う場合も、相手の指摘を消さず「{相手の指摘} を踏まえつつ」と接続する。

### 0.3 人間にわかりやすく、簡潔に

- **要点を先頭に**置く（結論 → 理由の順）。
- **1 コメントは短く**。1 つの指摘・1 つの論点に絞る（複数論点は inline スレッドを分ける → 4 章）。
- **専門用語は噛み砕く**。略語・内部用語をそのまま投げない（例: 「N+1」→「ループ内で毎回クエリが飛ぶ状態」と一言補う）。

### 0.4 良い点には触れない

- **投稿する文面（返答・承認メッセージのいずれも）で良い点を述べない**。1 文でも文面が伸び、著者が読む量が増えるため。
- **著者への配慮は称賛ではなく 0.2（敬意）・0.6（配慮チェックリスト）で担保する**。褒め言葉を落としても配慮は落とさない。
- レビューレポート本体の「良かった点」セクション（SKILL.md）は**チャット出力なので対象外**。ただし**投稿文面には転記しない**。

### 0.5 レビュアー発信の文面には重大度・確信度・ブロッカー可否を明記する

著者が**対応の優先度を判断するための一次情報**。レビューレポート本体にしかなくても著者には届かないので、投稿する文面自体に書く。

判定はパターン番号ではなく**文面の声（voice = 誰の発言か）**で行う。同じ 2.5 でも voice は分かれる（`[re-flag]` の再指摘はレビュアー発信、他者の指摘への反証は著者発信）ため、パターン番号だけでは決まらない。

**voice の決め方（指摘の出所で決める）**:

- **レビュアー発信** = こちらのレビューレポート由来の指摘を著者に伝える文面（2.6、`[re-flag]` 経由の 2.5）→ **メタ行あり**
- **著者発信** = PR の他者 review comment に著者として返す文面（2.1〜2.5 の本来の用法）→ **メタ行なし**（相手の指摘を自分がスコアリングして返す形になり 0.2 の敬意と衝突する）

**対象外**: 上記の著者発信すべて / 2.7 承認メッセージ（Approve 確定でブロッカーが存在しない）/ 5 章の例外（typo・lint・誤指摘・緊急対応への**返信**はいずれも著者視点）/ 2.6 のうち残存指摘のない全面解決の確認文（埋める確定値が存在しない → 2.6）。
- **書式**: 本文の冒頭に 1 行置く（結論 → 理由の順。0.3 と整合）。値はレポートの `[severity: ...]` / `[confidence: ...]` の確定値をそのまま引き継ぐ（ラベルのみ日本語化する ← 0.3「専門用語は噛み砕く」）。精査（締めフロー 1）で降格した指摘は**降格後**の値を使う。

  ```
  **重大度: CRITICAL / 確信度: 90 / マージブロッカー: はい**
  ```

- **マージブロッカー可否は severity から決定的に導く**（scoring-guide.md「レビュー結論（総合判定）」と同じ導出。文面ごとに判断しない）:

  | severity | マージブロッカー | 意味 |
  |---|---|---|
  | BLOCKER / CRITICAL | はい | マージ前の対応が必要 |
  | MAJOR | いいえ | 対応推奨（追跡 Issue / TODO を添えて可） |
  | MINOR | いいえ | 対応は任意 |

- **確信度が低い指摘・係争中の指摘はその旨も書く**: confidence 80 未満、または反証メモ（`⚠️ 反証メモ`）が付いた指摘は、メタ行に続けて未確定である事実を 1 文添える（例: 「確信度が低い指摘なので、意図的な実装であればその旨を教えてください」）。数値だけ出して断定で押し切らない（1.1 判断委譲・SKILL.md の断定抑止と整合）。

### 0.6 著者への配慮（ドラフト提示前のチェックリスト）

方針そのものは 0.2・1.1・1.3 に既出。ここでは**ドラフトを提示する前に必ず自己点検する項目**として列挙する。1 つでも欠けたら直してから提示する（review skill 締めフロー 3 から必ず適用される）。

**適用範囲**: 0.5 と同じ。**2.7 承認メッセージ**（謝辞・締めの一文を持たない構成が正）と **5 章の例外**（typo・lint・誤指摘・緊急対応への返信。簡潔さが正で、緊急時は「感謝表現を最小化」が明示されている）には**本チェックリストを適用しない** — 0 章は「1〜5 章より優先する」（→ 0.1 前文）ため、範囲を書かないと 5 章の特則を無効化してしまう。両ケースで必須なのは**署名（0.1）のみ**。

- [ ] 冒頭に**謝辞**がある（時間を割いてもらった事実に対して → 1.1）
- [ ] 著者・他レビュアーに**敬称**を添えている（→ 0.2）
- [ ] **議論を閉じていない**（断定しない → 1.1 / 1.3）。ただし**結論が出ている報告（2.1 完全対応 / 2.2 部分対応 / 2.3 据置）には締めの一文を付けていない**（確認依頼も「誤りがあれば指摘」も置かない → 1.1）
- [ ] 著者が**既に対応した箇所に言及**している（レビュアー発信の文面で、対応の事実に触れず再度指摘していない → 2.6）
- [ ] 指摘が**人でなくコードに向いている**（責任転嫁・皮肉・盲従表現がない → 1.3）
- [ ] **署名**が末尾にある（`— Created by Claude`。リポジトリ規約があればその文言 → 0.1）

## 1. 基本トーン

### 1.1 共通原則

- **丁寧体（です・ます調）を基本**
- **指摘・修正依頼への感謝を冒頭に置く**（事実として時間を割いてもらった）
- **断定を避けず議論を閉じない。ただし既定では相手に応答義務を課さない** — **結論が出ている報告には締めの一文を置かない**（対応内容・理由で終える）。誤りがあれば相手は再度コメントできるので、それを促す一文は文面を伸ばすだけになる
  - **「いかがでしょうか」系（応答を求める形）は「相手の応答がなければ次に進めない」場合に限る**（判定は番号でなくこの原理で行い、以下は例示）: 2.4（意図確認）/ 2.5（反証・両論提示して選んでもらう）/ **2.6 の部分対応**（残存指摘があり対応要否の判断が要る）。**結論が出ている報告には付けない**: 2.1（完全対応）/ 2.2（部分対応の報告）/ 2.3（据置）— 対応済みの報告に確認依頼を付けると、レビュアーは必要なら再度コメントするだけなのにレビューの往復が 1 回増える（GitHub issue #97）
- **過度な謝罪・卑下を避ける**（「申し訳ありません」の連発は逆に読みにくい）
- **絵文字は使わない**（このプロジェクトの規約。emoji は user 明示要請時のみ。署名も emoji なしのテキストで付ける → 0.1）

### 1.2 言い回しテンプレ（コピペ可）

| 場面 | 推奨表現 |
|---|---|
| 修正完了の報告 | 「ご指摘ありがとうございます。{commit} で対応しました」 |
| 据置判断（理由あり） | 「{理由} のため、本 PR では据置とさせてください」 |
| 部分対応 | 「{範囲} は対応しましたが、{残課題} は別 PR で対応予定です」 |
| 意図確認 | 「{解釈} という認識で合っていますか？」 |
| 仕様確認 | 「これは意図的な挙動でしょうか？」 |
| **締め（結論が出ている報告）** | **置かない** ← 2.1 / 2.2 / 2.3 は対応内容・理由で終える |
| 判断委譲（**相手の応答がないと次に進めないときだけ**） | 「いかがいたしましょうか」「判断お任せします」 ← 2.4 / 2.5 / 残存指摘のある 2.6 |
| 議論への合流 | 「{論点} について別途整理させてください」 |
| LGTM 表現 | 「対応ありがとうございます。問題なさそうです」 |
| 軽微な追補 | 「補足ですが、{詳細}」 |

### 1.3 禁則（書かないこと）

- **「すみません」「ごめんなさい」の連呼**（1 メッセージ 1 回まで、なくても可）
- **「言われた通りにします」のような盲従表現**（判断の理由が透けない）
- **「これは○○さんの責任で」のような責任転嫁**
- **「ちょっと」「ざっくり」のような曖昧語**（規模・範囲は具体化）
- **指摘の妥当性に対する直接的な反論**（「それは違います」→「{別の観点} もあるかもしれません」へ言い換え）
- **皮肉・受動攻撃**（既知だが念のため）
- **コミット番号のない「修正しました」**（必ず commit SHA か file:line を添える）
- **Claude 生成文面で署名を欠く**（0.1。人間が大幅に書き換えた場合を除き必須）

## 2. 返答パターン別ガイド

### 2.1 「完全に対応した」場合

**構成**: 感謝 → 対応内容（commit + 場所）→ 署名（**締めの一文は置かない**）

```
ご指摘ありがとうございます。
{file:line} で {対応内容を一文で} 修正しました（{commit-sha 短縮 7 桁}）。
— Created by Claude
```

**避ける**:
- 「修正しました。」だけの一文返答（追跡しづらい）
- **「ご確認いただけると助かります」「認識に誤りがあればご指摘ください」のような締めの一文**（対応が完了している以上、レビュアーは必要なら再度コメントする。往復を 1 回増やすか、文面を伸ばすだけ → 1.1）

### 2.2 「部分対応＋残課題」の場合

**構成**: 感謝 → 対応した範囲 → 残課題と理由 → 別 PR/Issue 化の宣言 → 署名（**締めの一文は置かない**）

```
ご指摘ありがとうございます。
{対応した範囲} については {commit} で対応しました。
残る {残課題} は {理由: スコープ/時間/影響範囲} のため、別途 {Issue/PR} で対応させてください。
— Created by Claude
```

**避ける**: 残課題に触れず「対応しました」とだけ書く（後でレビュー再開時に齟齬が出る）

### 2.3 「据置（意図的に対応しない）」場合

**構成**: 感謝 → 据置の理由（**ここが本体**）→ 署名（**締めの一文は置かない**）

```
ご指摘ありがとうございます。
{理由: 設計判断/既存挙動の維持/性能/影響範囲} のため、本 PR では据置とさせてください。
{懸念が残る場合の対応方針} という認識です。
— Created by Claude
```

**重要**: 据置は「意図的に何もしない」判断なので、**理由が最重要**。理由が薄いと再指摘の原因になる。

**判断そのものを相手に委ねたい場合は 2.5 を使う**（据置してよいか迷っている＝結論が出ていないなら、それは据置報告ではなく両論提示）。2.3 は**結論が出ている**据置の報告なので、締めで応答を求めない。

### 2.4 「意図を確認したい」場合

**構成**: 指摘の解釈 → 自分の理解 → 確認質問

```
{論点に対する自分の理解} という認識で読んだのですが、
{指摘の核心} は {解釈 A / 解釈 B} のどちらに近いでしょうか？
— Created by Claude
```

**避ける**: 「よくわかりません」だけの返答（相手に作業を全部投げない）

### 2.5 「指摘に対する追加情報・反証」がある場合

**構成**: 感謝 → 追加情報の提示 → 判断委譲

```
ご指摘ありがとうございます。
{追加情報: 既存実装/過去 commit/仕様ドキュメント} を踏まえると、
{別の解釈} という見方もできそうです。
{両論を踏まえた提案} としたいのですが、いかがでしょうか。
— Created by Claude
```

**避ける**: 「それは違います」「ここはこういう仕様です」など断定（議論を閉じる）

### 2.6 「自分が指摘した側からの再返信」（レビュアー視点）

**構成**: 対応への感謝 → 解決度の確認（必要なら追加質問）

レビュアー発信なので、**未解決の指摘が残る文面には冒頭にメタ行を置く**（0.5）。全面解決の確認だけなら指摘が残らないためメタ行は不要。

```
ご対応ありがとうございます。
{確認した範囲} を確認しました。問題なさそうです。
— Created by Claude
```

部分対応の場合:
```
**重大度: {残る指摘の severity} / 確信度: {confidence} / マージブロッカー: {はい|いいえ}**

ご対応ありがとうございます。
{対応された範囲} の修正は確認しました。
{残る点} について、{追加質問 / 別 Issue 化の提案} はいかがでしょうか。
— Created by Claude
```

### 2.7 承認メッセージ（総合判定 = Approve / Approve with nits 時）

SKILL.md Step 7 の総合判定が **Approve** または **Approve with nits** のとき、PR 全体コメントとして投稿する承認メッセージのガイド。**Needs work のときは承認メッセージを出さない**（指摘の返答ドラフトのみ生成する）。

**構成**: 簡潔な承認 → nits があれば軽く触れる → 署名（0.1）

Approve（指摘なし / nits なし）:

```
レビューしました。問題なさそうなので Approve します。
— Created by Claude
```

Approve with nits（軽微な指摘あり）:

```
レビューしました。大筋問題なく、Approve とさせてください。
細かい点として {nit の要点} がありますが、対応は任意で問題ありません（{file:line}）。
— Created by Claude
```

**避ける**:
- 良い点への言及を入れて冗長化（0.4。レポートの「良かった点」も転記しない）
- nits を承認メッセージで詳述（詳細は inline スレッドに置き、全体コメントは「任意」と添えるに留める）
- Needs work なのに承認文を出す（BLOCKER/CRITICAL がある間は承認しない）

## 3. ドラフト生成の判断ロジック

`review` skill Step 7 から呼ばれた時に従う手順:

1. **指摘ごとに状況を分類**:
   - 著者対応 commit がある → 解決度判定（完全/部分/未対応）
   - 著者対応 commit がない → 「未対応への追補」枠
   - 過去レビュー comment の `re-flag` タグ付き → 「再指摘の追補」枠

2. **2.1〜2.6 の該当パターンを選択**

3. **テンプレに沿って 1〜3 文で生成**（長文化させない）

4. **必ず以下を含める**:
   - メタ行（0.5。**レビュアー発信の文面のみ**。冒頭）
   - 感謝（冒頭）
   - 具体的な commit SHA / file:line（あれば）
   - 締めの一文は**相手の応答がないと次に進めない場合のみ**置く（2.4 / 2.5 / 残存指摘のある 2.6。「いかがでしょうか」系 → 1.1）。**結論が出ている報告（2.1 / 2.2 / 2.3）・2.7 承認メッセージ・5 章の例外には置かない**（いずれも必須なのは署名のみ）
   - 署名 1 行（0.1。文末。**voice を問わず `— Created by Claude`**。リポジトリ規約があればそちらを優先）

5. **0.6 のチェックリストで自己点検する**（欠けていたら直してから次へ）

6. **`writing-polish` を通してから提示する**（冗長な初稿をそのまま出さない）。呼び出し手順・未導入時の skip は closing-flow-guide.md `## 3` が正本。

7. **ユーザー確認を経るまで投稿しない**（このガイドは draft 生成のためで自動投稿は対象外）

## 4. 投稿時の注意（ユーザー手動投稿時の参考）

- **inline コメントへの返信**: GitHub の "Reply" ボタンで返信。`@user` メンションは GitHub が自動補完するので冒頭の手書きは不要
- **PR 全体コメント**: `gh pr comment <pr> --body "..."` でも投稿可だが、議論の文脈を辿りやすい inline 返信を優先
- **複数指摘への一括返答**: 1 コメントに詰め込まず、各 inline スレッドに個別返信する（後で追跡しやすい）
- **コミット直後の返信**: `git push` 完了を確認してから返信（push 前だと commit SHA が GitHub 側にない）

## 5. 例外: トーンを変える場面

以下の場合のみ、より直接的・簡潔な表現を選ぶ:

- **typo 指摘への返信**: 「ありがとうございます。{commit} で修正しました。」だけで十分
- **lint/format の指摘への返信**: 同上。長文化しない
- **明確な誤指摘への返信**: 「{該当箇所} は {理由} のため意図的にこの形にしています。仕様を {ドキュメント/コメント} に追記しました。」
- **緊急性の高い指摘（セキュリティ・データ損失）への返信**: 感謝表現を最小化し、対応状況・残リスク・タイムラインを優先

**署名は 5 章でも必須**（0.6 の適用除外は謝辞・締めの一文であって署名ではない → 0.6 適用範囲）。上の各文例にも末尾に `— Created by Claude` を 1 行添える。**簡潔さが正の短文ほど署名が落ちやすい**ので、ここで明示しておく。

## 6. このガイドの使い方（skill 側の責務）

- review skill Step 7 で、レポート出力後にユーザーへ「返答ドラフトが欲しい指摘」を選択させる
- 選ばれた指摘について、本ガイドを参照しながら 1 件ずつドラフトを生成する
- ドラフトは出力するのみ。投稿は行わない（ユーザーが GitHub 上で手動投稿する）
- トーンガイドに迷う点があれば「{論点} については本ガイドに明示なし」と添えて、ユーザー判断を仰ぐ
