# スコアリング設計の根拠（実行時には読まない）

`scoring-guide.md` から切り出した「なぜそうなっているか」と将来拡張。**Step 6 のスコアリング実行中に読む必要はない** — 規範はガイド本体にあり、ここにあるのは規範を変えるときに必要な背景。


## なぜ 2 軸か（単一軸のジレンマ）

この 2 軸を混同すると次のジレンマが起きる:

| ケース | 単一軸 (confidence のみ) の問題 |
|---|---|
| **重大だが不確実** (race condition の疑い) | confidence 中程度 → 80 未満で**落ちる**。致命的見落とし |
| **軽微だが確実** (typo) | confidence 高い → 報告される。ノイズ |

2 軸化により **「BLOCKER は不確実でも報告」「MINOR はほぼ確実な時だけ報告」** という非対称な報告ルールを表現できる。


## `severity-inflated` の穴（v2.41.0 で塞いだ）

- **`severity-inflated` の穴（v2.41.0 で塞いだ）**: 旧規約は `severity-inflated` を「全 severity で 1 段階下げる」としていたため、**BLOCKER 60-79 → CRITICAL 60-79（要 80）/ CRITICAL 80-94 → MAJOR 80-94（要 95）** が報告マトリクスを割って silent に消えていた。`refuted` 経路しか塞いでいない不変条件は、反証レイヤーの effort を下げる根拠には使えない（orchestration-guide.md `## 5` の「扱い側で保険が効いている」はこの修正込みで成立する）


## パネル運用時の集計（将来拡張）

### パネル運用時の集計（max effort で 1 指摘を複数体反証する場合・将来拡張）

- `refuted` 成立は **過半数かつ全員が file:line 反証根拠を提示** した時のみ。票割れ・棄権（uncertain 混在）は uncertain 扱いとし delta を合算しない
- 現行は全 effort で **1 指摘 1 verdict**（v2.41.0 以降、反証エージェント 1 体が最大 5 件を担当するバッチ運用。1 件を複数体で見るパネルではない）。パネルは event bus 計測後に拡張判断
- **バッチはパネルではない**: 同じ指摘に複数 verdict が付くことは無いので、上の過半数ルールは現行では発火しない。バッチ内の verdict 同士を合算・相殺してはならない（triage-dynamic-gates.md `## 9`）


## 判断待ちの観測: review 経路の MAJOR がゼロに張り付いている

**scoring 規約を変える前に `design-notes/triage-rationale.md` の「未解決の観測」を読むこと。** 特に「MAJOR/MINOR の `severity-inflated` を無条件降格から保護する」（高 severity の不変条件を MAJOR へ拡張する）は precision を直接下げる不可逆な変更であり、**降格由来だと確認できていない段階で入れてはならない**。

## 反証 verdict の実測分布と、上流ガードを入れた根拠（v2.55.0 / GitHub issue #114）

全期間の集計（`adversarial_verify.severity_inflated` を持つ **19 サンプル / 計 67 verdict**）:

| verdict | 件数 | 比率 |
|---|---:|---:|
| confirmed | 23 | 34% |
| **severity_inflated** | **40** | **60%** |
| refuted | 4 | 6% |
| uncertain | 0 | 0% |

### 累計 n=102 での再集計と、層別できない問題（v2.62.0 / GitHub issue #123 A）

**49 サンプル / 計 102 verdict**（`severity_inflated` 53 = 52% / `confirmed` 38 = 37% / `refuted` 9 = 9% / `uncertain` 0 / `contested` 2 = 2%）。**上の n=19 はこの母集団の部分集合**である。

- **この 52% を「上流ガードが効かなかった証拠」と読んではならない。** 累計値は v2.55.0 より前のサンプルを含むため、施策の効果が構造的に薄まる。差分（67 → 102 の 35 verdict）だけを取れば別の値になるが、**publish 側に版マーカーが無かったため差分を厳密に切り出せない** — 2 つの集計の母集団が包含関係にあるという前提に依存した引き算しかできず、それは「フィールドの有無で層別し日付では切らない」という本リポジトリの流儀を満たさない
- そこで v2.62.0 で **`adversarial_verify.calibration_schema`** を足した（1 = base 確認のみ / 2 = 降格典型 4 型を明示）。以後は層別した内訳で判定する。**この教訓の一般形は `orchestration-measurement.md ## 16` の「ゲートを動かす変更には必ず版マーカーを足す」で、v2.55.0 の上流ガードはその対象と認識されていなかった**（プロンプト変更はゲート変更ではないと読んだが、**計測値の意味は同じように変わる**）
- 4 型（base 由来 / 読み違え / 影響の過大見積もり / カテゴリの取り違え）の内訳は、下記 n=1 の軸別内訳（pre-existing / intended / misread / 影響が過大）を型として一般化したもの。**型の妥当性そのものは n=1 由来のまま**なので、`calibration_schema: 2` のサンプルで `severity_inflated` が下がらなければ「型が的外れ」と「そもそも上流で直せない」の切り分けが要る

**反証レイヤーの実際の主機能は severity の較正であって偽陽性の除去ではない**（`refuted` は 6%）。層の価値を否定するデータではない — 実測 1 件では 9 件中 6 件を降格して報告を 1 件に絞れている。**記述と実挙動がずれていた**ので `triage-dynamic-gates.md ## 9` / `prompts/adversarial-verify.md` / 両 SKILL の位置づけを書き換えた。

### v2.41.0 の縮小（バッチ化 + effort 引き下げ）は維持で確定した（GitHub issue #119）

同じ 19 サンプルが `triage-dynamic-gates.md ## 9` のロールバック条件の判定材料でもあった。**`uncertain` 0% / `refuted` 6%** で、どちらの戻し条件（uncertain 増 → effort を `max` に戻す / refuted 増 → バッチ 5 → 3）にも該当しない。**`effort: high` とバッチサイズ 5 を維持**する判定を `## 9` に記録し、「サンプルが貯まるまでは判断しない」の保留状態を解消した。

- `uncertain` が 0 なのは判定を避けているのではなく**判定できている**と読む（`adversarial-verify.md` は根拠を出せない場合に `uncertain` を選ぶよう指示しており、実測 1 件では 9 件すべてに `file:line` 付き根拠が返っていた。1 件は実ブラウザでの再現まで実施）
- **`orchestration-guide.md ## 5` の注記は閉じていない** — 「不変条件（高 severity 非削除）を緩めるときは反証 effort を `max` に戻すか同時に判断する」は verdict 分布とは独立の条件なので、本判定に巻き込まない

**上流ガード（`prompts/reviewer-common.md`「severity を付ける前に: base 状態の確認」）を入れた根拠は n=1 のデータである。** review 1 件の `severity_inflated` 6 件の軸別内訳（pre-existing 1 / intended 2 / misread 1 / 影響が過大 2）から「半分は base を先に見れば避けられた」と読んだ。

- **軸別の内訳は payload に無く、レポート本文から手で数えた値**。集計値（n=19）と内訳（n=1）の信頼度は別物として扱うこと
- そのため**入れたのは prompt の手順追加という可逆な変更だけ**にした。`severity-inflated` の降格規則そのもの（不可逆側）は触っていない。この非対称は意図的で、上の「判断待ちの観測」と同じ流儀
- **効果の確認は `pre_adjust_counts` と `adversarial_verify.severity_inflated` の比率で行う**。ガードが効けば reviewer 側で降格済みの指摘が増え、反証の `severity_inflated` 比率が下がるはず。下がらなければ「reviewer は base を見ていない」か「過大評価の主因が base 以外（misread / 影響の見積もり）」のどちらかで、打ち手が変わる

### 仮説 3 は棄却され、打ち手は「挙動ゼロの MAJOR」に移った（v2.90.0 / GitHub issue #150）

#150 の期待動作 3 は「`inflated_axes` で `pre-existing` / `intended` が支配的なら、打ち手はプロンプトではなく **review 側に base 情報を渡す**こと」という分岐だった。`calibration_schema: 2` の review サンプル 1 件（2026-08-24 / PR 398 / xhigh / large / 21 体）で**この予測は外れた**:

| | 件数 | 比率 |
|---|---:|---:|
| `miscategorized` | **7** | **54%** |
| base 由来（`intended` 2 件の `unknown` 落ち #167 を補正後） | 3 | 23% |
| `overstated_impact` | 2 | 15% |
| `misread` | 1 | 8% |

この回は反証 15 件が **confirmed 0 / severity_inflated 13（87%）** で、報告 0 件。レポート本文が 13 件の降格を一文でまとめており、**降格根拠の共通項が「実行時挙動への影響がいずれも現時点でゼロ」**だった。個別には 2 型に割れる:

1. **命名・コメント・型表現の不備に MAJOR を付けた** — 重複した述語 / コメントの陳腐化 / 名前が分類を約束している / スキーマで排他が未表現
2. **担保を破る呼び出し元が実在しないのに「型で担保されていない」を MAJOR にした** — 本番 5 経路すべて同一値で、誤順・矛盾組を構成できない

**上流降格（`## below-threshold` 跨ぎ）側は逆に review が base 由来 50%**（10 件中 5 件）で、reviewer は base 由来を自分で降格できている。**下流に残るのは主に `miscategorized`** という非対称が、打ち手の位置を決めた。

**なぜ「実行時影響なし = MINOR〜MAJOR」という旧記述が抜け道になったか**: MAJOR の定義は「設計上の問題・将来のバグ温床・保守性悪化（当面動く負債）」で、**挙動が変わらない指摘も定義上は正しく MAJOR に置ける**。しかし `{{SEVERITY_THRESHOLD}}` の既定が `MAJOR` なので、置いた瞬間に本文へ出る。旧記述は CRITICAL → MAJOR の降格しか要求しておらず、**閾値を跨ぐ側の判断を何も規定していなかった**。

**入れたのは立証責任の移動だけ**（「挙動が変わらないなら MINOR 既定。MAJOR を主張するなら発現経路を `file:line` まで書く」）。指摘を出すこと自体は禁じていないので、**判定された** MAJOR→MINOR 降格は `## below-threshold` の件数に残る。

- **ただし「recall を削ったか事後に測れる」とは言い切れない** — この施策は #117 と同じ `## below-threshold` 計数機構に乗るので、下の「効果測定の盲点」がそのまま適用される。立証責任を課したことで reviewer が**そもそも MAJOR 主張を形成しなくなった**分は件数に現れない（形成段階の recall 低下は計数の盲点に入る）。**降格の件数が測るのは「判定された降格」だけ**で、形成されなかった指摘は測れない。切り分けるには下の対照サンプル法（`review_severity_threshold` を変えた群との比較）が要る

- **n=1 の暫定措置**である。issue のコメント自身が「n=1 なので即当てはせず、次の review サンプルで同じ構成なら根拠にする」と書いており、**それを承知で先に当てている**。次の review サンプルで `miscategorized` の構成比が下がらなければ、この規約は効いていないので戻す
- **効果の測り方**: `inflated_axes` の `miscategorized` 比率が下がり、かつ `demoted_types` の `miscategorized`（上流降格）が増えるのが「効いた」形。**両方下がったら recall を削っただけ**なので戻す
- **`calibration_schema` を 3 に上げた。** 型の語彙は 4 型のまま変えていないので据え置きたくなるが、**`miscategorized` の判別条件そのものを変えたので同じキーの意味が違う**。据え置くと v2.90.0 以降のサンプルが PR 398 の回と同じ層 2 に入り、**上の「効果の測り方」が原理的に実行できなくなる**。これは上の #123 A（v2.55.0 の上流ガードで版を足し忘れ、差分を厳密に切り出せなくなった）と**同一の失敗**で、そのとき得た一般則「プロンプト変更でも計測値の意味は同じように変わる」がそのまま適用される。**語彙の同一性は層を合算してよい根拠にならない**
  - **`review-retro.sh` の型別内訳テーブルも層別が要った**（当初「変更不要」と書いたがセルフレビューで否定された）。`severity_inflated` 比率シグナル（`verdict_layers` / `newest_layer`）は元から `calibration_schema` で層別していたが、**効果測定の主指標である `inflated_axes` / `demoted_types` の skill 別テーブル（`demote_rows`）は層別しておらず**、層 2 と層 3 の `miscategorized` を合算していた。版を上げても消費側が混ぜれば #123 A の轍を踏むので、`with_gen`（世代 2 種以上でだけ足す）と同じ条件付き分割で `/calib<N>` を付けた。`CALIB_MIN = 2` は `verdict_layers` 側の下限で本テーブルとは無関係なので据え置き
- **比較条件にモデル世代を含めること**（#169 で payload に入った）。PR 398 の回は main / sub とも Opus 5 で 4.8 の混入が無いので、この 1 件は世代交絡を受けていない

## 反証ゲートの帯を今は広げない（GitHub issue #196 期待動作 2 / v2.105.0）

#196 が「`skip_reason=no-eligible-findings` のゲート幅を見直すかを別途判断する」を残していた。**今は広げない。**

**論点**: 既定 high の帯は BLOCKER 60-94 / CRITICAL 80-94（`triage-dynamic-gates.md ## 9`）。BLOCKER / CRITICAL が 0 件のレビューでは対象が構造的に 0 件になり、層が「走る構成なのに未実施」で終わる。MAJOR まで広げれば埋まる。

**広げない理由**:

- **不発率のシグナルは既に鳴っており、これは監視されている状態**（`review-retro.sh` が「反証レイヤーがゲート該当 0 件で不発だった回が N%」を出す）。**鳴っているシグナルに対して、原因の切り分け前に打ち手を当てない**
- **その不発率が世代と交絡している**（#191）。踏み下げ期は `pre_adjust` の MAJOR 中央値が 7 → 0・報告 0 件率が 42% → 91% で、**上流に指摘が無いから帯に入らない**のか**帯が狭いから入らない**のかが分離できない。世代別の層別は v2.105.0 で入ったばかりで、分離できるサンプルはこれから貯まる
- **帯を広げるのはコストの主要項を増やす方向**。反証はかつて指摘数に比例する唯一の変動費で、バッチ化で上限 3 体・15 件に頭打ちにした経緯がある（`triage-dynamic-gates.md ## 9`）。MAJOR を含めると `xhigh` / `max` の構成に近づく
- **#196 の本題（指摘単位で未検証が読めない）は帯を広げなくても解ける。** 帯の外にいた指摘にマーカーを付け、採用段で一次ソース確認を先に置く方が安い

**再検討の条件**: 世代を揃えた母集団で `no-eligible-findings` 率が高止まりし、かつ**その回の MAJOR に偽陽性が実際に出ている**ことが観測されたとき。前者だけでは「上流に指摘が無い健全な回」と区別が付かない。

## `## below-threshold` は CLAUDE.md「Opus 5 足場③」に反する方向である（v2.58.0 / #117 のセルフレビュー指摘）

ルート CLAUDE.md は「**重要な指摘だけ報告せよ**（recall 低下。全報告→下流フィルタに）」を Opus 5 世代で逆効果になる足場として禁じている。#117 の実装は**下流にあったフィルタを reviewer 側の「書くか書かないか」へ上流移動**させるもので、この規約と逆を向く。**認識した上で、実測（MINOR が調整前 60 → 報告 9 の 85% 破棄・うち confidence 95+ が 7 件）を理由に採った。**

規約が想定する劣化を抑えるため、上流移動を**列挙だけ**に限定してある（判定は従来どおり / 繰り上げ禁止 / 0 件でも申告 / 未注入時は抑制しない）。ただし**散文の但し書きで抑えきれないという前提でこの規約は書かれている**ので、以下は既知のリスクとして残る。

**効果測定の盲点（重要）**: `pre_adjust_counts` に `## below-threshold` を足しても回収できるのは「**判定された** MINOR の件数」だけで、閾値を知った reviewer が**そもそも探索・形成しなくなった** MINOR は数に現れない。**この施策で最も起きやすい劣化が、施策の効果測定の盲点に入っている。** `pre_adjust_counts.minor` が減っても「PR の質が上がった」と読んではならない。

**切り分ける唯一の方法**: `review_severity_threshold = "MINOR"`（抑制なし）の対照サンプルを同規模 PR で数件取り、`pre_adjust_counts.minor`（schema 2 同士）を比較する。抑制ありの群で有意に少なければ、形成段階の recall が落ちている。

**撤去条件**: 上の対照比較で形成段階の劣化が確認されたら、#117 は撤去して下流フィルタに戻す（削減効果より recall を優先する。CLAUDE.md の規約が本則）。
