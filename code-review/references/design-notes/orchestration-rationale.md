# オーケストレーション設計の根拠（実行時には読まない）

`orchestration-guide.md` 系から切り出した「なぜそうなっているか」。**レビュー実行中に読む必要はない** — 規範（何をせよ）は各ガイド本体にあり、ここにあるのは規範を将来ゆるめる／変えるときに必要な背景。ガイド本体を編集するときだけ読む。

各項目の見出しは、対応するガイドの節番号に揃えてある。

## `## 0` 並列発行を「同一メッセージ内の一括発行」と明記している理由

`run_in_background: false`（取りこぼし防止）と一括発行（並列性）は直交する独立の要件で、前者だけ守っても並列にならない。1 体ずつ別メッセージで発行すると、フェーズの実時間が「相内最長」ではなく「全体の合計」になる。

**実測（GitHub issue #95）**: 12 体のレビューで 20.9 min で済むところが 72.9 min、約 3.5 倍。

`run_in_background` の既定が background に変わったのは CC 2.1.198。省略すると完了通知の遅れた agent の出力を取りこぼす（「反応が返ってこない agent」の正体）。

### 一括発行が破られたことを計測に残す（v2.61.0 / issue #122）

規約は v2.35.0 から正しく書かれていたが、**破ったときに計測へ現れなかった**ため事後に検知できなかった。実測（self-review / xhigh / large 帯）: explorer 1 体を単独発行してから残り 3 体を次のメッセージで出したため `duration_explore_min` が **18 分（7.7 + 9.2）**になった。一括なら wave 内最長の約 9 分で済んでいる。

**マーカー種別を増やさずに検知する**: explorer wave の打点（現 `mark wave --explorer`）は「explorer 結果を回収した直後」に打つ規約なので、wave ごとに打てば**行数がそのまま wave 本数**になる（`review-timing.sh waves` → `agents.explorer_waves`）。`durations` は最後の explorer 打点を採るので既存の `duration_explore_min` の意味は変わらない。**LLM の自己申告にしなかった**のは、破ったことを自覚していれば最初から破らないため（自己申告は系統的に「1」へ潰れる）。

### `wave-split` を WARN 化した根拠（v2.91.0 / GitHub issue #172）

`wave-split`（v2.84.0 / 全層検出）は **「偽陽性がどれだけ混ざるかを測る」ため**に WARN を出さない段階に置いていた。9 本のログを合算（`review:completed` n=99 / `dispatch.schema >= 2` が 17 件）して 6 件の発火を人手で判定したところ、**偽陽性 2 件の型が両方同定できた**ので測定段階を抜けた。

| ts (UTC) | skill | waves / expected | wave_sizes | 判定 |
|---|---|---:|---|---|
| 08-24T02:34 | review | 4 / 3 | `[6,10,4,1]` | 偽陽性（meta 項追加前 = #166 で解決済み） |
| 08-24T05:40 | self-review | 3 / 2 | `[2,5,1]` | 偽陽性（skeptic fallback の末尾単独 wave） |
| 08-25T08:32 | review | 4 / 3 | `[1,1,6,1]` | **本物**（explorer 2 体が先頭で 2 wave に割れた） |
| 08-25T13:42 | self-review | 3 / 2 | `[2,2,4]` | **本物** |
| 08-26T02:48 | self-review | 5 / 2 | `[1,2,1,2,1]` | **本物** |
| 08-26T06:07 | review | 2 / 1 | `[2,3]` | **本物** |

**判定可能な直近 5 レビューのうち 4 件が本物の違反。** しかも `agents.explorer_waves` は 4 件すべて `1`（打点は 1 回しか打たれていない）で、`verdict` は 6 件すべて `layered`（#149 の単独 wave 3 連続要件に届かない）＝ **既存 2 経路はどちらも 1 件も拾えていない**。8/23 時点は「判定可能 6 / 検出 2」だったので、3 日で本物が 4 件増えている ＝ **現在も継続して破られている**。

**「skeptic 項を無条件に足す」案は採らなかった（実データで否定された）**:

| ts | waves | 無条件 +1 後の expected | 検出継続? |
|---|---:|---:|---|
| 08-24T05:40（偽陽性） | 3 | 3 | 消える（意図どおり） |
| 08-25T08:32（本物） | 4 | 4 | **消える** |
| 08-25T13:42（本物） | 3 | 3 | **消える** |
| 08-26T06:07（本物） | 2 | 2 | **消える** |

偽陽性 1 件を消す代わりに**本物 3 件が消える**（3/6）。

### 採った条件と、初版が間違えた点（セルフレビューで検出）

採用したのは「**`recall_skeptic.fired` かつ「単独 wave がちょうど 1 本あり、それが末尾」のとき期待を +1**」（`wave_sizes[-1] == 1` かつ `wave_sizes[:-1]` に 1 が無い）。実測 **6/6・偽陽性 0・取り逃し 0**。

**v2.91.0 の初版は `wave_sizes[-1] == 1` だけで切っており、5/6 だった。** 起票時の検証表が 08-25T08:32（`[1,1,6,1]`）を「末尾単独 ○ だが単独 wave が先頭に 2 本残る → 検出」と書いていたのをそのまま実装したが、**この理屈は実装に対応していなかった**:

- 判定は `waves > expected` という**総本数の比較**で、「単独 wave が何本残っているか」は見ていない
- 控除は残数ではなく**総数の期待値を 1 増やすだけ**なので、超過がちょうど 1 の回はそれで消える
- 08-25T08:32 は waves 4 / 記録 expected 3 ＝ 超過 1 なので、末尾控除で `4 > 4` が偽になり**本物の違反が検出されなくなっていた**

| 条件 | 08-24T02:34 | 08-24T05:40 | 08-25T08:32 | 08-25T13:42 | 08-26T02:48 | 08-26T06:07 | 計 |
|---|---|---|---|---|---|---|---|
| 無条件 +1 | ✓ | ✓ | ✗ | ✗ | ✓ | ✗ | 3/6 |
| 末尾単独のみ（初版） | ✓ | ✓ | **✗** | ✓ | ✓ | ✓ | 5/6 |
| 末尾が**唯一の**単独（現行） | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | **6/6** |

**教訓**: 起票時の検証表が「どういう理屈で当たるか」を自然言語で書いていても、**その理屈が実装の判定式と同じ演算をしているとは限らない**。表の結論（検出/非検出）ではなく、**実装した式で表を再計算して突き合わせる**こと。今回はセルフレビューの specialist が実際に `publish-review-event.sh` を走らせて 5/6 を検出した。

### 式の正本を `lib/wave_expect.py` に寄せた（issue #200 / v2.100.0）

式は publish（違反を立てる側）と backfill（後付け）に複製があり、一致を回帰テストで縛っていた。#200 で **retro が集計時に再計算する**ようになって 3 つ目の消費者ができたので、複製を持たせる理由が消えた。

**retro が payload の `waves_expected` をそのまま使わない理由**: 値は publish 時点の式で焼き付くが、**式の版マーカーが無い**。`dispatch.schema` は `measure-tokens.sh` が持つ版で、publish 側の式変更では上げない契約（上げると出所が 2 つに割れる）。結果、式を直しても過去のイベントは旧値のまま数え続けられ、**一度出た偽陽性が固定化する** — 実測で `[6,10,4,1]`（#166 の meta 項が入る前に publish された回）が、解決済みの偽陽性なのに違反として数え続けられていた。

**式に版を持たせて層別する案は採らなかった。** 版を足すと過去のサンプルが層に割れて母集団が痩せる一方、再計算に必要な入力（`agents` / `meta_reviewer` / `recall_skeptic` / `wave_sizes`）は**すべて payload にある**。payload の値は消さず、再計算と食い違った件数を `stale` として出す。

### 限界②が実サンプルで出たので条件を緩めた（issue #200 / v2.100.0）

上の「残存限界②」— **fallback が走っても後ろに meta / 反証 wave が付く回では fallback wave が末尾に来ない** — が、母集団 108 件（10 ログ合算）で初めて実サンプルとして出た。

| ts | `wave_sizes` | waves | 期待（初版） | 期待（現行） | 判定 |
|---|---|---:|---:|---:|---|
| 08-28T00:28 | `[2,5,1,1]` | 4 | 3 | **4** | 初版は**偽陽性** |

`wave_sizes` の合計 9 が申告体数（explorer 2 + reviewer 5 + verify 1 + skeptic 1）と一致し、末尾 2 本はそれぞれ skeptic wave と反証 wave。**どちらも構造的に別 wave が要る**（skeptic は reviewer 完了後、反証は指摘確定後）。初版の条件「末尾が**唯一の**単独 wave」は、後ろに 1 本付いた瞬間に効かなくなる。

**採った条件**: 「**末尾から連続する単独 wave の並びがあり、それより前に単独 wave が無い**」。控除は**常に 1 本だけ**（見込むのは fallback の 1 本であって、末尾の連なりの本数ではない）。

| 条件 | `[2,5,1]` | `[2,5,1,1]` | `[1,1,6,1]` | `[1,2,1,2,1]` | `[2,2,4]` | `[2,3]` |
|---|---|---|---|---|---|---|
| 末尾が唯一の単独（初版） | ✓ | **✗ 偽陽性** | ✓ | ✓ | ✓ | ✓ |
| 末尾の連なり（現行） | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

**`[1,1,6,1]` を落とさないことが要件**（explorer の先頭分割 ＝ 本物）。末尾の連なりは `[1]` の 1 本だけで、その前に単独 wave が残るので控除しない。

### 残存限界（位置ヒューリスティックでは解けない）

- **skeptic の既定経路は fallback ではなく reviewer wave への相乗り**（`triage-dynamic-gates.md ## 8.5`）。つまり `recall_skeptic.fired == true` は追加 wave の存在を**含意しない**。相乗りの回でたまたま末尾が単独になると、控除が誤って効きうる
- **末尾に固まった単独 wave が本当に構造的な直列かは位置からは決まらない**（限界②の残り）。末尾で分割された reviewer wave を控除で 1 本ぶん見逃す余地がある。控除を 1 本に固定してあるので**長い連なりは違反として残る**が、超過ちょうど 1 の回は消える
- どちらも `wave_sizes` の形からは分離できない。**構造的な解は `recall_skeptic` に起動経路（相乗り / fallback）を自己申告させること**で、位置による判定はそれまでの暫定措置
- **支えているのは分布のフィットではなく構造の規約**だが、6 サンプルへの後付けなので**過学習の留保は残る**
- **層の同定はしない**（#166 の判断を維持）— `meta.json` の `description` は LLM 自由文で、分類器は静かに偽陰性へ倒れる。上の案は `wave_sizes` の算術だけで済む
- **実損は idle だけでは測れない**: 4 件の `inter_wave_idle_sec` は 269 / 36 / 31 / 73 秒（`span_sec` の 3〜20%）だが、**wave が増えた分の agent 実行時間**（`inter_wave_agent_sec` 中央値 279 秒）の方が大きい

## `## 1` ブランチ名 checkout を廃止し detach + SHA 突合にした経緯（issue #98 / #69）

review 経路は Step 0 の `EnterWorktree` + Step 1 の `gh pr checkout` により**親 review worktree が PR ブランチを保持している**。子 worktree の `HEAD` が PR ブランチ名と一致することは構造的にありえないため、子側の `gh pr checkout` は git の二重チェックアウト禁止で**必ず失敗する**。テンプレートは失敗時に続行する作りだったので、agent が base branch のファイルを読んだままレビューを始めていた（テンプレート自身が「深刻な偽陽性の原因」と警告している状態のまま走っていた）。

issue #69 で入れた `{{HEAD_REF}}` ガード（「親が checkout 済みなら子でスキップ」）は、この機構により**一度も発火しない**。

そのため子側は `refs/pull/<N>/head` を fetch して detach で入る（親と競合しない）。`{{HEAD_REF}}` はブランチ名なので detach 後の検証には使えず、検証は `{{HEAD_SHA}}` との突合で行う。

**`HEAD_SHA` を空のまま注入してはならない理由**: 子側の突合が `[ "$(git rev-parse HEAD)" = "" ]` になり、detach が正しく成功していても**全 agent が恒常的に「HEAD 不一致」warning を出して confidence を下げる**（逆方向の静かな品質劣化）。さらに `git rev-parse` 自体が失敗する環境では空同士が一致して、**checkout を丸ごとスキップしたうえ「一致」と判定する**。

## `## 5` HEAD 検証行を「必須 1 行」にした理由（issue #98）

checkout は agent 側で走るため、「検証したか」をオーケストレーターが観測できなければ、base branch を読んだままの agent の指摘が silent に報告へ混ざる。issue #98 が「HEAD 検証はテンプレートが agent の自己申告に委ねているため、オーケストレーター側では失敗を検知できない」と指摘したのはこの構造で、**SHA 注入だけでは解消しない**（不在と成功が同じ「warning が無い出力」に見える）。

**行の不在自体が信号になる**ことが要点で、agent の善意に依存しない設計にしてある。

## `## 3.5` ファイル経由渡しに至った実測（issue #100 A）

Step 2.5 は「LLM による再構築・要約・編集は禁止」と正しく定めているが、素直に実装するとオーケストレーターが同一ブロックを N 体ぶん**書き出す**設計になる（xhigh/max・large 帯なら 10〜16 体）。

**実測**: PR コンテキストが約 15,000 字、これを 6 体に転記していた（52 分のレビューのうちメインコンテキスト消費が約 20 分）。

v2.46.0 で同じ処方箋をプロンプトテンプレートと diff にも広げた。共通指示だけで約 7.3k tokens あり、6 体構成では約 44k tokens の出力複製になっていた（出力トークンは単価が最も高い）。

### 「確定事実」だけは全 reviewer に複製する（v2.61.0 / issue #122）

`## 3.5` の判断基準は複製係数なので、原則としては explorer 結果を全 reviewer に配ることはしない。**この枠だけが意図的な例外**である。

**実測**: 1 レビューで **同じ事実に 5 体が独立に到達していた**（`next.config.ts` に `serverActions` 設定が無く Next の既定 1MB が効く、という事実）。5 体それぞれが同じ 2 ファイルを読み直しており、**消しているのは複製コストではなく reviewer 側の重複探索**（tool_uses と cache_read）。

- 複製係数は体数ぶん立つので、**長さで殺す**（合計 10 行以内・explorer 側も 5 項目まで）。10 行を超えるなら選択的注入に落とす
- **裏取り済みとして扱わせる**のが要点（`reviewer-common.md`）。「参考情報」として渡すと結局各自が読み直し、複製コストだけが増えて重複探索は減らない
- 矛盾したときは reviewer 自身の Read を優先させる（explorer の誤りが全 reviewer に伝播する経路を残さない）

**パス渡しの副次効果**: 忠実性がむしろ上がる。agent が読むのはバイト同一の原本なので、転記・要約のリスクがゼロになる（「再構築禁止」を機械的に保証する）。子 worktree でも `$TMPDIR` は同一ホストなので読める。

## `## 5` reviewer の既定 effort を `xhigh` → `high` に下げた根拠（v2.41.0）

reviewer は**全レビューで必ず走り、体数も最大**（最小保証 2 体 〜 high 6 体 / xhigh・max 10 体）のため、レビュー総コストの最大項。ここが最大のコストレバーだった。

引き下げの根拠は 2 つ:

1. Opus 5 はコードレビュー・バグ発見が低 effort でも精度が落ちにくい（公式モデルガイダンス）
2. reviewer 単発の深さには依存しない補償層がある（skeptic / meta-reviewer / 反証）

効果は `review:completed` メトリクス（blocker/critical 件数・findings 推移）で監視し、**悪化が観測されたら既定を `xhigh` に戻す**。

### 反証エージェントだけ effort を下げた理由

反証は既定パスで走り、かつ体数が指摘数に比例する**唯一の変動費**だった（reviewer / specialist は上限で頭打ちになる。v2.41.0 のバッチ化で反証も上限 3 体・15 件に頭打ちになった。v2.61.0 の meta 由来追加バッチを含めても 4 体・20 件）。

ここは誤判定コストの非対称性を **verdict の扱い側**で吸収している — BLOCKER / CRITICAL は `refuted` でも `severity-inflated` でも報告から消さず係争注記を付ける（**2 経路とも** scoring-guide の不変条件で機械保証。`severity-inflated` 側は v2.41.0 で塞いだ）。消えるのは MAJOR / MINOR だけ。**扱い側で保険が効いている層に effort でも保険をかけるのは二重**なので `max` → `high` に下げバッチ化した。

> **この論拠は scoring-guide の不変条件に依存している。** `severity-inflated` の穴（旧規約では高 severity が 1 段階降格で報告マトリクスを割って silent に消えた）を塞ぐ前は、effort 引き下げの前提が成立しない。**不変条件を緩める変更をするときは、反証 effort を `max` に戻すかどうかを同時に判断すること**（この 1 点だけはガイド本体にも残してある）。

### 1 体固定の検証レイヤーを `max` 据え置きにした理由

**誤判定コストの非対称性**（skeptic の見落としは recall 補強そのものを無効化する＝足す係が足さなければ層ごと無意味）と、**体数が 1 体固定でコストが伸びない**ことの両方。

切り分けの原則は「**下げるのは『全レビューで走る』または『指摘数に比例する』レイヤー、据え置くのは 1 体固定の検証レイヤー**」。残る変動費は specialist だが、red-flag 検出時のみで上限も効くため次の検討対象ではない。

## meta-reviewer と反証レイヤーを同一 wave にした経緯（v2.61.0 / issue #122）

**v2.51.0 の時点では見送っていた**（当時は `design-notes/pending-optimizations.md` の未実装案として置いていた）。理由は 2 つで、①実装複雑度（反証が 2 段になり verdict の突合が 2 系統になる）②**xhigh / max でしか meta が走らないので既定 high の運用では効果ゼロ**。「壁時計の実測が貯まって meta の wave が実際に効いていると分かってから入れる」と保留していた。

**実測が出たので採った**（self-review / xhigh / large 帯 / 全体 57 分）: 直列 wave は explorer → reviewer+skeptic → meta → 反証 の 4 本で、meta と反証の分離だけで**約 8 分**。v2.60.0 の実測（review / small 帯）でも meta 8.9 分・反証 6.2 分がそれぞれ独立の wave になっていた。**meta が走る帯（xhigh/max）は 1 wave の単価が最も高い帯**でもあるので、「既定 high では効果ゼロ」は据え置く理由として弱い。

**②の複雑度は「追加バッチ 1 体・上限 5 件」に閉じた**。meta 由来指摘のうち反証ゲート該当分だけを直列の追加バッチに回す（該当 0 件なら wave は増えない = 期待値で削減）。verdict の突合は同じ finding_id 突合を 2 回回すだけで、系統が増えるわけではない。

**依存関係の確認**: meta は「reviewer の全指摘 + diff + explorer 結果」を入力に**指摘を足す**係、反証は「既存指摘の主張のみ」を入力に**較正する**係。互いの出力を参照しないので同時発火できる（冷や読み skeptic を reviewer wave に相乗りさせたのと同じ理屈）。**唯一の依存**が「meta が足した指摘も反証対象」で、それが上の追加バッチ。

## `## 8` 観点カバレッジ検算を起動前へ前倒しした経緯（v2.39.0）

reviewer 起動後（旧 Phase 5.7 / 4.7 の補完起動）から前倒しした。起動前に検算すれば漏れ focus は本隊 wave に合流でき、事後の補完起動（直列 wave 1 本追加）が不要になる。planning 漏れ（判定表 vs 構成）の検出力は同一の機械的な表照合のため変わらない（issue #69 の「観点漏れを常時検査する」意図は維持）。

**意図的トレードオフ**: 旧 5.7 が持っていた「失敗 reviewer の補完起動」（起動されたが完走しなかった focus を 1 体だけ再起動する救済）は、直列 wave 削減とのトレードオフで**廃止**した。失敗 focus は `missing_coverage` として欠損観点セクションに必ず明示され、必要ならユーザーが再実行を指示する。auto-retry（出力形式検証）は形式不正のみが対象でハード失敗は救わない — **この差は仕様であり見落としではない**。

旧 5.7 の「追加は 1 体まで」制限は事後の直列 wave を抑えるためのものだったので、起動前検算には引き継がない。

**バイト数からの概算ではなく、実トークンで測った値。** 同一指示の subagent 2 体に
「指定ファイルを Read するだけ」をさせ、transcript の `usage` から比較した
（fleet を回さずに済むので、変えた変数＝オーケストレーターが常時読む doc だけを分離できる）。

  反証レイヤーが走ると `orchestration-dynamic-rounds.md` + `triage-dynamic-gates.md` が

## 締めフロー 5 で agent worktree を掃除する理由（GitHub issue #105）

Agent tool の `isolation: "worktree"` は **「変更が無ければ自動削除」** する仕様。にもかかわらず実測で 13〜23 個の agent worktree が残り、`agent-*` ブランチは 45 本まで蓄積していた。

**原因はプラグイン自身にある。** `prompts/reviewer-common.md` の必須セットアップが

```
git fetch origin refs/pull/<N>/head
git checkout --detach FETCH_HEAD
```

を実行するため、子 worktree の作業ツリーが作成時（origin/default-branch 派生）から**丸ごと入れ替わる**。ファイルは dirty でないが「作成時と同じ状態」ではないので、自動削除の対象から外れる。issue の観察「未コミット変更なし・PR head SHA のまま」と整合する。

**detach をやめて自動削除に任せる選択は取れない。** これは issue #98 で「子 agent が base branch のファイルを読んだままレビューする」偽陽性を潰すために入れた機構で、戻すと品質が落ちる。残留を作っているのがプラグインである以上、プラグインが片付ける。

**却下した代替案**:

| 案 | 却下理由 |
|---|---|
| SKILL.md に手順を書くだけ（吸収しない） | 毎回手作業。`ExitWorktree` が失敗して運用がブロックされる |
| `git worktree prune` | prune は「ディレクトリが消えた worktree の登録を掃除する」だけで、実体があるものは消さない |
| `ExitWorktree` に force 相当を渡す | そのオプションは無い。あっても state 検証を潰すのは危険 |

**`agent-*` ブランチを消してよい理由**: agent はコミットしないので、ブランチが指すのは PR head そのもの。削除で失われるコミットは無い。並行レビューの生きた worktree は「どの worktree にも checkout されていないものだけ消す」条件で保護される（ただし agent が detach 済みだとブランチは free に見えるため、並行実行時に他レビューの未使用ブランチを消しうる。agent の作業には影響しない）。
