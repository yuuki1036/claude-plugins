# review-guide レポート形式（正本）

review-guide Step 4 の統合執筆と Step 5 の出力、Step 6 の精読の解説・Step 7 の読み合わせの締めで従う。**severity / confidence は付けない**（判定ではなく説明）。全ての事実主張に根拠 `file:line` を添える。

## レポートテンプレート

```
## 読み順ガイド: PR #<N> <title>（<core_files> files / <core_lines> lines / <size_tier>）
（base モードでは「読み順ガイド: <base>..HEAD（<core_files> files / …）」）
（base モードでは見出しの直後に次の 1 行を必ず出す / GitHub issue #274）
base: <base_branch>（<決め方: 引数指定 / このブランチを作った起点（reflog）/ default branch へのフォールバック>）・比較先: <diff_base の短縮 sha>（<base_branch> との分岐点。editor でこの commit と比べるとタスクの diff だけが見える）<base_refresh が fast-forwarded なら「・ローカルの <base> を N commits 早送りした」/ behind-checked-out なら「・⚠️ ローカルの <base> は N commits 遅れている（別の作業ツリーでチェックアウト中のため進めていない）」/ diverged なら「・⚠️ ローカルの <base> に未 push のコミットがある」/ fetch-failed なら「・⚠️ origin から取り直せなかった（比較先は手元の origin/<base> 基準）」/ not-on-origin なら「・<base> は origin に無い（ローカルのブランチ基準）」>

### まず全体
- この PR がやったこと（PR 本文 + diff から 2〜3 行）
- スレッド一覧:
  ① <入口> → <ロジック> → <永続化>（属する精読ファイル番号）
  ② …
- 分割の検討（精読に値するものが上限を超えた回だけ。それ以外は行ごと省く）:
  <スレッドが独立なら「① と ② は同じ精読ファイルを共有せず、片方だけで動く → スレッド単位でコミット / PR / Issue に分けられる」。1 本のスレッドで超えたなら「精読候補が上限 <N> 件を超えた（残り K 件は流し読みに印付きで置いた）。1 回で読み切れる量を超えている」>

### 読まなくてよい（K 件）
- <path> — <理由 1 行: 生成物 / lockfile / rename のみ / 機械的置換（import 差し替え）>

### 流し読み（M 件）
- <path> — <何が変わったか 1 行>
- <path>（精読候補・上限超え） — <何が変わったか 1 行>
- <path>（<signal> の代表・精読から外した） — <何が変わったか 1 行>。<外した理由 1 行。例: surface の検出はテストデータの列名の文字列だけで、数量の計算も永続化も変えていない>

### 精読（N 件・実装の流れ順。精読に値するものだけで、上限に満たなくても埋めない）
1. <path>（スレッド ①・入口）
   この PR で: <何をしたか 2〜3 行>
   難点: <非自明な分岐・並行性・境界値・暗黙の前提。無ければ「特になし」>
   見る行: <file:line 〜 file:line> — <なぜここか>
   レビュー観点: <triage-guide の観点名> → <この PR での具体的な問い>
   前提・決定: <セッション中に伝えられた前提・決定のうち、この精読に関係するもの。無ければ行ごと省く>
2. …
（精読を検査・分岐ごとに分けたときだけ、最後に次の 1 項目を足す。上限 N に数える）
横断: <まとめて見る検査・分岐の名前>（精読 <i>〜<j> の関係）
   評価順: <検査が評価される順 file:line 〜 file:line>
   重なったとき: <2 つ以上が同時に成り立つ入力で返る結果。例: 「作成不可」かつ「値が見つからない」→ 後者が先に返る file:line>
   共有する前提: <検査どうしが共有する値・前提。無ければ「特になし」>
   レビュー観点: <この順・重なりで利用者が正しく対処できるか、などの問い>

### 主張 vs diff（base モードでは「対象なし（ローカル diff）」）
- 本文の主張「…」→ diff で確認: <あり file:line / 見当たらない>
- diff にあるが本文に無い: <path> — <内容>

### テスト対応
| 変更した振る舞い | テスト | 場所 |
|---|---|---|
| … | あり / なし | file:line |

### 人間の判断が効く箇所（base モードでは「対象なし（ローカル diff）」。該当が無ければ「特になし」）
- 既存の行コメント（解決状態は不明）: <file:line> — <要旨>
- review が閾値を割った指摘（同一セッションのみ）: <要旨> — <脱落理由>

（base モードで読み順を記録できたときだけ、末尾に次の 1 行を出す）
読み順の diff: `/guide-diff` で比較先からの diff を上の読み順に 1 ファイルずつ送れる（`/guide-diff N` で N 番目から。ペインを描けない場所では一覧と比較先を返す）

（`--walkthrough` のときだけ、最後に次の 1 行を出してターンを終える）
読み合わせ: 概要を確かめたら「次」で精読 1（<path>）の解説に入ります。前提の補足・解説への要望・質問もそのまま書いてください
```

## 4 項目の書き方

### この PR で（何をしたか）

- diff の追加・変更行から**このファイルで起きた変化**を 2〜3 行。「実装の流れの中でこのファイルが担う役割」を含める（スレッドのどの位置か）
- コミットメッセージや PR 本文の言い換えにしない。diff を読んで書く

### 難点

- **書くもの**: 非自明な条件分岐 / 並行・非同期の順序依存 / 境界値・オフバイワン / 暗黙の前提（呼び出し元がこの順で呼ぶ、この値は事前に検証済み等）/ 他ファイルとの結合で初めて意味を持つ変更
- **書かないもの**: コードを読めばすぐ分かること / 一般論のリスク（「エラーハンドリングに注意」等の中身の無い注意）
- 該当が無ければ「特になし」と書く（無理に埋めない）

### 見る行

- `file:line` か `file:line 〜 file:line` の範囲で、**そのファイルで最初に読むべき箇所**を示す
- なぜそこかを 1 行添える（「ここが分岐の起点」「この代入が下流の永続化に効く」等）
- 粒度は関数単位〜数行。ファイル全体を指さない

### レビュー観点

- `triage-guide.md ## 3` の観点判定表で、このファイルの `## focus-signals` ヒットに対応する観点名を引く（error-handling / security / performance / type-design 等）
- 観点名を挙げるだけにせず、**この PR での具体的な問い**に落とす（例: 「performance → ループ内 await が N+1 になっていないか」「type-design → この enum 追加で網羅していない switch が無いか」）
- これは「何を見るか」であって「バグがある」という判定ではない
- **難点の言い換えだけの問いは書かない**: 答えが難点か問いの括弧書きにもう書いてある問い（例: 難点「`??` は空文字を通す」に対する「`??` は空文字を通すか」）。確かめても新しいことが分からない。難点で見つけたことからは、その先の問い（同じ原因の別の経路はあるか・テストは変更の前後を区別できるか・この変更が前提にしている呼び出し元の約束は守られているか）を立てる。その先の問いが立たなければ「レビュー観点: 難点に含む」と 1 行で書く

### 前提・決定（セッション中に伝えられたもの / GitHub issue #291）

- SKILL.md Step 1.5 で控えた前提・決定のうち、この精読に関係するものだけを書く。関係するものが無ければ行ごと省く（「特になし」で埋めない）
- 確定と未決を書き分ける:
  - 確定: 「確定: <要旨>（根拠: セッション中の決定）」。仕様の該当節で確かめられるなら「（根拠: 仕様 `path:line`）」
  - 未決: 「未決: <要旨>（<どこで決まるか。分かれば>）」
- コードが伝えられた前提と食い違うときは「⚠️ 食い違い: 伝えられた前提『<要旨>』↔ コード `file:line`」と書く。どちらが正しいかは判定しない
- 確定済みの論点を「難点」に書くときは「仕様どおり（確定）」と明記し、修正が要ると読める言い方にしない

### 横断の精読（GitHub issue #294）

精読を検査・分岐ごとに分けたとき（1 つのファイルに足した複数の検査を別々の精読にした / 同じ入口に効く検査が複数の精読に分かれた）だけ足す。各精読はその検査単体の妥当性を見るので、検査どうしの関係はどの精読にも入らない。拒否の順序のような問題はこの隙間で見落とされる。

- **評価順**: 検査が実際に評価される順を `file:line` で並べる。呼び出し側で組み合わさる場合は、組み合わせる箇所を見る行にする
- **重なったとき**: 2 つ以上の条件が同時に成り立つ入力を 1〜2 組作り、評価順どおりに辿って返る結果を書く。対象そのもので決まる拒否（作成不可・権限・状態）より、入力値で決まる拒否（値が見つからない・形式が違う）が先に返るなら、そう書く
- **共有する前提**: 複数の検査が同じ値・同じ事前検証を前提にしているなら書く（片方の検査を外すと、もう片方の前提が崩れるもの）
- 判定はしない。「この順で利用者が正しく対処できるか」のような問いに落とす

## 精読の解説（Step 6 / 読み合わせ）

レポートの精読 1 件を 1 ターンで解説する。**editor を開かずに読み切れること**を基準にする: 読み手が `file:line` を開きに行かないと分からない書き方をしない。

```
### 精読 <i>/<N>: <path>（スレッド ①・<入口 / ロジック / 永続化 / テスト>）

置き場所: <このファイルがなぜこのパス・この層にあるか。同じ役割のファイルの並び・規約の該当箇所 file:line。新規ファイルなら、既存のファイルに足さずに分けた理由>

関連ファイル:
- <path> — <役割 1 行>（呼び出し元 / 呼び出し先 / テスト / 正本・規約 / 同じ形の兄弟）。<この変更で一緒に変わったか、変わっていないが前提にしているか>
- …

この変更で: <何をしたか 2〜4 行。スレッドの中でこのファイルが担う役割から書く>

コード:
<file:start-end>（<この範囲が何をする所か>）
（言語名付きのコードフェンスで変更後のコードを引用する）
→ <この引用で何が起きているか 1〜3 行>
（変更前に意味がある回は、変更前の引用を並べる）

難点: <何が難しいか>
  なぜ難点になったか: <原因。外部の制約（API・ツールの仕様）/ 既存コードとの結合 / 後方互換 / 仕様の未決・曖昧さ / 並行・順序 / 規約 のどれか>
  （難点が無ければ「難点: 特になし」の 1 行で、原因の行は出さない）

レビュー観点（確かめた結果）:
- <問い> → 問題なし: <理由> file:line
- <問い> → 直した: <何を>（下の「修正」）
- <問い> → 直すべき（未修正）: <何がどう壊れるか> — <直さなかった理由: FIX_OK=0 / diff の外へ広がる / 別チケット候補>
- <問い> → 判断が要る: <選択肢と、それぞれで何が変わるか。1 つは必ず「このまま」で、変えないときの利点と欠点を書く>
- <問い> → 未確認: <何が分かれば決まるか> — <どこを見れば / 誰に聞けば決まるか>（手元で試したこと）
- <問い>（言い換え: 答えは難点。その先の問いを次の行に。立たなければこの行だけ）
確かめた手段: <走らせたコマンドと結果 / 読解のみ（走らせなかった理由を事実で）>

前提・決定: <関係するものだけ。無ければ行ごと省く>

修正: <この解説の前に直したもの。無ければ行ごと省く>
- <file:line> — <何をどう直したか>（変更前 → 変更後の引用。テストを走らせたら結果、走らせていなければ「未実行」）
  確かめ方: <挙動を変える修正だけ。直ったことを観測できる手順と、テストが直す前後を区別できるか>
  副作用: <挙動を変える修正だけ。この修正で他に振る舞いが変わる経路。無ければ「無い」と根拠 file:line>

確認したいこと: <直さずに聞く 1 問。上の「判断が要る」から選ぶときは、どの問いかを示すだけで選択肢は繰り返さない。無ければ行ごと省く>
持ち越した確認: <この精読で新たに持ち越した問い（聞かなかったもの・答えが返らなかったもの。各 1 行。締めで聞く）。前の精読から持ち越しているものは載せ直さない。無ければ行ごと省く>

次: 「次」で精読 <i+1>（<path>）へ。質問・修正の指示・前提の補足はそのまま書いてください
（最後の精読では「次」で締め（精読の外で気になるところ）へ）
```

### 置き場所

- パス・ディレクトリの規約（`scripts/` に寄せる、`references/` は実行時に読む、など）と、同じ役割のファイルが並んでいる事実（`ls` の結果）から書く。規約の文言があればその `file:line`
- 新規ファイルは「なぜ既存のファイルに足さずに分けたか」を、diff・規約・設計 doc から読めるときだけ書く。読めなければ「分けた理由はコードから読めない（要確認）」と書き、推測で埋めない

### 関連ファイル

- 呼び出し元・呼び出し先・対応するテスト・正本や規約・同じ形の兄弟ファイルから、この変更を理解するのに要るものだけを選ぶ（目安は 2〜5 件。多ければ要るものに絞る）
- 各行に「この変更で一緒に変わったか / 変わっていないが前提にしているか」を書く。後者は、この変更が前提を崩していないかを見る入口になる
- テストは実装の精読に畳んでいるので（SKILL.md Step 2）、対応するテストはここに必ず入れる。テストが無ければ「テスト: なし」と書く

### コード

- 引用は変更後のコードを、範囲 `file:start-end` を見出しにして示す。1 精読あたり 1〜3 か所、1 か所 30 行まで。長い関数は要る行だけを残し、間を `…（file:a-b は省略: <そこにあるもの>）` で畳む
- 条件を緩めた・順序を入れ替えた・値を変えたなど、**変更前に意味がある回**は変更前も並べる（`git show <diff_base>:<path>` か diff の `-` 行から）
- 引用の後に、その引用で何が起きているかを 1〜3 行で書く。引用を貼るだけにしない

### 難点となぜ難点になったか

- 難点の書き方はレポートの「難点」と同じ（書くもの / 書かないもの）
- 「なぜ難点になったか」は、その難しさがどこから来たかを 1〜2 行で書く。コード・コミット履歴（`git log -S'<行の文字列>'`）・設計 doc・規約から読めるときだけ書き、読めなければ「原因はコードと履歴から読めない（要確認）」と書く

### レビュー観点（確かめた結果）

- レポートで挙げた問いに、読んだコードで答える。問いを並べて利用者に答えさせない
- 「問題なし」には、そう言える理由と根拠 `file:line` を付ける（「問題なし」だけを書かない）
- 「確かめた手段」は精読ごとに 1 行。走らせたコマンドと結果か、「読解のみ」と走らせなかった理由を事実で書く（走らせられるのに走らせなかったなら「走らせていない」とだけ書き、走らせられないとは書かない）。答えの行ごとには繰り返さない。走らせた答えと読解だけの答えが混ざるときだけ、読解だけの行の末尾に「読解のみ」と付ける
- 「判断が要る」は、答えしだいでコードを変えるか変えないかが分かれる問いに使う（仕様が未決でもこちら）。選択肢と、それぞれを選んだときに何が変わるかを書き、どれを選ぶかは聞く（「確認したいこと」へ）。**選択肢には `このまま`（変えない）を必ず入れ**、変えないときの利点と欠点の両方を書く（欠点だけを書いて変える案へ傾けない）
- 「直すべき（未修正）」は、直すべきだと決まったが、この場では直さなかったもの（`FIX_OK=0` / diff の外へ広がる / 新しい仕組みが要る）。直さなかった理由を書く。直すと決まっているので `このまま` を含む選択肢は出さない（好みで選ぶ「判断が要る」に寄せない）
- **同じ事実・同じ問いは 1 か所に書く**: 難点・コードの説明・答え・確かめ方・確認したいことで同じ事実を言い直さず、2 か所目からは「難点のとおり」「上の問い 2」のように指すだけにする。読み合わせの解説は 1 精読 1 ターンで読まれるので、繰り返しはそのまま読む量になる
- 「未確認」は、答えが分かっても直すかどうかに直結しない事実のうち、このリポジトリと手元で走らせられるものからは決まらないものに使う（リポジトリの外の呼び出し元が渡す値・実行環境や DB の種類・運用のデータ・作者の意図）。何が分かれば決まるかと、どこを見れば / 誰に聞けば決まるか、手元で試したこと（リポジトリ内の呼び出し元の grep など）を書く。決まらないのに「問題なし」で閉じず、読めば決まる問いを未確認に逃がさない。未確認は締めの「まだ答えの無い確認」に集める
- 難点の言い換えだけの問い（答えが難点か問いの括弧書きにもう書いてあるもの）には答えを出さない。レポートに載ったものは「（言い換え: 答えは難点）」と 1 行示して、その先の問いに置き換える（黙って消さない）

### 修正

- 直したものは変更前後を引用し、どの問いから見つかったかを添える。直してよい範囲は SKILL.md Step 6 の 4.
- 対応するテストを走らせたら、コマンドと結果（通った件数 / 落ちたテスト名）を書く。走らせていなければ「未実行」と書く
- **挙動を変える修正**（本命。1 精読に複数あればそれぞれ。利用者の指示や締めで入れたものも同じ）には、確かめ方と副作用を添える:
  - 確かめ方: 利用者が直ったことを観測できる手順。直る前に失敗した入力と、直った後に期待する結果・ログ・戻り値を書く。テストがあれば、そのテストが直す前後を区別できるかも書く（戻り値が前後で同じなら、戻り値だけを見るテストでは区別できない）。走らせて確かめていなければ「読解のみ」と書く
  - 副作用: この修正で他に振る舞いが変わる経路（例: 共通のハンドラに通したので、別のエラーもログに出るようになる）。無ければ「無い」と、そう言える根拠 `file:line`

## 読み合わせの締め（Step 7）

```
### 読み合わせの締め

精読の外で気になるところ:
- <path or 観点> — <何が気になるか 1〜2 行> file:line
（無ければ「特になし」）

まだ答えの無い確認:
- 精読 <i>（<path>）— 持ち越し: <問い>
- 精読 <i>（<path>）— 未確認: <問い> — <どこを見れば / 誰に聞けば決まるか>
（各 1 行。選択肢や理由は解説に書いたので繰り返さない。下の「確認したいこと」で聞く 1 問は載せない。1 件も無ければこの見出しごと省く）

確認したいこと: <1 問だけ。持ち越しがあれば、答えで直すかどうかが変わり影響が大きいもの（選択肢つき。このまま を含む）。無ければ「ほかに精読の外で気になるところがあれば書いてください」>
（未確認は、分かるものがあればあわせて書いてもらう。返信ごとに次の 1 問へ進む。切り上げで来た回は聞かずに次へ）

（聞くものが尽きるか、利用者が「締めて」と返したら、次をまとめて出す）
入れた修正（K 件）:
- <file:line> — <何を>（精読 <i> / 締め）
  （締めで入れた挙動を変える修正には、確かめ方と副作用の 2 行を添える）
残った確認（答えが返らなかった持ち越しと未確認。各 1 行。無ければ行ごと省く）:
- 精読 <i> — <問い>（持ち越し / 未確認: <どこを見れば決まるか>）
持ち越した前提・決定: <要旨。無ければ行ごと省く>
別チケット候補: <直さずに残したもの。無ければ行ごと省く>
変異テスト: <提案する / 不要 / 道具なし> — <理由 1 行>（`提案する` のときだけ、続けて「。回し方: `<コマンド>`（所要の目安: <…>）」）
self-review 以降の変更: <あり / なし / 不明（理由）>
次の一手: <self-review をもう一度 / 決定的な検証: <回すもの> → コミットへ / コミットへ> — <理由 1 行>
```

- `self-review 以降の変更:` の行は呼び出し元が読む契約。値は `あり` / `なし` / `不明（<理由>）` の 3 つで、言い換えない
- `次の一手:` は下の「回し直すかの判断」で決める。先頭は `self-review をもう一度` / `決定的な検証` / `コミットへ` の 3 つで、言い換えない（呼び出し元は `あり` のとき、この先頭が `決定的な検証` かで self-review を回すかを決める）。`self-review をもう一度` の引数は base だけで、`--focus` / `--rereview` / `--embed` を付けない
- `変異テスト:` の行も呼び出し元（issue-workflow の軽量フロー・feature-dev の Phase 7）が読む契約（GitHub issue #307）。先頭は `提案する` / `不要` / `道具なし` の 3 つで、言い換えない。決め方は下の「変異テストの提案」。`提案する` のときだけ、理由の後に `回し方:`（リポジトリのルートでそのまま実行できるコマンド）と `所要の目安:` を続ける。呼び出し元はそれをそのまま回すかの問いに使い、承認を得てから回す。この skill は回さない
- `コミットへ`（`決定的な検証` の後を含む）のコミットは、呼び出し元のフローがあればその手順で、単独で起動した回は使える skill に `dev-workflow:git-commit-helper` があればそれで行う。利用者が次の一手どおりに進めるよう返したときも `git commit` を直接打たない
- 「精読の外で気になるところ」を聞く前に、自分で挙げる（流し読み・上限超えの精読候補・横断・テスト対応表の「なし」・doc や CHANGELOG の追随漏れ）。利用者に一から探させない。精読の解説で扱った点・持ち越した確認と同じ点は載せない（無ければ「特になし」）
- 「まだ答えの無い確認」は、持ち越した確認と未確認の点（解説に書いた「要確認」を含む）を集めたもの。一覧は見えるように出すが、**聞くのは 1 問ずつ**（確認をまとめて出されると利用者は判断しにくい）。答えの扱いは SKILL.md Step 6 の「利用者の返信の扱い」と同じ。答えが返らなかったものは「残った確認」に残す（黙って消さない）

## 回し直すかの判断

Step 7 の 3. で従う。`self-review 以降の変更: あり` は「差分がある」という事実で、回し直す価値があるという判断ではない（GitHub issue #304）。値をそのまま次の一手に直結させると、回し直しても前回と同じ閾値未満の候補が並び直すだけの回まで self-review をもう一度回すことになり、利用者が毎回「self-review はいるか」を聞き直す。`次の一手:` は値と変更の中身から決め、理由を 1 行添える:

| 値 | 次の一手 |
|---|---|
| `なし` | `コミットへ` |
| `不明（…）` | 読み合わせで修正を入れた → `self-review をもう一度` / 入れていない → `コミットへ` |
| `あり` | 下の 3 条件をすべて満たす → `決定的な検証` / 1 つでも外れる → `self-review をもう一度` |

`あり` で `決定的な検証` にする条件:

1. **全部を挙げられる**: self-review の後に入った変更を、このセッションの記録（読み合わせで入れた修正・self-review の修正方針で直した指摘・利用者の指示で入れた変更）からすべて挙げられる。利用者が editor で直した・別のセッションで入ったなど、中身を見ていない変更があれば外れる
2. **解説で確かめた**: どの変更も、読み合わせの解説か「修正」の引用で変更前後を確かめた
3. **実行時の挙動を変えない**: 分岐・状態・入出力の契約（引数・戻り値・出力の形式・規約の文言）を足していない・変えていない。当たるのは名前・コメント・doc、テストの改名やアサーションの追加、中身を変えないブロックの移動（並びが表示や評価の順に効くなら、その並びをテストで固定してある）

`決定的な検証` の後には、変更に効くものを挙げる: 関連テスト・typecheck・lint（プロジェクトが `.claude/review-oracles.sh` を宣言していればそれ）。理由には、どの条件で self-review を外したか（または、どの条件が外れて self-review をもう一度にしたか）を書く。例: 「self-review の後の変更はテスト名・コメントの直し 6 件と、テストで並びを固定したブロックの移動だけで、どれも解説で確かめた」

## 変異テストの提案

Step 7 の 4. で従う（GitHub issue #307）。締めの `変異テスト:` の行を決める。変異テストは変更した行を 1 か所ずつ壊してテストを回し、壊してもテストが通る（生存する）箇所を挙げる。テストの件数や「通った」では分からない、テストが検証していない挙動が出る。代わりに変異 1 個ごとにテストを 1 回回すので長い（変異の前にフルスイートを 1 回回す道具では、それだけで 10 分を超えることもある）。要るときだけ提案し、この skill からは回さない。回すかは呼び出し元か利用者が決める。

### 要るか

先に要るかを決め、要るときだけ道具を探す。次の 2 つを両方満たすときだけ要る:

1. **壊すと結果が変わる行を足した・変えた**: core の変更に、分岐の条件・境界（比較・範囲・上限）・検証ロジック（入力の検査・ガード・判定・早期 return）がある。精読の「難点」と流し読みの 1 行から当たりを付け、hunk で確かめる
2. **その振る舞いにテストがある**: テスト対応表で「あり」。この diff でテストを足した・変えた回は、足したテストがその分岐を検知するかを測る。テストを変えていない回は、既存のテストがこの変更を検知するかを測る（理由にどちらかを書く）

当たらなければ `不要` で、当たらなかった方を理由に書く。例:

- core の変更が無い（doc・test・gen だけ）
- 名前・コメント・文言・設定値・定型の追記・呼び出し側の機械的な追従だけ
- 1 に当たる振る舞いが、テスト対応表ですべて「なし」。壊せば全部生存すると分かっているので、先にテストを足す（締めの「精読の外で気になるところ」に挙げる）

### 道具

要るときだけ `bash "${CLAUDE_PLUGIN_ROOT}/scripts/detect-mutation-tool.sh"` で探す（引数なし。リポジトリのルートを見る）。値は出力の `mutation_tool=` で決める:

| `mutation_tool=` | 値 | 回し方 |
|---|---|---|
| `declared` | `提案する` | `bash .claude/mutation-test.sh --base <ref>`（推測しない） |
| `inferred` | `inferred=` の道具のうち、変更した core の言語に合うもの（Stryker: JS / TS・mutmut: Python・cargo-mutants: Rust）を 1 つ選んで `提案する`。合うものが無ければ `道具なし` | 下の「推測した道具の回し方」 |
| `none` | `道具なし` | — |

- `<ref>` は、base モードなら `## meta` の `diff_base=`。PR モードなら `git merge-base origin/<baseRefName> HEAD` の値で、`FIX_OK=0` なら理由に「PR head を checkout してから回す」を添える（手元が PR head と違うと、解説した diff と別のコードを測る）
- 所要の目安は、`declared` で出力に `estimate=` があればその値。無ければ「変異 1 個ごとにテストを 1 回回す（変更の規模 <core_files> files / <core_lines> lines）」
- `道具なし` では導入は提案しない。何が無かったかを 1 行書く（宣言も既知の道具の設定も無い / 見つかった道具が変更の言語に合わない / 引用できないパスのファイルを外すと何も残らない）。導入は道具の選定・設定・CI への組み込みまで広がり、締めで決める範囲を超える

推測した道具の回し方（範囲を変更行か変更ファイルに絞る。指定の仕方は道具の版で変わりうるので、呼び出し元は問いでコマンドを見せ、承認を得てから回す）:

- Stryker: `npx --no stryker run --mutate '<file>:<start>-<end>,<file>:<start>-<end>'`（変更した core のファイルと hunk の行範囲をカンマで並べる）。`--no` は、ローカルに入っていない Stryker を registry から取りに行かせないため（TTY の無い実行では npx が確認なしで取得し、同名の別パッケージが回りうる）。ローカルに無くて失敗した回は判定不能として報告する
- cargo-mutants: `d=$(mktemp -d) && git diff <ref> > "$d/mutants.diff" && cargo mutants --in-diff "$d/mutants.diff"`（diff は作業ツリーの外の、回ごとに作る一時ディレクトリに書く。名前を決め打ちにすると、同時に回した別の worktree と diff を上書きし合い、共有の `/tmp` では別のユーザーが先に置いたファイルやリンクに書き込みうる。未追跡のファイルは diff に入らない）
- mutmut（3 の形）: `mutmut run '<module>.*' '<module>.*'`（変更した core のモジュールを並べる。`<module>` はリポジトリのルートからのパスの `.py` を外して `/` を `.` に替え、先頭の `src.` を落とした名前で、`src/pkg/foo.py` なら `pkg.foo`。`pkg/__init__.py` は `pkg` になり、`pkg.*` は下のモジュールにも当たる）。引数は mutant 名（`<module>.<関数>__mutmut_<N>`）へのワイルドカード。`pkg.foo*` だと似た名前の別モジュール（`pkg.foobar`）にも当たるので `.*` まで書く。行範囲では絞れないので、変更したモジュールの関数すべてが対象になる。所要の目安にそう添える。mutant の生成（`mutants/` への複製と変異）だけは設定の `source_paths` 全体に掛かる。名前が 1 つも当たらないと止まる（変更したファイルが `source_paths` の外にある回など）ので、判定不能として報告する

Stryker の `<file>` と mutmut の `<module>` は単引用符で囲んで埋め込む。**パスに `'`・改行・制御文字を含むファイルは回し方に入れず**、理由に外したことを書く。`'` を `'\''` に置き換えて引用を組み立て直すことはしない（パスは diff から来る値で、組み立てを誤ると、利用者が承認したコマンドの中で別のコマンドが走る）。外した結果、回せるファイルが 1 つも残らなければ `道具なし` にして、外したことを理由に書く。

道具によっては作業ツリーに出力を残す（Stryker の `reports/` と失敗した回の `.stryker-tmp/`・cargo-mutants の `mutants.out/`・mutmut の `mutants/`）。変異体を作業ツリーのファイルへ直接書き込みながら回る道具もあるので、回しているあいだは作業ツリーを編集しない。呼び出し元は回す前と後で `git status --porcelain` を突き合わせ、増えたファイルを報告に並べて、コミットに混ぜない。

### 宣言の契約（`.claude/mutation-test.sh`）

- **存在自体が宣言**（`.claude/review-oracles.sh` と同じ流儀）。通常のファイルとしてあれば、それだけを使って推測しない。何を回すかはプロジェクトが決める
- 呼び方: リポジトリのルートから `bash .claude/mutation-test.sh --base <ref>`。範囲を `<ref>` との差分に絞るのは宣言の側。対象は `git diff <ref>` に出る変更で、未追跡のファイルは対象外（review-guide の diff と同じ）
- 終了コード: 0 は実行した変異に生存なし（上限・タイムアウトで未実行が残った回を含む）、または未計測（対象行・変異が 0 個）。どれかは stdout で見分ける。1 は生存あり（stdout に file:line と変異）か、途中で止まった（stderr に中断の FATAL と実行済みの件数）。stdout と stderr の両方で見分ける。2 は判定不能（変異前のテストが赤い・前提が無い）
- 見分ける手がかりは宣言が出す: 未実行が残った回は実行した数と未実行の数を stdout の集計に、未計測の回は集計の代わりに未計測と分かる 1 行を stdout に、途中で止まった回はその旨と実行済みの件数を stderr に出す。この repo の宣言が呼ぶ mutation-test.py では、集計の「上限で未実行 N」「タイムアウト N」、集計の代わりに出る「変異対象の変更行が無い」「変異 0 個」の行、stderr の中断の FATAL がそれに当たる
- 呼び出し元は exit 0 だけで「生存 0」と書かない。全件を実行して生存が無い回だけを生存 0 とし、一部未実行（上限・タイムアウトで未実行が残った回）と未計測を分けて報告する
- 冒頭のコメントに、行頭から `# 所要の目安: <…>` を 1 行置ける。あれば提案にそのまま添える（`detect-mutation-tool.sh` の `estimate=`。複数あれば最初の 1 行）
- 実行時間の上限は契約に含めない（呼び出し元は終わりを待つ）
- 宣言がどの言語を変異させるかを、この skill は知らない。宣言が変異させない言語だけを変えた回は、未計測の exit 0 で終わりうる

## 誤ガイド抑制（file:line 根拠強制の限界を補う）

反証レイヤーを持たないぶん、**解釈を含む項目（難点 / 主張 vs diff）では、根拠 `file:line` に加えて diff の該当ハンクの要点を 1 行引用**して、読み手が引用と主張を突き合わせられる形にする。`file:line` は「その行が実在する」ことしか担保せず、正しい行を引きつつ誤解釈する余地が残るため（設計 F5・未反映指摘への最小策）。断定できない解釈は「〜と読める（要確認）」と留保を付ける。
