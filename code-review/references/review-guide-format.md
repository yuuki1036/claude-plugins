# review-guide レポート形式（正本）

review-guide Step 4 の統合執筆と Step 5 の出力で従う。**severity / confidence は付けない**（判定ではなく説明）。全ての事実主張に根拠 `file:line` を添える。

## レポートテンプレート

```
## 読み順ガイド: PR #<N> <title>（<core_files> files / <core_lines> lines / <size_tier>）
（base モードでは「読み順ガイド: <base>..HEAD（<core_files> files / …）」）

### まず全体
- この PR がやったこと（PR 本文 + diff から 2〜3 行）
- スレッド一覧:
  ① <入口> → <ロジック> → <永続化>（属する精読ファイル番号）
  ② …

### 読まなくてよい（K 件）
- <path> — <理由 1 行: 生成物 / lockfile / rename のみ / 機械的置換（import 差し替え）>

### 流し読み（M 件）
- <path> — <何が変わったか 1 行>

### 精読（N 件・実装の流れ順）
1. <path>（スレッド ①・入口）
   この PR で: <何をしたか 2〜3 行>
   難点: <非自明な分岐・並行性・境界値・暗黙の前提。無ければ「特になし」>
   見る行: <file:line 〜 file:line> — <なぜここか>
   レビュー観点: <triage-guide の観点名> → <この PR での具体的な問い>
2. …

### 主張 vs diff（base モードでは「対象なし（ローカル diff）」）
- 本文の主張「…」→ diff で確認: <あり file:line / 見当たらない>
- diff にあるが本文に無い: <path> — <内容>

### テスト対応
| 変更した振る舞い | テスト | 場所 |
|---|---|---|
| … | あり / なし | file:line |

### 人間の判断が効く箇所（base モードでは「対象なし（ローカル diff）」。該当が無ければ「特になし」）
- 既存の行コメント（解決状態は不明）: <file:line> — <要旨>
- review が閾値を割った指摘（同一セッションのみ）: <要旨> — <脱落理由>
```

## 4 項目の書き方

### この PR で（何をしたか）

- diff の追加・変更行から**このファイルで起きた変化**を 2〜3 行。「実装の流れの中でこのファイルが担う役割」を含める（スレッドのどの位置か）
- コミットメッセージや PR 本文の言い換えにしない。diff を読んで書く

### 難点

- **書くもの**: 非自明な条件分岐 / 並行・非同期の順序依存 / 境界値・オフバイワン / 暗黙の前提（呼び出し元がこの順で呼ぶ、この値は事前に検証済み等）/ 他ファイルとの結合で初めて意味を持つ変更
- **書かないもの**: コードを読めばすぐ分かること / 一般論のリスク（「エラーハンドリングに注意」等の中身の無い注意）
- 該当が無ければ「特になし」と書く（無理に埋めない）

### 見る行

- `file:line` か `file:line 〜 file:line` の範囲で、**そのファイルで最初に読むべき箇所**を示す
- なぜそこかを 1 行添える（「ここが分岐の起点」「この代入が下流の永続化に効く」等）
- 粒度は関数単位〜数行。ファイル全体を指さない

### レビュー観点

- `triage-guide.md ## 3` の観点判定表で、このファイルの `## focus-signals` ヒットに対応する観点名を引く（error-handling / security / performance / type-design 等）
- 観点名を挙げるだけにせず、**この PR での具体的な問い**に落とす（例: 「performance → ループ内 await が N+1 になっていないか」「type-design → この enum 追加で網羅していない switch が無いか」）
- これは「何を見るか」であって「バグがある」という判定ではない

## 誤ガイド抑制（file:line 根拠強制の限界を補う）

反証レイヤーを持たないぶん、**解釈を含む項目（難点 / 主張 vs diff）では、根拠 `file:line` に加えて diff の該当ハンクの要点を 1 行引用**して、読み手が引用と主張を突き合わせられる形にする。`file:line` は「その行が実在する」ことしか担保せず、正しい行を引きつつ誤解釈する余地が残るため（設計 F5・未反映指摘への最小策）。断定できない解釈は「〜と読める（要確認）」と留保を付ける。
