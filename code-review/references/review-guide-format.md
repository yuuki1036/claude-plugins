# review-guide レポート形式（正本）

review-guide Step 4 の統合執筆と Step 5 の出力で従う。**severity / confidence は付けない**（判定ではなく説明）。全ての事実主張に根拠 `file:line` を添える。

## レポートテンプレート

```
## 読み順ガイド: PR #<N> <title>（<core_files> files / <core_lines> lines / <size_tier>）
（base モードでは「読み順ガイド: <base>..HEAD（<core_files> files / …）」）
（base モードでは見出しの直後に次の 1 行を必ず出す / GitHub issue #274）
base: <base_branch>（<決め方: 引数指定 / このブランチを作った起点（reflog）/ default branch へのフォールバック>）・比較先: <diff_base の短縮 sha>（<base_branch> との分岐点。editor でこの commit と比べるとタスクの diff だけが見える）<base_refresh が fast-forwarded なら「・ローカルの <base> を N commits 早送りした」/ behind-checked-out なら「・⚠️ ローカルの <base> は N commits 遅れている（別の作業ツリーでチェックアウト中のため進めていない）」/ diverged なら「・⚠️ ローカルの <base> に未 push のコミットがある」/ fetch-failed なら「・⚠️ origin から取り直せなかった（比較先は手元の origin/<base> 基準）」/ not-on-origin なら「・<base> は origin に無い（ローカルのブランチ基準）」>

### まず全体
- この PR がやったこと（PR 本文 + diff から 2〜3 行）
- スレッド一覧:
  ① <入口> → <ロジック> → <永続化>（属する精読ファイル番号）
  ② …

### 読まなくてよい（K 件）
- <path> — <理由 1 行: 生成物 / lockfile / rename のみ / 機械的置換（import 差し替え）>

### 流し読み（M 件）
- <path> — <何が変わったか 1 行>

### 精読（N 件・実装の流れ順）
1. <path>（スレッド ①・入口）
   この PR で: <何をしたか 2〜3 行>
   難点: <非自明な分岐・並行性・境界値・暗黙の前提。無ければ「特になし」>
   見る行: <file:line 〜 file:line> — <なぜここか>
   レビュー観点: <triage-guide の観点名> → <この PR での具体的な問い>
   前提・決定: <セッション中に伝えられた前提・決定のうち、この精読に関係するもの。無ければ行ごと省く>
2. …
（精読を検査・分岐ごとに分けたときだけ、最後に次の 1 項目を足す。N 件に数えない）
横断: <まとめて見る検査・分岐の名前>（精読 <i>〜<j> の関係）
   評価順: <検査が評価される順 file:line 〜 file:line>
   重なったとき: <2 つ以上が同時に成り立つ入力で返る結果。例: 「作成不可」かつ「値が見つからない」→ 後者が先に返る file:line>
   共有する前提: <検査どうしが共有する値・前提。無ければ「特になし」>
   レビュー観点: <この順・重なりで利用者が正しく対処できるか、などの問い>

### 主張 vs diff（base モードでは「対象なし（ローカル diff）」）
- 本文の主張「…」→ diff で確認: <あり file:line / 見当たらない>
- diff にあるが本文に無い: <path> — <内容>

### テスト対応
| 変更した振る舞い | テスト | 場所 |
|---|---|---|
| … | あり / なし | file:line |

### 人間の判断が効く箇所（base モードでは「対象なし（ローカル diff）」。該当が無ければ「特になし」）
- 既存の行コメント（解決状態は不明）: <file:line> — <要旨>
- review が閾値を割った指摘（同一セッションのみ）: <要旨> — <脱落理由>

（base モードで読み順を記録できたときだけ、末尾に次の 1 行を出す）
読み順の diff: `/guide-diff` で比較先からの diff を上の読み順に 1 ファイルずつ送れる（`/guide-diff N` で N 番目から。ペインを描けない場所では一覧と比較先を返す）
```

## 4 項目の書き方

### この PR で（何をしたか）

- diff の追加・変更行から**このファイルで起きた変化**を 2〜3 行。「実装の流れの中でこのファイルが担う役割」を含める（スレッドのどの位置か）
- コミットメッセージや PR 本文の言い換えにしない。diff を読んで書く

### 難点

- **書くもの**: 非自明な条件分岐 / 並行・非同期の順序依存 / 境界値・オフバイワン / 暗黙の前提（呼び出し元がこの順で呼ぶ、この値は事前に検証済み等）/ 他ファイルとの結合で初めて意味を持つ変更
- **書かないもの**: コードを読めばすぐ分かること / 一般論のリスク（「エラーハンドリングに注意」等の中身の無い注意）
- 該当が無ければ「特になし」と書く（無理に埋めない）

### 見る行

- `file:line` か `file:line 〜 file:line` の範囲で、**そのファイルで最初に読むべき箇所**を示す
- なぜそこかを 1 行添える（「ここが分岐の起点」「この代入が下流の永続化に効く」等）
- 粒度は関数単位〜数行。ファイル全体を指さない

### レビュー観点

- `triage-guide.md ## 3` の観点判定表で、このファイルの `## focus-signals` ヒットに対応する観点名を引く（error-handling / security / performance / type-design 等）
- 観点名を挙げるだけにせず、**この PR での具体的な問い**に落とす（例: 「performance → ループ内 await が N+1 になっていないか」「type-design → この enum 追加で網羅していない switch が無いか」）
- これは「何を見るか」であって「バグがある」という判定ではない

### 前提・決定（セッション中に伝えられたもの / GitHub issue #291）

- SKILL.md Step 1.5 で控えた前提・決定のうち、この精読に関係するものだけを書く。関係するものが無ければ行ごと省く（「特になし」で埋めない）
- 確定と未決を書き分ける:
  - 確定: 「確定: <要旨>（根拠: セッション中の決定）」。仕様の該当節で確かめられるなら「（根拠: 仕様 `path:line`）」
  - 未決: 「未決: <要旨>（<どこで決まるか。分かれば>）」
- コードが伝えられた前提と食い違うときは「⚠️ 食い違い: 伝えられた前提『<要旨>』↔ コード `file:line`」と書く。どちらが正しいかは判定しない
- 確定済みの論点を「難点」に書くときは「仕様どおり（確定）」と明記し、修正が要ると読める言い方にしない

### 横断の精読（GitHub issue #294）

精読を検査・分岐ごとに分けたとき（1 つのファイルに足した複数の検査を別々の精読にした / 同じ入口に効く検査が複数の精読に分かれた）だけ足す。各精読はその検査単体の妥当性を見るので、検査どうしの関係はどの精読にも入らない。拒否の順序のような問題はこの隙間で見落とされる。

- **評価順**: 検査が実際に評価される順を `file:line` で並べる。呼び出し側で組み合わさる場合は、組み合わせる箇所を見る行にする
- **重なったとき**: 2 つ以上の条件が同時に成り立つ入力を 1〜2 組作り、評価順どおりに辿って返る結果を書く。対象そのもので決まる拒否（作成不可・権限・状態）より、入力値で決まる拒否（値が見つからない・形式が違う）が先に返るなら、そう書く
- **共有する前提**: 複数の検査が同じ値・同じ事前検証を前提にしているなら書く（片方の検査を外すと、もう片方の前提が崩れるもの）
- 判定はしない。「この順で利用者が正しく対処できるか」のような問いに落とす

## 誤ガイド抑制（file:line 根拠強制の限界を補う）

反証レイヤーを持たないぶん、**解釈を含む項目（難点 / 主張 vs diff）では、根拠 `file:line` に加えて diff の該当ハンクの要点を 1 行引用**して、読み手が引用と主張を突き合わせられる形にする。`file:line` は「その行が実在する」ことしか担保せず、正しい行を引きつつ誤解釈する余地が残るため（設計 F5・未反映指摘への最小策）。断定できない解釈は「〜と読める（要確認）」と留保を付ける。
