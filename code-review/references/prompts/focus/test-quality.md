### test-quality（テスト品質分析）
```
## 観点: テスト品質分析

分析観点:
- 行カバレッジではなく振る舞いカバレッジに注目
- クリティカルなコードパス、エッジケース、エラー条件の網羅性
- テストが実装詳細ではなく振る舞い/契約をテストしているか
- リファクタリングに対する耐性
- ネガティブテスト（バリデーションロジック）の存在
- 振る舞いを持つ新しいソースファイルに、対応するテストがあるか（テストの変更が 0 のまま足された新規ソースで起動された回は、まずこれを見る）

名前の付いたアンチパターン（該当したら名前で指摘する）:
- **実装に結合したテスト**: 内部の協調オブジェクトを mock する・private メソッドを直接テストする・呼び出し回数や順序を assert する・interface を迂回して確かめる（DB を直接引く等）。振る舞いを変えないリファクタで落ちる
- **同語反復（トートロジー）**: 期待値をコードと同じ計算で作り直している（`expect(add(a, b)).toBe(a + b)`・同じ手順で作ったスナップショット・定数を自分自身と比べる）。構成上必ず通るので、守っているつもりのパスを守れていない。期待値は既知のリテラル・手で解いた例・仕様から取るべき
- **システム境界の外での mock**: 自分のモジュールやクラスを mock している（mock してよいのは外部 API・時刻と乱数・ときに DB やファイルシステムだけ）

**severity 目安**（旧 1-10 スコアの置き換え）:
- CRITICAL (旧 9-10): データ損失・セキュリティ・システム障害に直結するパスのテスト欠如
- MAJOR (旧 7-8): ユーザー影響のあるビジネスロジックのテスト欠如
- MINOR (旧 5-6 以下): マイナーなエッジケース・あれば良い程度
- 同語反復のテストは「テスト欠如」と同じ重さで扱う（そのパスの重要度で上の段を選ぶ）。実装に結合したテストは MINOR が既定（リファクタを妨げる保守コスト）
```
