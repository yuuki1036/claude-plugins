### doc-substance（ドキュメント内容妥当性分析）

doc を「テキスト」ではなく「**現実への主張の束 ＋ 読み手の目的を達成させる文書**」として検証する観点。次の **2 軸**を両方見る:

- **A 軸: 主張の真偽** — 書かれている内容が正しいか（`comment-accuracy` の「主張⇔コード一致」を doc 本文へ一般化したもの）
- **B 軸: 文書としての成立性** — **書かれるべきことが書かれ、読み手が目的を達成できる構造か**。語句・トーンを完璧に磨いても残る構造的欠陥を見る（Diátaxis の functional quality 系。prose polish では捕まらない）

起動条件・effort 制御・grounding 制限は triage-guide.md `### doc-substance の起動（重要度ゲート）` を参照。

```
## 観点: ドキュメント内容妥当性分析

対象は doc ファイル本文（README / API doc / CLAUDE.md / AGENTS.md / ADR / design doc / 手順書 / 解説）。
レビューするのは「内容が正しいか・筋が通っているか・読み手が目的を達成できるか」であって、
表現・言い回し・冗長性ではない。

### A 軸: 主張の真偽（裏取り = code:line / doc:line）
- ground-truth 正確性: doc の技術的主張が実コードと食い違う（code:line で矛盾を提示できるもの）
- 規範の正しさ: 規約 doc の指示通りで動かない / 既存ルールと直接矛盾（別 doc:line で提示できるもの）
- 論理的健全性: 自己矛盾・非論理（内部矛盾の出典を doc:line ×2 で提示できるもの）
- 意味の陳腐化: 内容がコード現状と食い違う（リンク切れではなく主張の陳腐化）
- 例の整合: コード例が現行のシグネチャ / 挙動と食い違う（引数名・戻り値・import パスを code:line で照合）

### B 軸: 文書としての成立性（裏取り = doc:line + 破られた期待）
**「書かれていないこと・構造の破綻」を指摘する軸。** prose の良し悪しではなく、読み手が目的を達成できるかで判定する。
- **完全性（missing content）**: 書かれるべきだが欠落 — 手順の前提条件 / 成功条件 / 失敗時の挙動、パラメータ・オプションの網羅、**コードに追加された新 API / フラグに対応する doc の不在**、一般的ユースケースの例の不在。「書かれた主張が誤り」ではなく「あるべき情報が無い」
- **doc 種別適合（mode purity / Diátaxis）**: how-to / 手順書に理論の長文が混入 / reference に手順・教育文脈が混入 / tutorial に網羅仕様が差し込まれる / **design doc に代替案の比較が無い** / ADR に context・帰結が無い。読み手が「これは学ぶ文書か作業する文書か仕様か」を判断できない
- **読み手前提・順序（cumulative ordering）**: 依存概念より後に前提概念が登場（prerequisite の後出し）/ 対象読者・前提環境（version / 権限 / 事前状態）が未明示のまま手順が始まる
- **判断根拠 WHY（rationale）**: 規約・設計・閾値・制約に「なぜそうするか」が無い（後で変えてよいか判断できない）。決定だけ書いて検討した代替案が無い
- **ナビゲーション（discoverable / addressable）**: 新規ページ / ADR が index・上位ページからリンクされず孤立し、事実上到達不能

**裏取り（2 軸で要求が違う）**:
- **A 軸**: 対象コードを Read して code:line（内部矛盾は doc:line ×2）を提示する（grounding explorer 結果があれば使う）。提示できない A 指摘は根拠なしとして低 confidence で申告する（Step 6 で ≤40 クランプされ実質除外）
- **B 軸**: **doc:line（欠落・誤配置・孤立の発生箇所）＋ 破られた期待**（doc 種別の契約 / その doc 自身が宣言する対象読者・スコープ / 手順が参照する未記載の前提）を示す。**コード照合は不要**。B 指摘は「裏取りできない」のではなく裏取りの相手が doc 種別の期待構造であり、根拠を示せれば好みベースクランプの対象外（scoring-guide.md「好みベース上限クランプ」の doc-substance 条項）

**prose polish との切り分け（誤爆防止 / 最重要）**: 各指摘に「**語句を最小差分で言い換えれば解消するか？**」を自問する。
- YES（言い換え・短縮・トーン統一で済む）→ **doc-substance の対象外**（writing-polish の領分）。低 confidence で申告し機械クランプに委ねる
- NO（内容の追加・再配置・前提充足・根拠補完・例修正が必要）→ **B 指摘として出す**

**自己削除はしない**: 「これは writing-polish/doc-freshness の領分」と自分で観点を落とさない
（`prompts/reviewer-common.md`「評価 6 原則」の原則 2）。表現の好みは「報告しない」のではなく
「根拠なし＝低 confidence」として申告し、機械的なクランプに除外を委ねる。

**severity 目安**（2 軸共通）:
- CRITICAL:
  - A — 裏取りできた内容誤り（doc の主張 vs コードが code:line で矛盾。Step 6 で git blame ガード後に昇格）/ コード例が現行 API と食い違い動かない
  - B — 手順書の必須 prerequisite・step の欠落で読者が**実行不能**になる（完全性の致命欠落）
- MAJOR:
  - A — 裏取りできない論理破綻・規範の誤り（根拠の出典は示せる）
  - B — doc 種別不適合 / WHY 根拠の欠如 / 完全性の重大欠落 / 孤立 doc
- MINOR: 軽微な有用性・曖昧さ・補足的なナビゲーション欠落
```
