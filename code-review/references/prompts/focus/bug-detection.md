### bug-detection（バグ・ロジックエラー検出）
```
## 観点: バグ・ロジックエラー検出

検出対象:
- ロジックエラー、null/undefined 未処理
- レースコンディション、メモリリーク
- 変数の意図しない上書き、型不一致
- 条件分岐の漏れ、else ブランチの副作用
- 類似名称の関数・変数の取り違え

新たに導入されたバグのみ報告。既存の問題は報告しない。

**敵対的入力逆算（受理入力の端点を末端の制約まで前進させる）**: 受理されうる入力の端点（`''` / 0 / null / undefined / 最大長 / 部分入力の draft）を列挙し、各々を末端の制約（DB カラム型・NOT NULL・CHECK・外部 API・ファイル I/O）まで実際に前進させて、途中の層が値を素通りさせないか検証する。「正常系は通る」で止めず、端点入力が末端で弾かれる／型不整合を起こす経路（例: 空文字が `?? null` を素通りし numeric 列へ INSERT）を探す。value-flow-trace explorer の層マップがあれば起点にする。

**外した防御の来歴（削除・条件変更の hunk に限る / GitHub issue #286）**: diff が条件・ガード・早期 return・例外処理・検証・処理順を**削った、または緩めた** hunk では、その行が入った理由を履歴から読む。過去に特定の失敗を防ぐために入れた防御を、理由を知らずに外す型を狙う。

- 入れたコミットは、削られた行の特徴的な文字列で引く（base の ref を知らなくてよい）: `git log -S'<文字列>' --reverse --format='%h %ad %s' --date=short -- <path>` の先頭がそれ。メッセージと一緒に変えたファイルは `git show --stat <sha>` で見る（本文が要るときだけ `-p`）
- **対象は削除・条件変更の hunk だけ**。追加だけの hunk・言い換えだけの hunk には使わない。1 体あたり 3 hunk まで（探索予算の内側）
- 入れたコミットが「〜で落ちたので」「〜を防ぐ」のように具体的な失敗を説明していて、今回の diff がその失敗を別の形で防いでいなければ指摘する。根拠に、入れたコミット（`<sha>`）と、今回それを外した diff 行を並べる
- 入れた理由が履歴から読めない（メッセージが「refactor」だけ等）なら、推測で指摘を作らない。削った意図が PR 説明・コミットメッセージにあれば intended として扱う（reviewer-common の base 状態の確認）

**拒否条件が重なったときの評価順（拒否・検証の分岐を 2 つ以上足した・変えた diff に限る / GitHub issue #293）**: 早期 return・throw・エラー応答の返却・バリデーションのような拒否の分岐を、同じ入口に 2 つ以上**追加・変更**した diff では、各条件を単独で正しいか見るだけで止めない。条件は 1 つずつ見ると正しくても、2 つが同時に成り立つ入力で、利用者が対処できない側のエラーが先に返ることがある。

- 同時に成り立ちうる条件の組を作り（例: 「対象そのものが作成不可」かつ「選んだ値が見つからない」）、評価順どおりに辿って、どの分岐が先に返るかを `file:line` で書き出す。今回足した分岐と既存の分岐の間の順序も対象にする
- 見るのは、返る順で利用者が正しく対処できるか。対象そのもので決まる拒否（作成不可・権限・状態）が、入力値で決まる拒否（値が見つからない・形式が違う）より後に評価されると、利用者は入力を直しても通らないエラーを見続ける
- 順序が仕様・PR 説明・同じ種類の既存の入口で決まっていれば、それに合っているかで判断する。どの順でも利用者の取る対処が変わらない組は指摘の対象外
- severity は、誤った順序で利用者が取る対処がどれだけ外れるかで決める。先に返るエラーを直せば次のエラーにたどり着けるなら MINOR、直しようのないエラーが返り続けて先に進めないなら MAJOR
- 認可・存在確認が入力検証より後ろに回り、権限の無い利用者に対象の有無が漏れる順序は、本観点ではなくセキュリティの問題として扱い、severity も漏れの影響で決める

**例外・早い return の後ろの後片付け（GitHub issue #353）**: catch で例外を投げ直す経路・早い return・`await` の reject がある関数では、その後ろに置いた後片付け（閉じる・解放・状態を戻す）が `finally` か同等の仕組みに入っているかを見る。`finally` の外に置いた後片付けは、正常系では呼ばれても、投げ直した・return した・reject された経路では呼ばれない。言語・フレームワークを問わない（脱出口を持つ言語すべて。`finally` の無い言語では `defer` などの同等の仕組みに置き換えて読む）。

- 関数の中の脱出口（`throw` / 投げ直し・`return`・reject されうる `await`・throw しうる関数呼び出し（自前のラッパーは呼び先を読んで確かめる））を列挙し、各々から後片付けの行まで辿って、届かない経路を `file:line` で書き出す。diff が足したのが脱出口だけで、飛ばされる後片付けの行が既存のままなら、指摘は足した脱出口の行（`+`）に置き、飛ばされる後片付けの行を根拠に並べる
- 次の経路は対象外: 後片付けが `finally` か同等の仕組み（`defer` / `with` / `using` / try-with-resources / `.finally()` / effect の cleanup / 呼び出し元の `finally`）で保証されている / 脱出口より前に済んでいる / 後片付けする状態を作る前の脱出口（`setPending(true)` より前の guard clause など）/ その経路で後片付けを飛ばすのが意図と読める（失敗時にダイアログを開いたまま残して再試行させる等。正常系や兄弟の catch の経路と比べて判断する）。意図した経路に「`finally` へ移す」修正を勧めると、その UX を壊す
- **意図の判定は脱出口ごとに行う**（catch 単位で決めない）。同じ catch に、失敗時にダイアログを残す `return` と、redirect を投げ直す呼び出しが並ぶことがある。再試行させる意図は、画面が移る脱出口（redirect / notFound / 認証切れの投げ直し）には及ばない — 移った先には再試行する画面が無い
- **フレームワークの制御フローを投げ直す helper を呼ぶ catch の後ろは特に疑う**（Next の `unstable_rethrow` / `redirect` / `notFound` など）。redirect や認証切れの誘導はこの経路を通り、後片付けを飛ばしたまま画面が移る。ルートの Provider にあるダイアログのように画面を移っても消えない状態は、遷移先に残る
- **同じ形が repo の既存コードにあっても、既存の作法として免除しない**。今回の diff が足した・変えた側は指摘し、既存側は根拠の末尾に「同じ形の既存箇所（diff 外・参考）: `file:line`」と 1 行で添える（既存側を別の指摘に立てない。diff が触っていない行は報告対象外という上の原則はそのまま）。この行に「pre-existing」の語を使わない — reviewer-common では diff 側の指摘を 1 段下げた申告の語で、書くと新しく入れた不備が base 由来として降格される
- severity は、後片付けが意図せず飛んだ後に何が残るかで決める。データの不整合が残る（状態を戻す処理・ロールバックが飛ぶ）かサービス全体が止まるなら BLOCKER（下の severity 目安どおり）、漏れが一部の後続の処理を止める（例外の経路でロックを保持したまま・接続プールが枯れて一部の経路が詰まる）なら CRITICAL、利用者の目に見える状態（開いたままのダイアログ・押せないままのボタン・消えない読み込み表示）や後続を止めないリソースの漏れ（購読・タイマー）が残るなら MAJOR、ログ・計測の欠けだけなら MINOR

**severity 目安**:
- BLOCKER: データ損失・データ破壊につながる論理エラー、認可ロジックの根本的な欠陥
- CRITICAL: null 参照で確実に落ちる、無限ループ、race condition でユーザー影響
- MAJOR: エッジケースの未処理、稀な条件での誤動作
- MINOR: 微小な可読性問題・既存コードの揺れ程度
```
