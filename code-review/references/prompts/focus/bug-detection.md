### bug-detection（バグ・ロジックエラー検出）
```
## 観点: バグ・ロジックエラー検出

検出対象:
- ロジックエラー、null/undefined 未処理
- レースコンディション、メモリリーク
- 変数の意図しない上書き、型不一致
- 条件分岐の漏れ、else ブランチの副作用
- 類似名称の関数・変数の取り違え

新たに導入されたバグのみ報告。既存の問題は報告しない。

**敵対的入力逆算（受理入力の端点を末端の制約まで前進させる）**: 受理されうる入力の端点（`''` / 0 / null / undefined / 最大長 / 部分入力の draft）を列挙し、各々を末端の制約（DB カラム型・NOT NULL・CHECK・外部 API・ファイル I/O）まで実際に前進させて、途中の層が値を素通りさせないか検証する。「正常系は通る」で止めず、端点入力が末端で弾かれる／型不整合を起こす経路（例: 空文字が `?? null` を素通りし numeric 列へ INSERT）を探す。value-flow-trace explorer の層マップがあれば起点にする。

**外した防御の来歴（削除・条件変更の hunk に限る / GitHub issue #286）**: diff が条件・ガード・早期 return・例外処理・検証・処理順を**削った、または緩めた** hunk では、その行が入った理由を履歴から読む。過去に特定の失敗を防ぐために入れた防御を、理由を知らずに外す型を狙う。

- 入れたコミットは、削られた行の特徴的な文字列で引く（base の ref を知らなくてよい）: `git log -S'<文字列>' --reverse --format='%h %ad %s' --date=short -- <path>` の先頭がそれ。メッセージと一緒に変えたファイルは `git show --stat <sha>` で見る（本文が要るときだけ `-p`）
- **対象は削除・条件変更の hunk だけ**。追加だけの hunk・言い換えだけの hunk には使わない。1 体あたり 3 hunk まで（探索予算の内側）
- 入れたコミットが「〜で落ちたので」「〜を防ぐ」のように具体的な失敗を説明していて、今回の diff がその失敗を別の形で防いでいなければ指摘する。根拠に、入れたコミット（`<sha>`）と、今回それを外した diff 行を並べる
- 入れた理由が履歴から読めない（メッセージが「refactor」だけ等）なら、推測で指摘を作らない。削った意図が PR 説明・コミットメッセージにあれば intended として扱う（reviewer-common の base 状態の確認）

**severity 目安**:
- BLOCKER: データ損失・データ破壊につながる論理エラー、認可ロジックの根本的な欠陥
- CRITICAL: null 参照で確実に落ちる、無限ループ、race condition でユーザー影響
- MAJOR: エッジケースの未処理、稀な条件での誤動作
- MINOR: 微小な可読性問題・既存コードの揺れ程度
```
