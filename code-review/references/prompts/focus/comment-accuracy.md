```
## 観点: コメント正確性分析

チェック項目:
- コメントの内容が実際のコードと一致しているか
- 関数シグネチャとドキュメントのパラメータ/戻り値の一致
- 陳腐化した参照（リファクタ済みコードへの言及等）
- TODO/FIXME が既に対応済みでないか
- 誤解を招く曖昧な記述
- **メッセージ時制 × 制御フロー照合**: ログ・エラー・例外メッセージの時制/断定が、実際の制御フローの到達状態と一致するか（例:「保存しました」と出すが後続で例外を投げうる / 「削除済み」と言うが削除は条件分岐の先で未実行のパスがある）。メッセージが主張する事後状態とコードが実際に到達する状態のズレは、コメント矛盾と同じく読み手・運用を誤誘導する

- **挙動変更の波及（diff 外 / GitHub issue #269）**: diff が既存の判定・前提・用語を変えたとき（`-` 行にある条件・戻り値・定数・メッセージ）、その判定を**述べている diff 外の記述**が古い前提のまま残っていないか。手順:
  1. `-` と `+` を見比べて、変わった判定・前提・用語を 1 つずつ書き出す（識別子・定数名・特徴的な語）
  2. 書き出した語で、diff の外のコメント・メッセージ定数・案内文言・doc を grep する（`git grep -n -e <語>`。語ごとに 1 回。探索はここで書き出した語に限る）
  3. 古い前提を述べている箇所を指摘する。指摘の file:line は**古い側**、根拠に**変えた側の diff 行**を並べる。冒頭に `[diff 外]` と書く
  - **base 由来として除外しない**: base では正しかった記述が、この diff の変更で誤りになった（PR が作った不備）。`reviewer-common.md`「base 状態の確認」の例外
  - 文言・案内の直し方が、変えた挙動と合わなくなった場合も同じ扱い

**文体（冗長さ・自明さ・what/why）は本観点の担当外。** それらは `comment-polish.md` の 2 観点（正本: `.claude-plugin/lib/comment-rule.md` の COMMENT-RULE 区間）が唯一の担当で、severity を持たない別枠経路に出る。ここで扱うのは「コメントが実装について**嘘をついている**」ケースだけ。

**severity 目安**:
- MAJOR: コメントが実装と矛盾し、読み手を誤誘導するレベル
- MINOR: 古い参照・陳腐化した TODO/FIXME / 波及で古くなった diff 外のコメント（読み手が古い前提で判断する経路を file:line まで書けるときは MAJOR）
```
