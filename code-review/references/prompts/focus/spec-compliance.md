## 観点: 仕様整合性チェック

以下の仕様ドキュメントと diff の整合性を検証する:
- session-context.md（設計判断、スコープ定義）
- Issue ファイル（要件定義、受入条件）
- knowledge ファイル（ドメイン知識、技術的制約）
- 呼び出し側が渡した仕様ファイル（self-review の `--spec`。BDD spec.md なら Scenario / Examples / 同値分割表を受入条件として読む。design doc なら採用案と設計判断）
- repo の仕様書（plan が見つけて渡す。`repo-spec-touched` = diff が触った文書、`repo-spec-ref` = session-context・Issue ファイル・PR 本文が言及した文書。受入条件・未決事項の表・「新しく決まったこと」の節を照合元にする。PR に紐づく GitHub Issue の本文が言及した文書は plan の対象外なので、Issue の本文に仕様書のパスがあれば自分で Read して照合元に足す）

検出対象:
- 仕様で定義された要件の実装漏れ
- スコープ外の変更（仕様にない機能の追加）
- 設計判断との矛盾（仕様では A と決めたが B を実装）
- knowledge に記載された制約の違反
- repo の仕様書が渡された回は、下の文書整合の規則（決定の未反映・同じ節の古い説明・文書と実装の食い違い）も見る。`repo-spec-touched` の文書は、変更した行の節を節ごと Read する（変更行だけ読むと周りの古い文が見えない）

**決めたことが文書に入っているか**（照合元の文書がある回だけ見る）:

1. **決定の未反映**: Issue（本文とコメント）・PR 本文・session-context・このセッションで決めた挙動が、それを書くべき文書の節に無い。足りない決定を 1 文で示し、足す先の見出しを挙げる
2. **同じ節の古い説明**: 変更した行と同じ節（直前の見出しから、同じか上のレベルの次の見出しまで）に、変更後の内容と矛盾する説明が残っている。1 行だけ直して周りの文が古いまま、の型。矛盾する行を引用する
3. **文書と実装の食い違い**: 文書が述べる挙動（受入条件・規約・例外の列挙）が、diff の後のコードと違う。どちらの画面・経路・条件の話かが書かれておらず、別の実装と食い違って読める記述もここに入れる

**書き方**:

4. 各指摘に、文書の file:line と該当行をそのまま引用する。実装・決定の側も出典（file:line・Issue / PR のどの記述か）を添える
5. 旧の振る舞いを出典付きで書いた節（経緯・履歴・移行前の挙動・ADR の決定記録・CHANGELOG）は、今の実装と違っていても食い違いとして数えない。直し方は、その節を書き換えず「新しく決めたこと」に当たる節へ足す形にする（その節が無ければ、作る位置を示す）

**doc-substance との境界**: 同じ節の中の矛盾（上の 2）はこの観点、変えた節と同じ文書の変えていない節の矛盾は doc-substance の担当。同じ行に両方の観点で指摘を立てない

**仕様の行を引用する（必須）**: 各指摘に、照合元の仕様の file:line と該当行（受入条件・Scenario・設計判断の文）をそのまま引用する。反証レイヤーと人間がその場で照合できるようにするため。

confidence の目安:
- 仕様の行を引用でき、diff の hunk と突き合わせて食い違いを示せる指摘（要件の実装漏れ・スコープ逸脱・設計判断との矛盾のどれでも）: **95 まで付けてよい**。スコープ逸脱と設計判断との矛盾は MAJOR で、報告マトリクスは MAJOR に 95 以上を求めるので、根拠が揃っているのに 70〜80 に置くと本文に出ない
- スコープ逸脱で、仕様がスコープを明記している行（対象外の列挙・範囲の定義）を引用できず「仕様に書かれていない」ことしか示せないもの、または仕様の記述が曖昧で解釈が割れるもの: 80 を上限にする（本文に出なかった分は 🔁 付録に残る）

**契約の前提は呼び出し側で実地検証せよ**（整合性の罠の昇格）: 仕様・型・スキーマが宣言する前提（例:「この列は非 null」「この値は検証済み」）を、宣言と他記述の整合だけで確認したことにしない。**その前提に依存する呼び出し側・末端の永続層まで実際に値を辿り、前提が本当に保証されているかを裏取りする**。複数箇所が同じ前提で書かれていても、前提自体が誤っていれば全部誤り（`### 事実主張のツール接地` の「整合性の罠」参照）。一貫性の確認は正しさの確認の代用にならない。

**severity 目安**:
- CRITICAL: 受入条件を満たさない実装、明確な要件違反
- MAJOR: スコープ逸脱（仕様にない機能追加）、設計判断との矛盾
- MINOR: knowledge との軽微な相違
- 文書整合（決定の未反映・同じ節の古い説明・文書と実装の食い違い）: 受入条件・規約の例外の列挙と実装が食い違うものは CRITICAL、それ以外は MAJOR。文書の行と、決定・実装の出典の両方を引用できれば confidence は 95 まで付けてよい

**注**: spec-compliance での仕様違反判定は `[intent-conflict]` タグの減算対象外（scoring-guide.md 参照）。
