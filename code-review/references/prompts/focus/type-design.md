### type-design（型設計分析）
```
## 観点: 型設計分析

分析軸（各 1-10 で評価）:
- カプセル化: 内部実装の隠蔽、外部からの不変条件違反の防止
- 不変条件の表現: 型構造による制約の明確さ、コンパイル時保証
- 不変条件の有用性: 実際のバグ防止、ビジネス要件との整合性
- 不変条件の強制: コンストラクタでの検証、ミュータブル操作のガード

フラグすべきアンチパターン:
- 振る舞いのない anemic domain model
- ミュータブルな内部状態の露出
- ドキュメントでのみ強制される不変条件
- 外部コードに依存する不変条件の維持

名前と中身の一致（GitHub issue #269）:
- 新規・変更した型・フィールド・プロパティの名前が、**持つ値・判定の範囲・実際の読み手**と合っているか。合わなければ改名案を出す
  - 過大: 中身より多くを主張する（「読み替えを受け付けるかの可否」だけを持つのに、読み替えそのものに読める名前 / 一部の状態だけを見るのに、全体のゲートに読める名前）
  - 用途の消失: 挙動の変更で読み手がいなくなったのに「表示用」等の用途を名乗り続ける（読み手は grep で確かめる）
- 根拠は「名前の箇所」と「中身・読み手を決めている箇所」の file:line ×2 で示す。リポジトリ固有の命名規約（接尾辞等）は claude-md-compliance の範囲なので扱わない

**severity 目安**:
- CRITICAL: 外部から不変条件を破壊できる設計（実害ありえる）
- MAJOR: ミュータブル状態露出・ドキュメントのみの制約
- MINOR: 設計改善提案レベル / 名前と中身のずれ（実行時の挙動は変えないので既定は MINOR。名前を信じた読み手が誤った値を使う経路を file:line まで書けるときだけ MAJOR）
```
