### claude-md-compliance（CLAUDE.md 準拠チェック）
```
## 観点: CLAUDE.md 準拠チェック

対象:
- CLAUDE.md に明示されたルール
- コーディング規約（ESLint 設定、Prettier 設定等）
- import/export パターン、命名規則
- エラーハンドリング方針、テスト方針
- repo 直下の `CONTRIBUTING.md` / `CODING_STANDARDS.md`（あれば読む。CLAUDE.md と同じ扱いの規約ソースにする。無ければ探さない）

CLAUDE.md に明示的に記載のあるルール違反は confidence >= 80。
暗黙のルール違反は confidence <= 50。

**帰結まで接続する（パターンの有無で止めない）**: 「規約パターンが存在するか」でなく「その機構が実際に呼ばれ・期待した帰結を生むか」まで見る。共有機構（共通エラーハンドラ・ロガー・バリデータ等）を import・言及していても、ある経路がそれを迂回して独自実装で握りつぶしていれば違反（観測性の欠落・規約の空洞化という帰結が生じる）。`instanceof AppError` のようなパターン一致を「準拠」と即断せず、無条件ラップ等の規約が**全経路で満たされるか**を確認する。準拠と判定するときも、その帰結（機構が実際に効いていること）を接続してから PASS する。

**層の規約との照合（行ではなく、ファイルの置き場所と判断の所在で見る）**: 注入された AGENTS.md / CLAUDE.md が層（ディレクトリ）ごとの役割を定めているときだけ行う。層の役割が文書化されていなければこの節は飛ばす（規約に無い層の区分を推測で作らない）。diff の行を規約と照らすだけでは、次の 3 つが抜ける:

1. **置き場所**: 変更したファイルごとに、ファイル全体の中身を、そのディレクトリの層の規約（例: 「usecase/ は 1 ファイル = 1 行為」「純粋なドメインロジックは Domain Service に置く」）と照合する。足した行が規約に沿って書かれていても、ファイルそのものが層の役割に合っていなければ違反になる。指摘は PR が足した行（層の役割に合わない中身を足した箇所）に付け、同じ形の PR 前からの中身は理由欄に件数だけ添える。`+` に無い行を単独で指摘しない原則（reviewer-common「base 状態の確認」）は変えない
2. **判断の持ち場**: 変更した関数が行う判断が、その層の関心事か。特に表示層（FE）が、server から受け取った値に無い情報（「押せない理由」など）を推測して決め打ちしていないかを見る。受け取る型（DTO / レスポンス型）が diff の外にあっても Read し、判断に要る情報が届いているかを確かめる（diff 外 Read の予算内で）
3. **層をまたぐ重複**: 同じ判定・同じ文言が層をまたいで 2 か所にあるときは、「一致を保証するテストを足す」ではなく「どちらの層が持つべきか」として出す。推奨欄には持つべき層と、もう一方の層が受け取る形（レスポンスへのフィールド追加など）を書く

confidence: 置き場所（1）は、層の規約が明文で定めていれば明示ルール扱い（80 以上）。判断の持ち場（2）と重複（3）は、個別の状況まで規約に書かれていないことが多い。層の役割の記述を典拠として引用できれば 60-75、引用できなければ暗黙のルール扱い（50 以下）。

severity: 置き場所（1）は実行時の挙動を変えないので、「禁止」「必須」と明記された規約でも **MINOR が既定**（reviewer-common「カテゴリの取り違え」。下の CRITICAL 目安の対象外）。判断の持ち場（2）と重複（3）は、片方の層だけが変わったとき（server 側で判定条件や理由が増えた等）にどの経路で表示や判定が食い違うかを `file:line` まで書ければ MAJOR、書けなければ MINOR。

**severity 目安**:
- CRITICAL: CLAUDE.md で「禁止」「必須」と明記されたルールの違反
- MAJOR: CLAUDE.md 推奨パターンからの大きな逸脱
- MINOR: 命名規則・スタイル系の軽微な揺れ
```
