## 観点: 層の責務

書かれた中身が、そのディレクトリ（層）の役割に合っているかを見る。diff の行を規約と照らす claude-md-compliance とは単位が違う — ここでは**ファイルの置き場所**と**判断がどの層にあるか**で見る。lint が通っても層の役割は守られていないことがある。

### 手順 0: 層の地図を作る（最初に 1 回）

注入された AGENTS.md / CLAUDE.md（`## agents-md`）から、層（ディレクトリ）ごとの役割・置いてよいもの・依存方向・import 境界を抜き出し、変更ファイルをそれぞれどの層に属するかへ割り当てる。

- **規約を緩める・具体化する文書も読む**: 変更ファイルの近くにある設計書・ADR（`docs/` / `design*/` / `adr/` / feature ディレクトリ直下の README 等）が層の規約に例外や細則（「usecase/ 直下に部品を置いてよい」等）を定めていれば、その文書が優先する。読まずに AGENTS.md の原則だけで違反と判定しない
- **既存の前例を 1 回だけ確かめる**: 同じ層の既存ファイルが同じ形をとっていれば、規約の読み違いの可能性がある。前例が多数あるなら、違反と判定する前に上の細則を探す
- 層の役割がどこにも文書化されていなければ、ここで終える（規約に無い層の区分を推測で作らない）。`## 総括` に「層の規約が文書化されていないため対象外」と 1 行書く

### 見るもの（3 つ）

1. **置き場所**: 変更したファイルごとに、ファイル全体の中身を、その層の規約（例: 「usecase/ は 1 ファイル = 1 行為」「純粋なドメインロジックは Domain Service に置く」「scripts/ に寄せ、SKILL 本文に書き下ろさない」）と照合する。足した行が規約どおりに書かれていても、ファイルそのものが層の役割に合っていなければ違反になる。指摘は PR が足した行（層の役割に合わない中身を足した箇所）に付け、同じ形の PR 前からの中身は理由欄に件数だけ添える。`+` に無い行を単独で指摘しない原則（reviewer-common「base 状態の確認」）は変えない

2. **判断の持ち場（両方向から見る）**: 判断（可否・状態の分類・理由の決定）がどの層にあり、それがその層の関心事かを見る。
   - **受け取る側から**: 表示層（FE）や呼び出し側が、受け取った値に無い情報（「押せない理由」など）を推測して決め打ちしていないか
   - **渡す側から**: 変更した判断（server / Domain Service / UseCase の分岐・拒否・受付判定）ごとに、その結果と理由が**レスポンス型（DTO）に載っているか**を確かめる。載っていなければ、呼び出し側（今ある画面・これから作る画面）は判断を作り直すしかない。**いま推測している呼び出し元が無くても指摘する** — 推測するしかない形を DTO が決めている
   - 受け取る型（DTO / レスポンス型）が diff の外にあっても Read する。判断の分岐を列挙し、DTO のフィールドと 1 つずつ突き合わせる

3. **層をまたぐ重複**: diff が足した・変えた判定（述語・条件式・定数・エラー文言）ごとに、**同じ判定が別の層にもないかを Grep で探す**（述語名・比較している値・文言リテラル・enum の分岐で引く）。次の形を拾う:
   - 同じ判定が 2 つの層にある（Domain Service の述語と UseCase の `if` / server と FE の文言）
   - 同じ概念の求め方が層ごとに違う（「子を持つか」を画面側と作成処理で別の方法で求めている）
   - 一方の層の分岐が、もう一方の層が先に弾くために本番で一度も通らない（通らない分岐は重複の証拠）

   「一致を保証するテストを足す」ではなく「どちらの層が持つべきか」として出す。推奨欄には持つべき層と、もう一方の層が受け取る形（レスポンスへのフィールド追加など）を書く

### 探索の配分

探索予算（reviewer-common）の diff 外 Read は、**DTO / レスポンス型 → 層の細則を定めた設計書 → 重複の相手先**の順に使う。重複の探索は Grep で当たりを付け、Read は相手先の該当範囲だけにする。予算内で見られなかった判断・重複の相手は `## unmet_information` に `予算切れ: <対象>` と書く。

### confidence / severity

confidence: 置き場所（1）は、層の規約（または細則）が明文で定めていれば明示ルール扱い（80 以上）。判断の持ち場（2）と重複（3）は、個別の状況まで規約に書かれていないことが多い。層の役割の記述を典拠として引用できれば 60-75、引用できなければ 50 以下。細則を探したが見つからなかった置き場所の違反は、その旨を理由欄に書く。

severity: 置き場所（1）は実行時の挙動を変えないので、「禁止」「必須」と明記された規約でも **MINOR が既定**（reviewer-common「カテゴリの取り違え」）。判断の持ち場（2）と重複（3）は、片方の層だけが変わったとき（server 側で判定条件や理由が増えた等）にどの経路で表示や判定が食い違うかを `file:line` まで書ければ MAJOR、書けなければ MINOR。通らない分岐（3 の 3 つ目）は、通らないことを `file:line` の先行判定で示せれば MAJOR。

**severity 目安**:
- MAJOR: 判断が DTO に載らず呼び出し側が作り直すしかない / 層をまたぐ重複で、片方だけの変更による食い違いの経路を示せる
- MINOR: 置き場所の規約違反 / 経路を示せない持ち場・重複
