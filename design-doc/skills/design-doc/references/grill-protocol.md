# Grill プロトコル

コミット（実装・設計確定）の前に、プランや設計を **1 問ずつ容赦なく質問して詰める**ための対話規範。Frederick Brooks『The Design of Design』の design tree（コードに落とす前に設計木の全分岐を歩く）と、Matt Pocock の "grill-me" skill に由来する。

> 狙い: plan mode が「共通理解の前にプラン文書を吐く」問題を防ぐ。一括の質問リストではなく、design tree の依存を 1 分岐ずつ解きほぐして合意に到達する。

---

## 3 原則

### ① コードで答えられる問いは聞かない

質問候補のうち、コードベースや既存成果物で答えが出るものは **自分で調べて解決し、質問リストから落とす**。

- 調べ先: codebase exploration の結果 / `Grep` / `Glob` / 既存の BDD spec / Issue context / ADR / knowledge
- 落とした問いは「調査で確定した前提」として最後に提示する（黙って仮定しない）
- ユーザーの時間は「コードを読めば分かること」ではなく「ユーザーしか知らない意図・優先順位」に使う

### ② 1 問ずつ、依存順に

残った問いを **design tree の依存順**（上流の決定が下流を制約する順）に並べ、1 問ずつ確認する。

- 上流の問いを先に解くと、下流の問いが消える / 選択肢が絞られることが多い
- 各回答のあと、残りの問いを再評価する: 前の答えで解消・変形した問いは畳み、新たに見えた分岐は挿入する
- 一括リストはこの依存構造を潰してしまう（だから使わない）

### ③ 各問いに推奨回答を添える

各質問には必ず **推奨案を先頭に置き `(Recommended)` を付け**、1 行で理由を添える。

- `AskUserQuestion` の最初の option を推奨案にする（リポジトリの AskUserQuestion 規約に整合）
- ユーザーが「おまかせ」と言えば推奨案で確定して進む
- 推奨があることで「説明を読んで考える」コストが減り、grill が速く進む

---

## 過剰質問を避ける（proportionality）

grill は relentless だが、無意味な質問の量産ではない。次のときは圧縮してよい:

- 残った問いが 1〜2 個かつ方向性が明確 → 1 回の提示にまとめる
- 影響が小さく後から安全に変えられる判断 → 推奨で進めて確認を 1 行添えるだけにする

「コードで答えられる問いは聞かない（原則①）」と並ぶ、grill の自己抑制ルール。writing-polish の over-correction 抑制と同じ思想。
