# セクションガイド（書き方とアンチパターン）

design doc 10 セクションの書き方規範。template.md の各セクションを埋めるときに適用する。

## 1. TL;DR

3 行以内。「何を・どう解くか」。背景説明や経緯は書かない（次セクションの仕事）。

❌ 「本ドキュメントでは〜について検討した結果を記述する」（メタ説明はノイズ）
✅ 「決済リトライを Pub/Sub からジョブテーブル方式に変える。可視性タイムアウトと重複実行の問題を解消する」

## 2. 背景 / 課題

なぜ今この設計が必要か。**観察可能な事実**（障害件数・性能値・コード上の制約）で書く。

❌ 「現状の実装には課題が多い」（曖昧。何がどう困るのか不明）
✅ 「リトライ中の重複実行が直近 30 日で 4 件。原因は ack タイミングとジョブ完了の不一致」

## 3. ゴール / 非ゴール

非ゴールには**やらない理由を 1 行**添える。スコープ外の明記が後続の grill とレビューを軽くする。

❌ 非ゴールが空（「全部やる」と読まれ、レビューで無限に広がる）

## 4. 確定した前提

grill で自己解決した事実とユーザー確定事項。**出典必須**（ファイルパス・ADR id・回答日）。

❌ 「認証は既存方式を使う想定」（仮定なのか確定なのか不明）
✅ 「認証は session cookie 方式（`src/auth/session.ts:42` で確認、ADR-20260301120000 で決定済み）」

## 5. 採用案

実装者が迷わない粒度: アーキテクチャ → データフロー → 変更対象ファイル一覧 → 移行手順。
「なぜこの案か」はここに書かない（代替案の比較表に委ねる。重複は乖離の温床）。

## 6. 検討した代替案

比較表の観点はテーマに合わせて選ぶ（変更量 / 複雑性 / 拡張性 / リスク / 運用コスト等）。
各案に「採用しなかった理由」を 1 行。**比較していない案を後から聞かれるのが design doc の最頻レビュー指摘**なので、検討して捨てた案は短くても残す。

## 7. 設計判断ログ

doc 内で下した個々の判断を 1 行ずつ。**全行にマーカー必須**:

- `[→ADR候補]` — プロジェクト全体に効く決定（他の機能・将来の設計を拘束する）。adr-keeper への切り出し対象
- `[local]` — この設計の中でだけ意味を持つ判断

仕分けの問い: 「この決定は、この doc を読まない人の作業も拘束するか？」 YES → `[→ADR候補]`

## 8. 未解決事項 (open)

issue-design の open ルールと同じ。各 open に必ず:

1. `(a)(b)(c)` の選択肢 + pros/cons（インライン圧縮形式: `— Pros: … / Cons: …`）
2. **現時点の方向性**（有力案 + 理由。「未定」で止めない）
3. **確定タイミング**（いつ・どこで確定するか。「要検討」は禁止）

❌ 「キャッシュ戦略は要検討」
✅ 「キャッシュ戦略: (a) TTL — Pros: 単純 / Cons: 整合ラグ (b) イベント無効化 — Pros: 即時 / Cons: 実装重い。現時点では (a) が有力（要件は 5 分ラグ許容）。確定タイミング: 負荷試験後」

## 9. 実装ブリッジ (Implementation Bridge)

**必須・空欄禁止**。design doc の死に方は「書いたが実装に接続されず腐る」こと。ADR の Enforcement（機械強制の検討必須）に相当する欄。

必ず埋める 3 点:

1. **実装着手の単位**: Issue 分解案（タイトル列挙）または `/feature-dev <要約> spec=<path>` のコピペ可能な起動引数
2. **検証方法**: 実装とこの doc の一致をどう確認するか
3. **実装完了時の doc 更新手順**: `phase: target → current` + 乖離時の追記 or supersede

書けない場合は**理由と確定タイミング**を残す（例: 「PoC 未了のため Issue 分解不能。確定タイミング: PoC 後」）。

❌ 「実装は別途検討」（接続情報ゼロ。この doc は高確率で腐る）

## 10. 関連

Issue / spec.md / ADR / 他 design doc への相対パスリンク。双方向にする（ADR 切り出し時は ADR 側にも doc パスを書く）。

---

## 全体のアンチパターン

- **HOW に WHAT を混ぜる**: 振る舞い仕様（Scenario）を design doc に書き始めたら bdd-spec の領分。spec.md へのリンクに置き換える
- **採用案だけ書いて代替案ゼロ**: 比較がない doc は「検討した」証拠にならない。最低 1 つは捨て案を残す
- **frontmatter の更新忘れ**: 本文を改訂したら `last-validated` を更新する。doc-freshness の stale 検出が機能しなくなる
- **巨大化**: 1 doc 1 テーマ。複数テーマが混ざり始めたら「別 doc + 関連リンク」に分割する（naming.md の判断基準）
