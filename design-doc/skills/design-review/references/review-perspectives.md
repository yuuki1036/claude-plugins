# レビュー視点定義（正本）

design-review の 4 視点とチェックリスト。design-reviewer agent に 1 視点ずつ割り当てる。feature-dev の multi-architect（minimal / clean / pragmatic の視点分散）を doc 静的レビューに転用し、risk を加えた構成。

## minimal — 過剰設計の検出

「この設計、もっと小さくできないか」を問う視点。

- 採用案に**現時点の要件が要求していない**汎用化・抽象化・設定可能性はないか（YAGNI）
- 代替案比較で「単純だが要件は満たす案」が不当に低く評価されていないか
- 新規コンポーネント・新規依存のうち、既存の仕組みの再利用で消せるものはないか
- 移行手順は段階化しすぎ / 一括すぎないか（変更量に対して妥当か）
- ゴール / 非ゴールに対して採用案のスコープが膨らんでいないか

## clean — 構造・責務の検証

「この構造は変更に耐えるか」を問う視点。

- コンポーネントの責務分離は明確か。1 コンポーネントに複数の変更理由が同居していないか
- データフローに循環・暗黙の共有状態・双方向依存はないか
- 既存コードベースの規約・レイヤ構造・命名パターンと整合しているか（裏取り必須）
- 拡張が予見される箇所（open に挙がっている分岐など）の変更コストは妥当か
- インターフェイス境界は実装詳細を漏らしていないか

## pragmatic — 実装可能性・運用の検証

「この設計はそのまま実装に降ろせるか」を問う視点。

- 「確定した前提」のコード由来の主張は実際のコードと一致するか（最重要の裏取り対象）
- 変更対象ファイル一覧は網羅的か。漏れている呼び出し元・設定・マイグレーションはないか
- 移行手順は現実的か（ダウンタイム・後方互換・ロールバック手順）
- 実装ブリッジの Issue 分解 / feature-dev 起動引数は実際に着手可能な粒度か
- 運用負荷（監視・デバッグ・障害時の切り分け）が考慮されているか

## risk — 障害モード・見落とし制約の検出

「この設計はどう壊れるか」を問う視点。

- 失敗パス: 部分的失敗・タイムアウト・重複実行・順序逆転時の挙動が定義されているか
- データ整合性: 移行中・ロールバック時にデータが壊れる経路はないか
- セキュリティ: 信頼境界の変更・新しい入力経路・権限の拡大はないか
- 暗黙の前提: 負荷特性・外部サービスの SLA・同時実行数など、検証されていない環境前提はないか
- 検討した代替案の「捨てた理由」が将来の制約変化で復活しうる場合、その条件が open に残っているか

---

## effort 別の視点構成（design-review Phase 2 が参照）

| 実行時 effort | 構成 | 視点 |
|---|---|---|
| `low` / `medium` | agent なし。メインコンテキストで順次適用 | minimal + risk |
| `high` | design-reviewer agent ×3 並列 | minimal / pragmatic / risk |
| `xhigh` / `max` | design-reviewer agent ×4 並列 | 全 4 視点 |

- 低 effort で minimal + risk を選ぶ理由: 設計レビューの 2 大事故は「過剰設計の通過」と「障害モードの見落とし」。構造の美しさ（clean）と実装詳細の裏取り（pragmatic）は実装フェーズでも検出機会がある
- ユーザーが `--focus <視点>` を指定した場合は effort に関わらずその視点のみ実行する
