# SSoT pin（正本 → 消費サイトの伝播を強制する）

doc が実行手順そのものになるプラグインでは、consumer が別の doc なので**正本を直しても
伝播漏れが見えにくい**（code-review v2.63.0 のセルフレビューで検出した欠陥 11 件中 6 件が
この型だった）。

CLAUDE.md には規範だけを置き、記法と運用の詳細はここに集約する。
設計判断（なぜマーカー同期でなく pin か）: `.claude/adr/20260813223000-ssot-pin-over-marker-sync.md`。

## 何を強制するか

**内容の一致ではなく、「正本が変わったら消費サイトを確認して pin を打ち直す」手順**を強制する。
言い換え・要約で複製されている関係は一致比較にできないので、ハッシュのずれを
「確認しろ」の合図として使う。

> `routing-axes` の同期は「**同一テキストであること自体が仕様**」の関係を扱う別の仕組み。
> 両者は併存する（あちらは dedent 比較、こちらはハッシュ突合）。

## 記法

消費サイトの**冒頭**に置く:

```
<!-- SSOT: <repo ルート相対の md パス>#<見出し前方一致 anchor> @<hash8> -->
```

`validate_plugin_quality.py` の `check_ssot_pins` が正本の該当節をハッシュして突合し、
ずれていれば Critical。

## 打ち直し

```bash
python3 .claude-plugin/scripts/validate_plugin_quality.py --update-ssot-pins
```

**明示操作**。pre-commit では自動更新しない（自動化すると確認の強制力が消える）。
**repo 全体の pin を一括で打ち直す**ので、**全消費サイトを確認してから**使う。

## 落とし穴

- **新規 pin は hash を手計算しない**。`@00000000` のダミーで宣言し `--update-ssot-pins` で
  確定させる（初期値も検証も同じ切り出しを通るので、これが正規経路）。確定は版上げ（`bump-version.sh`）の**後に**行う。`vNEXT` の解決で正本の節の digest が変わることがある
- **hash は 8 桁の小文字 hex**。外すと `pin 記法が不正で検証されない` の Critical になる
  （黙って無効化はしない）
- **pin 宣言はファイル冒頭＝最初の見出しより前**に置く。pin した節の中に pin があると
  打ち直しが収束せず、これも Critical
- **doc に記法例を書くときはフェンスか行内コードに入れる**（生きた pin として拾われない）
- **正本・消費サイトとも md のみ対応**。スクリプトを正本にはできず、非 md に pin を書いても
  警告なく無効化される
- **節の区切りは見出しレベルで決まる**ので `#8` は同レベルの `## 8.5` を含まない（別 pin を打つ）。
  anchor `8` は `## 8.5` に吸着せず、一致が 2 件以上なら曖昧として Critical

## pin を置くかの判定（言い換えか、指しているだけか）

pin が守るのは**正本の節の中身を自分の文で書いている箇所**。正本が変わるとその文が古くなるので、打ち直しの対象に上げる。

- **置く**: 節の規則・契約・値を本文で言い換えている。1 行でも、出典の括弧（`orchestration-guide.md` の `## 3.5` など）が付いていても同じ。
  例: 「diff は reviewer へパスで渡す（本文を転記しない。`## 3.5`）」は `## 3.5` の規則を言い換えている。
  例: 「`pre_adjust_counts` に閾値未満の件数を足し、`schema` はスクリプトが入れるので書かない（`## 16`）」は、`## 16` の payload 契約を言い換えている
- **置かない**: 節を指しているだけで中身を書いていない（「→ `## 4`」「正本: `## 13.1`」「`## 6` の手順に従う」）。
  正本が変わっても、指す先が残っている限りその文は古くならない
- **その節の pin は置かない**: 書いている規則の正本が別の doc にある。同じ語が出てきても、その節の言い換えとは数えない。
  例: 動的ラウンドの meta-reviewer と反証を同じメッセージで発行する手順は、`orchestration-dynamic-rounds.md` と `triage-dynamic-gates.md` が正本。一括発行の一般則（`orchestration-guide.md` の `## 0`）の言い換えではない。
  別の doc の節を言い換えているなら、その節の pin を検討する

迷ったら置く側に倒す。置きすぎても、正本が変わったときに確認するファイルが増えるだけで済む。置き漏らすと、古い言い換えがそのまま残る。

## SKILL.md を分けるとき（Step / phase ごとのファイルに）

分ける前の SKILL.md の冒頭の pin は、SKILL.md 全体を守っていた。どの Step の言い換えも、正本が変わったときの確認の範囲に入っていた。分けた後は、pin を持つファイルだけが確認の範囲に入る。

- **分ける前の pin の節ごとに、その節を言い換えているファイルのすべてに pin を置く**。最もよく要約している 1 本だけに移さない。判定は上の節に従う
- 洗い出しは、分けたファイルの本文で pin の正本のパスを grep し、引いている節を 1 件ずつ上の基準で判定する。言い換えには出典が付いていないことや、別の doc を出典に挙げていることもある。そのため、正本の節が定める値や識別子（`skip_reason` の語彙・フィールド名など）でも grep し、それでも拾えなかった箇所は通読で見る
- 指しているだけのファイルには置かない（分ける前の pin が SKILL.md 全体に掛かっていたことは、配る理由にならない）
- 新しく置く pin の書き方と確定の順は「落とし穴」の新規 pin の項に従う
- 実例: review と self-review を分けたときは、最もよく要約している Step のファイルにだけ pin を移した。そのため `## 3.5` と `## 16` を言い換えている 19 ファイルが、確認の範囲から外れていた（GitHub #473）。うち 10 本（動的ラウンドと Phase 0 の Step）は出典に別の doc を挙げたまま `## 16` の `skip_reason` の語彙や扱いを書いており、正本のパスの grep では拾えなかった

## 適用範囲

code-review・feature-dev・issue-workflow・dev-workflow・design-doc の md。引くときは行頭に限って md だけを grep する（`git grep -l '^<!-- SSOT:' -- '*.md'`）。行頭に限らないと、テストや CLAUDE.md・ADR の行内コードに書いた記法の例も当たる。行頭に限っても、この doc の「記法」の節の例が 1 件残る（フェンスの中なので `check_ssot_pins` は数えない）
