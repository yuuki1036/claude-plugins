# ルール配置の意思決定（決定的 hook > LLM 判定）

新しいルール・制約を追加するときは、以下の優先順位で配置先を決める。決定的機械検証（lint/型/テスト/hook）は LLM 判定より ROI が高い（Thoughtworks Harness Engineering 参照）。Hook の遵守率 100% に対し CLAUDE.md は ~80% にとどまる前提で判断する。

## 意思決定フロー

```
ルールを追加したい
  │
  ▼
① 決定的検証で判定可能か？（文字列・ファイル存在・JSON スキーマ・exit code 等）
  ├─ YES → Hook（PreToolUse/PostToolUse/Stop 等）で強制する
  └─ NO  ↓
  ▼
② 文脈判断・自然言語理解が必要か？（コードレビュー・意図推定・要約等）
  ├─ YES → Skill（呼び出しタイミング明示）または Agent（自律実行）
  └─ NO  ↓
  ▼
③ 恒常的に参照したい規約・背景情報か？
  └─ CLAUDE.md（プロジェクト全体）or skill の references/（局所的）
```

## 配置先の判定表

| 特性 | Hook | Skill / Agent | CLAUDE.md |
|------|------|---------------|-----------|
| 遵守率 | 100%（決定的） | ~90%（呼び出せば確実） | ~80%（読み落としあり） |
| 自然言語判定 | 不可 | 可 | 可 |
| セッション外で強制 | 可 | 不可 | 不可 |
| 具体例・背景説明 | 不向き | 向く | 向く |
| 変更コスト | 中（スクリプト編集） | 中（SKILL.md 編集） | 低（文章修正） |
| 代表例 | バージョンバンプ忘れ検知 / 禁止コマンド遮断 | セルフレビュー / Issue 作成 | 命名規約 / 言語設定 |

## CLAUDE.md → Hook 昇格の判断基準

CLAUDE.md に書いたルールが守られていない事象が以下いずれかに該当したら、Hook 昇格を検討する。

- 同じ違反が 2 回以上発生している（履歴・コミットログから確認）
- 違反した場合の修復コストが高い（後から辿ると手戻りが大きい、データ損失、外部影響）
- 判定ロジックがルールベースで表現可能（if/grep/diff で書ける）

逆に、以下に該当する場合は CLAUDE.md / Skill に留める。

- 文脈依存で例外が多い（「基本は X、ただし Y のときは Z」）
- 違反してもリカバリが容易
- 判定に自然言語理解が必要
- **判定対象が時間とともに変わる**（執筆時点では正しく、検査時点では正しくない）。hook は書き込み時に走るので作業ツリーの現在値しか見えず、「書いた時点で正しかったか」は原理的に判定できない

## 昇格を決める前に発火数を測る

`if`/`grep`/`diff` で書けることと、**偽陽性なく書けること**は別。新しい検査を hook / lint に足す前に、既存のリポジトリ（実物の corpus）で発火数と真陽性数を数えること。真陽性ゼロの警告は「⚠️ が出たときだけ行動する」契約を壊し、既存の全警告の信頼度を下げるので、入れない方がまし。

実測して却下した事例:

| 検査案 | 実測 | 記録 |
|---|---|---|
| 公開記録（issue 本文）の典拠パス実在検証 | 5 述語すべて真陽性 0 / 発火率 19〜86% | `.claude/adr/20260817120000-citation-guard-not-mechanizable.md` |
| 版ラベルの追随漏れ検出 | 6/6 偽陽性 | `code-review/references/design-notes/pending-optimizations.md` `## 9` |
| 未リリース版を参照している行の検出 | 429 件中 147 件（34%）が偽陽性 | 同上 |

## 判定基準の持ち主は 1 つ（数えるのはツール）

数える・閾値と比べる・照合する判定は、LLM に読ませる散文ではなくスクリプトに置く。そのうえで、1 つの判定基準の実装は 1 か所だけにする。同じ検査を複数の場所（hook・skill・別のスクリプト）から呼ぶのはよいが、独立に書いた 2 つ目の実装は欠陥として扱う。基準が散らばると、1 か所を直しても残りが古い値のまま食い違う。5 プラグインの CHANGELOG の修正 360 件のうち 85 件（23.6%）が判定基準の誤りだった（`docs/session-reports/2026-11-08-aidlc-v2-evaluation.md`）。

実例: scope_size の上限と判定は hook・issue-maintain・retrospective・散文 3 か所に別々の値で書かれていて、同じ Issue（small・タスク 4 個）が hook では警告され、issue-maintain では警告されず、retrospective では「適正」になっていた。判定を `issue-workflow/scripts/scope-size.py` 1 本に寄せ、各所はそれを呼んで結果だけを使う形にした（#425）。

- **判定はスクリプトに置き、消費側は呼ぶだけにする**: SKILL.md には呼び出しの 1 行と出力の読み方だけを書く。LLM にチェックリストを数えさせない（数え間違いと、手順ごとの数え方の揺れが起きる）
- **散文に値を書き写さない**: 「上限は `scope-size.py limits`」のように正本を指す。SSoT pin は md から md への関係専用で、スクリプトを正本にできない（`docs/ssot-pin.md`）。値を散文に書くと、正本を直したときにずれを検出する手段が無い
- **呼べない実装に複製するときは、一致をテストで機械検証する**: TS の mod は python を呼べないので値を複製している。上限の値はテストが正本の出力と突き合わせ、数え方と超過判定は手で期待値を書いた共有 fixture を両方の実装に通す（`test_issue_workflow_scope_size.py` と mod の `issue-band.test.ts`）。値だけを突き合わせると、数え方を片方だけ直したときにテストが緑のまま食い違う。複製の横には正本の場所と、検証するテストの名前を書く
- **散らばった判定基準を見つけたら、その場で値を揃えて終わりにしない**: 揃えただけでは、次に 1 か所を直したときにまた食い違う。正本を 1 つ決め、残りを呼び出しか参照に置き換える。その作業が今の変更の範囲を超えるなら、食い違っている場所（file:line）と値を並べて issue を立てる
