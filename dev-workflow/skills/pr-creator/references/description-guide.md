# Description 生成ガイドライン

PR description はレビュアー（人間 + bot）が GitHub 上で読むための文章である。AI やレビュー bot が参照する構造化情報は `<details>` の折りたたみに退避して、本文は人間が短時間で全体像を掴めるように保つ。

## 大事にしたいこと

レビュアーが PR を開いたとき、まず本文を読んで「何が変わったのか・なぜ変えたのか・どこを見ればよいのか」を理解できるのが理想。差分を見なくても判断材料が揃っているのが望ましい。

そのために意識すること。

- 概要では `What / Why / Outcome` の三要素を伝える（後述）
- 既にコミットメッセージや Linear Issue に書いてあることは、リンクで済ませて写経しない
- 「〜したつもりです」「〜と思います」のような曖昧さは削る
- 全体で 200〜400 字に収まるのが目安。長くなるならセクションを削れないか考える

## 情報の集め方

Linear Issue の説明、`git log`、`git diff` を主な情報源にする。いずれも丸ごと貼らずに、PR の文脈で意味のある部分だけを引用する。

ローカルの計画ファイル（`.claude/plans/` 等）は実装時の内部メモであり、GitHub 上の PR 本文には書かない。レビュアーはそのパスにアクセスできない。

## 構成

リポジトリに PR テンプレート（`.github/PULL_REQUEST_TEMPLATE.md` など）があれば、本文はそれに従う。テンプレートがなければ次の構成を使う。末尾の折りたたみは常に追加する。

````markdown
## 概要

`What / Why / Outcome` を 1〜3 文で。GitHub の PR 一覧でも冒頭が見えるので、ここに最重要情報を置く。

## 変更点

主要な変更を文章または箇条書きで。粒度はセクションやモジュール単位。

## レビューしてほしいところ

レビュアーに特に見てほしい箇所や、判断に迷ったので意見が欲しい点があれば書く。なければセクションごと省略する。

## 動作確認

実際に試した手順や結果。コマンドは inline code で。

## 備考

Breaking change、関連 PR、後続タスクなど。なければ省略する。

<details>
<summary>詳細情報</summary>

(AI 向けの補足情報。中身は自由)

</details>
````

## 各セクションについて

### 概要

このPRを 1〜3 文で説明する。以下の三要素を満たすことを意識する。

- **What**: どのコード・機能・領域を触ったか（対象・スコープ）
- **Why**: 何が問題・状況だったか（動機・背景）
- **Outcome**: 結果としてどう変わったか（効果・新しい挙動）

実装の手段（How）は概要に書かない。「変更点」セクションに任せる。概要で How まで踏み込むと冗長になり、レビュアーが PR 一覧で全体像を掴めなくなる。

三要素が埋まらない場合は `git diff` や Linear Issue から拾う。それでも判断できない場合は `AskUserQuestion` でユーザーに確認する。

良い例: `PR 作成時に Linear Issue のステータスを自動遷移させる処理を追加した（What）。手動更新の漏れが発生していた（Why）ため、PR 作成と同時に In Review へ切り替わるようにした（Outcome）。`

避けたい例 1: `pr-creator/SKILL.md を編集し、linear-integration.md にセクションを追加した。`
（実装の手順を並べてしまい、何のためのPRかが伝わらない）

避けたい例 2: `Linear MCP の updateIssue を呼ぶ処理を追加し、ブランチ名から正規表現で ID を抽出した後、ステータスを In Review に PATCH する。`
（How が概要に侵食している。実装手段は「変更点」セクションに移す）

### 変更点

何をどう変えたかを書く。並列性のある情報（複数の独立した変更、試したケースの一覧）は箇条書きが自然。因果関係の説明や「なぜそうしたか」は散文で書く。無理に散文化しない。

良い例（散文）:

```
Linear MCP に status update リクエストを送る処理を追加した。ブランチ名から Issue ID が取れなかった場合は skip する。MCP がエラーを返したときも PR 作成自体は止めず、warning だけ出す方針にした。
```

良い例（並列変更を箇条書き）:

```
- extractIssueId() に小文字ブランチ対応の正規表現を追加
- MCP エラー時のフォールバック処理を追加
- linear-integration.md にステータス遷移の説明を追記
```

避けたい例: 編集したファイルを 10 個以上ずらっと並べる、関数名だけを羅列する、テストを追加した自明なことをいちいち書く。これらは差分タブで分かる。

### レビューしてほしいところ

任意。レビュアーが「どこを重点的に読むか」を判断する助けになるなら書く。複数の観点がある場合は箇条書きが読みやすい。

良い例: `extractIssueId() の正規表現が小文字のブランチ名 (feat/team-123) も拾うべきか、現状の uppercase 限定でよいかの判断が欲しい。`

「全体を見てください」「気になる点があれば指摘してください」のような中身のない依頼は書かないでよい。

### 動作確認

実際にやった検証を、再現できる粒度で書く。手順や確認ケースが複数あれば箇条書きが自然。CI で分かる「テスト通過」だけしか書くことがないなら省略してよい。

良い例:

```
- gh pr create をブランチ feat/TEAM-123-... で実行し、Linear のステータスが In Review に変わることを確認
- Linear MCP を未接続にして実行し、warning が出つつも PR 作成が完了することを確認
```

### 備考

破壊的変更の移行手順、関連PR (`Closes #123`, `Refs #456`)、後続タスクなど。書くことがなければセクションごと消す。空の「なし」を残さない。

## 末尾の折りたたみについて

`<details><summary>詳細情報</summary>...</details>` を本文の末尾に置く。中身は AI が自動生成してよいが、人間向けに書くべきことをここに逃がさないのが原則。

折りたたみに入れて差し支えないもの:

- ファイル単位の影響マップや変更ファイル一覧
- 長くなる設計トレードオフの検討メモ
- 自動生成された差分サマリ

逆に本文側に残すもの:

- レビュアーが行動を変える判断材料
- 3 行で書ける程度の「なぜそうしたか」
- Linear Issue や関連 PR へのリンク（折りたたみに隠すと辿りづらい）

判断に迷ったら「この情報なしでレビュアーは approve できるか」を考える。できないなら本文に残す。

中身に決まりはないが、迷ったら以下の骨組みでよい。GitHub からクリックできないローカルパスは書かない。

```markdown
<details>
<summary>詳細情報</summary>

### 影響範囲
モジュールやレイヤー単位の影響を簡単に。

### 主な変更ファイル
- `path/to/file.ts` — 役割の一言
- `path/to/other.ts` — 役割の一言

### 関連リソース
- Linear Issue: https://linear.app/...
- 関連 PR: #456

</details>
```

## PR の大きさによる省略の目安

typo やコメント修正なら概要 1 文だけで十分。docs のみの変更も同様で、変更点や動作確認は省いてよい。50 行程度の小さい修正なら、概要と変更点を短く、動作確認を 1〜2 行添える程度。中規模以上の機能追加では概要・変更点・動作確認をきちんと書き、レビューしてほしいところも添える。破壊的変更を含むPRは備考も必須にする。

| 規模 | 概要 | 変更点 | レビューしてほしいところ | 動作確認 | 備考 |
|------|------|--------|--------------------------|----------|------|
| typo / コメント | 1 文 | 省略 | 省略 | 省略 | 省略 |
| docs のみ | 1〜2 文 | 任意 | 省略 | 省略 | 任意 |
| 小規模 fix（〜50 行） | 1〜2 文 | 短く | 任意 | 1〜2 行 | 任意 |
| 中規模機能（〜300 行） | 2〜3 文 | 必須 | 推奨 | 必須 | 任意 |
| 大規模・破壊的変更 | 背景含めて | 必須 | 必須 | 必須 | 必須 |

折りたたみの詳細情報は、規模に関わらず付けてよい。typo レベルなら省いて構わない。

## 変更の粒度を小さく保つ（Small CL）

description の良し悪し以前に、PR そのものが小さく単一目的だとレビューが速く正確になり、バグが減り、revert も容易になる。pr-creator は既存ブランチから PR を作るので分割そのものはできないが、diff が大きいときは「次はもっと小さく刻めないか」を考える材料として以下を意識する。

### 目安

- 1 つの PR は self-contained な「1 つのこと」に絞る。独立した複数の変更が混在していたら分割のサイン
- 行数は ~100 行が快適、~400 行で要注意、1000 行超は過大。ただし行数は目安であって絶対基準ではない
- リファクタと機能変更は別 PR に分ける。混ぜると「どの変更が挙動を変えたか」がレビューで追えなくなる
- 無関係なバグ修正・typo 修正をついでに混ぜない。レビュー対象がぼやける
- テストは対象ロジックと同じ PR に含める（テストだけ別 PR に切り出さない）
- 「この PR 単独で revert できるか」を自問する。できないなら結合しすぎ

### 大きくても許容される例外

- ファイル / ディレクトリの全削除
- 信頼できる自動ツールによる機械的リファクタ（一括 rename など）
- 設定ファイルの一括生成

### pr-creator での扱い

diff が目安を超えて大きい場合（おおよそ 400 行超 または 10 ファイル超）、PR は作成したうえで、レポート末尾に「この PR は大きめ（N ファイル / M 行）。レビュー負荷が高いので次回は分割を検討」と一言添える。作成済みの作業を止める必要はない（advisory にとどめる）。

## 文体

体言止めと常体（だ・である）を基本にする。コミットメッセージの規約と揃えるため敬体（です・ます）は使わない。一人称（「私は」「自分が」）も省く。

絵文字や装飾的な記号は使わない。AI が好んで付ける ✅ ❌ 🤖 のような目印も避ける。強調はマークダウンの太字を本当に必要なときだけ使う。

箇条書きは並列性のある情報（独立した変更の列挙、確認手順、レビュー観点など）に使う。2 項目でも並列なら箇条書きで構わない。一方で因果説明や背景の文脈は散文で書く。過剰な箇条書きで散文を細切れにしない。

## ありがちな書き方の失敗

コミットメッセージを時系列で全部貼ってしまうケース。コミット履歴を見ればよいので、PR description で同じことを繰り返さない。

「対応しました」「修正しました」だけで終わるケース。何をどう変えたかが残らないのでレビューしづらい。

概要に実装の詳細を書き、変更点に「このPRは〜です」と概要のような文を入れてしまうケース。セクションの役割がずれているサイン。

折りたたみの中に動作確認や概要のような主要情報を入れてしまうケース。折りたたみは本文を読んでから「もっと知りたい人だけが開く」場所なので、レビューに必要な情報は本文側に残す。

空のセクション（「## 備考」のあとに「なし」だけ）を残すケース。読み手の視線を奪うだけなのでセクションごと消す。

ローカルパス（`.claude/plans/` 等）を PR 本文や折りたたみに書いてしまうケース。GitHub 上でクリックできないパスはレビュアーにとって無意味なので書かない。

## GitHub Markdown の注意

`<details>` タグの直後には空行を 1 行入れる。空行がないと中の Markdown がレンダリングされない。
`<summary>` の中では一部の Markdown しか効かない。太字 (`**bold**`) は使えるが、見出し記号 (`#`) は使えない。
折りたたみ内の見出しは `###` から始める。本文の `##` 階層を壊さないため。
