### 4.6 説明図の添付（UI 変更の有無を問わない / GitHub issue #287）

差分の要点を 1〜2 枚の図にして PR 本文に添付する。バックエンド中心で処理の流れや集計の範囲を変える PR でも、変更の全体像やレビューで見てほしい範囲は、図にすると読み手の理解が早い。Step 4.5 の Screenshots（ui-verify で撮った画面）とは別に扱い、UI 変更の有無で判定しない。

#### 判定（作るかを提案するか）

次をすべて満たすときだけ、作成を提案する:

- ユーザー引数に `--no-diagrams` が含まれない
- 添付できる: Step 4.5 と同じ `ATTACH_OK` の判定（`gh` が `--attach` に対応し、base リポジトリに書き込み権限がある）が 1。Step 4.5 を skip した回もこの判定だけは行う
- 差分の性質から、図が読み手の役に立つ。シグナルは次のどれか:
  - 処理の流れ・順序が変わる（分岐の追加や入れ替え、導出・集計の起点や範囲の変更、状態遷移の変更）
  - レビューで判断が分かれる範囲があり、その境界を示したい（「ここまでが今回の変更、ここから先は既存」）
  - 複数の層・モジュールにまたがる変更で、本文の箇条書きだけでは全体の流れを追いにくい

docs・設定・依存の更新だけの PR、typo や rename、1 つの関数の中で閉じる小さな修正、見た目だけの UI 変更（Screenshots で足りる）は役に立たない側に倒す。

満たせば、判定の根拠を 1 行添えて `AskUserQuestion` で確認する:

- question: "変更の要点を図にして PR に添付する？"
- header: "説明図"
- options:
  1. label: "作る（1〜2 枚）(Recommended)" / description: "<根拠 1 行>。図は SVG で作って PNG にし、承認の提示に含める"
  2. label: "作らない" / description: "図を付けずに進める"

満たさない・「作らない」なら本ステップを終える（Step 4.93 で `N-A`）。

#### 作成

1. 置き場所を作業ツリーの外に作り、出力されたパスを控える（シェル変数は Bash 呼び出し間で消える）:

   ```bash
   mktemp -d "${TMPDIR:-/tmp}/pr-diagrams.XXXXXX"
   ```

2. 主題を決め、主題ごとに図の型（`flow` / `sequence` / `state`）を選ぶ（1 枚 1 主題。1 つの PR で型が混ざってよい）。`${CLAUDE_PLUGIN_ROOT}/skills/pr-creator/references/diagram-guide.md` を読み、型の選び方・定義の書き方・型ごとの描き方はそこに従う。選んだ型と理由（1 行。選ばなかった型のうち次に近いものと理由も添える）を図ごとに控え、Step 4.95 の提示に出す
3. 型ごとの JSON 定義を `<控えたパス>/<名前>.json` に書き、SVG を組む。定義は区切りを引用したヒアドキュメント（`<<'EOF'`）で書く（引用しないと、ラベルに入った `$` やバッククォートがファイルに書く前に展開される）:

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/diagram-svg.py" '<控えたパス>/<名前>.json' …
   ```

   - `svg=<パス>` の行の SVG を次の手順で PNG にする
   - `warn=` / `failed=` の行は、理由に沿って定義を直して組み直す（diagram-guide.md §2・§5）
4. PNG に書き出す:

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/svg-to-png.sh" '<控えたパス>/<名前>.svg' …
   ```

   - `png=<パス>` の行のファイルを `ATTACH` に足す。足す前に PNG を Read で開き、文字の欠け・重なりが無いかを見る（warn= が拾わない崩れもある）
   - `failed=` の行や exit 2（変換の手段が無い）の図は、SVG のまま `ATTACH` に足す（gh は SVG も受け付ける）。PNG にできなかった理由を Step 5 のレポートに一言添える
5. 図の機密チェック: 図は PR を閲覧できる人全員に見える（public repo なら誰でも）。図に描かれる文字の一覧を出し、1 行ずつ見直す:

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/diagram-svg.py" --texts '<控えたパス>/<名前>.json' …
   ```

   - `text=<定義のパス>\t<定義の中の場所>\t<文字列>` の行が、その図に描かれる文字のすべて。どのキーが文字を描くかはスクリプトが決める。`id` は SVG の属性に残るので、`label` があっても出る。.svg は書き換えない
   - 文字列を「機密 UI チェックリスト」（Step 4.5）と同じ基準で見直す。社内 URL・社内サービス名・顧客名・実データが入っていれば、その場所の値を汎用の名前に置き換えて 3 から作り直す。リポジトリが public（`gh repo view --json visibility -q .visibility` が `PUBLIC`）なら、業務の識別子（業務リポジトリ名・画面名・ドメイン用語）も汎用の名前にする
6. PR body に節を足す。置き場所は「変更点」の直後（テンプレートがあるときはテンプレートの末尾、Screenshots 節の前）。各図の前には「何についての図か」を 1 行だけ置く（中身の説明は図と本文の他の節に任せ、長い解説を書かない）。画像の参照先は Step 4.5 と同じく `ATTACH` に入れたローカルパスをそのまま書く:

   ```markdown
   ## 図で見る要点

   <何についての図か 1 行（例: 削除の呼び出しの順と、見つからないときに抜ける経路）>

   ![削除の呼び出しの順](<ATTACH のパス>)

   <何についての図か 1 行（例: 削除ダイアログの状態の移り変わり）>

   ![削除ダイアログの状態](<ATTACH のパス>)
   ```

アップロードは Step 5 の PR 作成時（`--attach`）に行う（本ステップではまだ何も送信しない）。
