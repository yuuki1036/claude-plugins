# diagnose — feedback loop 駆動のバグ診断

厄介なバグと性能劣化のための診断規律。核心は 1 つ: **バグを赤く点灯させる tight な feedback loop を先に作る**。loop さえあれば二分探索・仮説検証・計装はそれを消費するだけの機械的作業になり、loop が無ければコードをいくら眺めても原因には辿り着けない。Phase の省略は、省略する理由を明示できるときだけ許される。

探索を始める前に、プロジェクトに蓄積された文脈があれば先に読む: issue-workflow の knowledge（`.claude/indie/*/knowledge/` または `.claude/linear/*/knowledge/`）と ADR（`.claude/adr/`）のうち対象領域に関わるもの（無ければ黙ってスキップ）。

> **pipeline-design 採否**: 多段 agent は使わない（診断は状態を引き継ぐ逐次規律で、コンテキスト分割が仮説検証の連続性を壊す）。採用は原則 8（外部オラクル = feedback loop そのもの）と原則 5（暴走ガード = 各 Phase の進入条件）。

## Phase 0: 適用判定

- **使わない**: スタックトレースが 1 箇所を明確に指す / 直前の変更が自明な原因 / 影響が数行に閉じる — こうした自明バグは本規律なしで普通に直す
- **使う**: 再現が不安定 / 原因箇所が絞れない / 「直したはず」が直らない / 複数モジュールを跨ぐ / 性能劣化（いつから・どこでが不明）

## `${CLAUDE_EFFORT}` 適応

| effort | 診断の深さ |
|--------|-----------|
| low / medium | loop は最初に成立した 1 本で進む・最小化は 1 周のみ・仮説 2〜3 個 |
| high | 全 Phase 標準（本文どおり） |
| xhigh / max | loop の決定化・高速化に追加投資し、仮説 5 個・最小化は全要素が load-bearing になるまで完遂 |

## Phase 1: feedback loop を作る（これがスキルの本体）

**このバグで赤くなる pass/fail シグナル**を 1 コマンドで得られるようにする。ここに不釣り合いなほどの労力を掛ける。執拗に、あきらめずに。

### 構築手段（おおむねこの順で試す）

1. **失敗するテスト** — バグに届く任意の層（unit / integration / e2e）で
2. **curl / HTTP スクリプト** — 起動中の dev server に対して
3. **CLI 起動 + fixture 入力** — stdout を既知の正解スナップショットと diff
4. **headless ブラウザスクリプト**（Playwright / Puppeteer）— UI を駆動し DOM / console / network を assert
5. **キャプチャの再生** — 実際のリクエスト / ペイロード / イベントログをディスクに保存し、対象コードパスだけに単独で流す
6. **使い捨てハーネス** — 対象コードパスを 1 関数呼び出しで叩く最小構成（1 サービス + モック依存）
7. **property / fuzz ループ** — 「たまに出力がおかしい」型ならランダム入力 1000 件で失敗モードを探す
8. **二分探索ハーネス** — 2 つの既知状態（コミット・データセット・バージョン）の間で発生したなら「状態 X で起動 → 判定」を自動化して `git bisect run` に載せる
9. **差分ループ** — 同じ入力を旧版と新版（or 2 つの設定）に流して出力を diff
10. **人間参加ループ**（最終手段）— 人のクリックが必須なら、手順を 1 ステップずつ指示 → 結果を貼ってもらう構造化ループにする（人任せの「試してみて」にしない）

### loop を tight にする

loop はプロダクトとして扱い、成立したら磨く: **速く**（セットアップをキャッシュ・無関係な初期化をスキップ・スコープを絞る）、**シグナルを鋭く**（「クラッシュしない」ではなく症状そのものを assert）、**決定的に**（時刻固定・乱数シード・ファイルシステム隔離・ネットワーク凍結）。30 秒かかる flaky な loop は無いよりマシな程度、2 秒で決定的な loop は診断の主導権そのもの。

### 非決定的バグ

目標は完全な再現ではなく**再現率の引き上げ**。トリガーを 100 回ループ・並列化・負荷付与・タイミング窓の絞り込み・sleep 注入。再現率 50% なら診断可能、1% なら不可能 — 診断可能になるまで率を上げる。

### どうしても loop が作れないとき

止まって明示的にそう言う。試した手段を列挙し、ユーザーに (a) 再現する環境へのアクセス、(b) キャプチャ済み成果物（HAR・ログダンプ・タイムスタンプ付き録画）、(c) 一時的な計装追加の許可、のいずれかを求める。**loop なしで仮説フェーズに進まない。**

### 完了基準 — red-capable な 1 コマンド

Phase 1 の完了は、**既に 1 回以上実行済み**（呼び出しと出力を提示できる）の 1 コマンドが次を満たすこと:

- [ ] **red-capable** — 実際のバグのコードパスを駆動し、**ユーザーの訴えた症状そのもの**を assert する（「エラーなく走る」ではなく、このバグで赤・修正で緑になれる）
- [ ] **決定的** — 毎回同じ判定（flaky バグは上記の引き上げ済み高再現率で代替）
- [ ] **速い** — 秒単位
- [ ] **無人実行可能** — 自分だけで回せる（人間参加は手段 10 の構造化ループ経由のみ）

コマンドが存在する前にコードを読んで仮説を組み立て始めていたら、**止まる — 仮説先行こそこのスキルが防ぐ失敗そのもの**。

## Phase 2: 再現 + 最小化

loop を回し、赤くなるのを確認する。

- [ ] 再現したのは**ユーザーが訴えた症状**である（近くにある別の失敗ではない。バグ違いは修正違いに直結する）
- [ ] 複数回の実行で再現する（非決定的バグは診断に足る率で）
- [ ] 症状の実体（エラーメッセージ・誤出力・遅延時間）を記録した（後の Phase で「本当にこれを直したか」を照合するため)

**最小化**: 赤のまま**最小のシナリオ**まで削る。入力・呼び出し元・設定・データ・手順を 1 つずつ削り、削るたびに loop を再実行。残った全要素が load-bearing（どれを外しても緑になる）になったら完了。最小 repro は Phase 3 の仮説空間を縮め、Phase 5 の回帰テストの素体になる。

再現と最小化が終わるまで先に進まない。

## Phase 3: 仮説

検証を始める前に**ランク付きの仮説を 3〜5 個**生成する（1 個ずつ出すと最初のもっともらしい案にアンカリングする）。

各仮説は**反証可能**な形式で書く: 「もし <X> が原因なら、<Y を変える> とバグは消える / <Z を変える> と悪化する」。予測が書けない仮説は雰囲気であり、捨てるか鋭くする。

**ランク付きリストを検証前にユーザーへ提示する。** ユーザーはドメイン知識で瞬時に並べ替えられる（「#3 は昨日デプロイした所だ」）し、検証済みの仮説を除外できる。安いチェックポイントで大きな時間節約。ただし**返答を待って止まらない** — 反応が無ければ自分のランキングで進む。

**完了基準**: 反証可能な予測を持つ仮説が 3〜5 個、有力順にランクされ、ユーザーに提示済みであること。予測の書けない仮説が混ざったまま Phase 4 に進まない。

## Phase 4: 計装

各プローブは Phase 3 の特定の予測に対応させ、**一度に 1 変数だけ**変える。

手段の優先順: ①デバッガ / REPL（環境が許すなら。ブレークポイント 1 個はログ 10 行に勝る）→ ②仮説を判別する境界への**狙い撃ちログ** → ③「全部ログして grep」は決してやらない。

**デバッグログには必ず一意の接頭辞タグを付ける**（例: `[DEBUG-a4f2]`）。後始末が grep 1 回になる。タグ無しログは生き残って本番に混入し、タグ付きログは確実に死ぬ。

**性能劣化の分岐**: perf にログは大抵不適。ベースライン計測（タイミングハーネス・`performance.now()`・プロファイラ・クエリプラン）を確立してから二分探索する。**計測が先、修正は後。**

**完了基準**: いずれかの仮説の予測が観測で支持され、原因箇所を `file:line` で特定できたこと。**全仮説が反証されたら Phase 5 に進まず Phase 3 へ戻る** — 計装で得た観測（どの予測がどう外れたか）は仮説空間を狭める新しい材料であり、最小化済みの repro がある限りこのループは収束に向かう。2 巡しても原因に届かないときは、Phase 2 に戻って repro をさらに最小化するか、観測結果を添えてユーザーに知見を求める。

## Phase 5: 修正 + 回帰テスト

回帰テストは**修正より先に**書く — ただし**正しい seam があるときだけ**。正しい seam とは、バグが実際に発生した呼び出しパターンをテストが再現できる境界のこと。浅すぎる seam（複数呼び出し元で起きるバグに単一呼び出しテスト、発火チェーンを再現できない unit テスト）に置いた回帰テストは偽の安心にしかならない。

**正しい seam が無いなら、それ自体が発見。** 記録する — アーキテクチャがバグの封じ込めを妨げている（Phase 6 の post-mortem で扱う）。

seam があるなら: ①最小 repro をその seam の失敗テストに変換 → ②赤を確認 → ③修正 → ④緑を確認 → ⑤**最小化前の元シナリオ**で Phase 1 の loop を再実行。

## Phase 6: 後始末 + post-mortem

完了宣言の前に必須:

- [ ] 元の repro が再現しない（Phase 1 の loop を再実行）
- [ ] 回帰テストが通る（or seam 欠如を記録済み）
- [ ] `[DEBUG-` を grep してヒット 0（計装の全撤去）
- [ ] 使い捨てハーネス・プロトタイプを削除（意図的に残すなら明示的な置き場と印を付ける）
- [ ] 正解だった仮説をコミットメッセージに 1 行残す（次にここを診断する人への遺産）

**最後に自問する: このバグを防げたものは何か。** 答えに応じて還流する（いずれも対象が未導入なら黙ってスキップ）:

- **再発しうる作業パターン起因**（検証せず断定した・ツール出力を読み違えた等）→ failure-journal 導入済み（`.claude/failure-journal/` が存在）なら candidates.jsonl に 1 行 append（自己申告ルールと同形式・確認不要）
- **アーキテクチャ起因**（テスト seam の欠如・呼び出し元の絡まり・隠れた結合）→ issue-workflow 導入済みならユーザーに follow-up / issue 起票を提案する。提案は修正が入った**後**に行う — 着手前より今のほうが判断材料が多い
