# code-review に review-guide skill を新設する（人間が PR を理解するための読み順ガイド）

## TL;DR

PR（または base 指定のローカル diff）を人間が読むための「読み順ガイド」をセッション内に出力する読み取り専用 skill。`triage-signals.sh` の分類とリスク信号で精読ファイルを上位 N 件に絞り、explorer（sonnet）が辿った呼び出し関係を「入口 → ロジック → 永続化 → テスト」のスレッド単位に並べ、各ファイルに「この PR で何をした / 難点 / 見る行 / レビュー観点」を付ける。ファイルは作らず、コメントも投稿しない。

（2026-10-18 追記: 精読は「精読に値するものだけ 1〜5 件」に改め、コミット前の読み合わせ `--walkthrough` を足した。コードを直すのは読み合わせの中だけ。末尾の追記を参照）

## 背景 / 課題

- 主用途は**自分の PR を後から理解する**こと（マージ済み・時間が経った PR を読み直す）。副用途は他者 PR に `review` を回した後の学習
- 既存 4 skill はどれも「指摘を出す」（review / self-review）か「付いた指摘に応える」（review-triage）か「コメントを直す」（comment-polish）で、**人間が読む行為そのものを支援するものが無い**。`claude-meta:component-addition-advisor` の観点で既存拡張を検討したが、review の出力契約（severity 付き findings）と読み順ガイドの出力（説明文）は形が違い、review に `--guide` を足すと Phase 0〜反証の全機構が無駄に回る。新 skill が最小構成
- diff 全文を人間が上から読むのは非効率で、生成物・lockfile・機械的置換に時間を使ってしまう。**読まなくてよいものを理由付きで切る**のがガイドの価値の半分

## ゴール / 非ゴール

- **ゴール**:
  - PR 番号（既定）または `--base <ref>` のローカル diff を入力に、精読 N 件（既定 5、`--top N`）/ 流し読み / 不要 の 3 段に振り、不要には 1 行の理由を付ける → 精読の数は 2026-10-18 追記で改めた
  - 精読ファイルをスレッド（変更が貫く 1 本の流れ）単位で実装順に並べ、各ファイルに 4 項目（この PR で何をした / 難点 / 見る行 `file:line` / レビュー観点）を付ける
  - PR 本文の主張と diff の突合（書いてあるが無い / 無いが入っている）
  - 変更した振る舞いごとのテスト対応表（ある / 無い）
  - PR に付いた既存コメント（review が投稿したものを含む）と、同一セッションに review レポートがあればその `🔁 報告閾値を割った指摘` を「人間の判断が効く箇所」として案内する。**無ければ単独で完結**
  - `${CLAUDE_EFFORT}` で agent 体数を変える（low / medium: agent なし、high: explorer 上限 2、xhigh / max: 上限 3）
- **非ゴール**:
  - ファイルへの永続化（ユーザー確定 2026-09-16: セッション出力のみ。必要なときに再実行する）
  - コメント投稿・PR 本文編集・コード修正（Edit / Write を持たない） → コード修正は 2026-10-18 追記で改めた（読み合わせの中だけ Edit を持つ。Write は持たない）
  - severity 付き指摘の生成（review の領分。ガイドの「レビュー観点」は「何を見るか」の問いであって判定ではない）
  - 全ファイルの解説（上位 N 件に絞る。残りは 1 行） → 絞り方は 2026-10-18 追記で改めた（上位 N 件ではなく、精読に値するものだけ）
  - 反証レイヤー（説明文の誤りは `file:line` の根拠強制で抑える。独立検証を足すコストに見合わない）

## 採用案

### 全体フロー

→ 2026-10-18 追記で改めた: 下の図は初版のフロー。引数 `--walkthrough`、Step 2 の選び方（「上位 N 件 = 精読」ではなく、精読に値するものだけを 1〜5 件）、Step 5 の後の Step 6・7（読み合わせ・その場の修正・締め）は末尾の追記 (a)〜(d) と SKILL.md が正本

```
/review-guide [PR番号 | --base <ref>] [--top N]
  │
  ├─ Step 0  入力確定: PR 番号（省略時は現ブランチの PR）→ triage-signals.sh --pr N
  │          --base 指定なら triage-signals.sh --base <ref>（PR 本文・コメントの Step は skip）
  │          → diff_file / files 分類 / red-flags / surface を得る（diff 全文は読まない）
  │
  ├─ Step 1  PR コンテキスト: fetch-pr-context.sh N --save → 本文・既存コメントを Read
  │          （--base モードでは無し。同一セッションに review レポートがあれば 🔁 付録を控える）
  │
  ├─ Step 2  重要度スコアと 3 段振り分け（メインコンテキスト・agent なし）
  │          score = 分類（core=3 / test=2 / doc=1 / generated・lock=0）
  │                + red-flags・surface の代表ファイルに +2（triage-signals の digest は
  │                  1 signal につき代表 1 ファイルしか出さないため、その代表にのみ加点する）
  │          分類だけで core(3) > test(2) > doc(1) が確定するので、シグナル加点が無くても
  │          core が上位に来る。同点は core 優先でタイブレークする（core を N 件目以降に落とさない）
  │          上位 N 件 = 精読 / 残りの core・test・doc = 流し読み / gen(生成物・lock)・rename・機械的置換 = 不要（理由 1 行）
  │
  ├─ Step 3  流れの把握（effort 分岐）
  │          low / medium: agent なし。diff-slice.sh で精読ファイルの hunk だけ読み、
  │                        import / 呼び出しの字面からスレッドを組む
  │          high:         explorer 上限 2（sonnet）。function-flow（精読ファイルの変更関数）と
  │                        dependency-trace（精読ファイルの被参照＝呼び出し元）を同一メッセージで一括発行
  │          xhigh / max:  explorer 上限 3（+ value-flow-trace で入口→永続化の値の流れ）
  │          explorer には diff_file のパスと担当ファイルだけ渡す（本文を転記しない）
  │
  ├─ Step 4  統合・執筆（メインコンテキスト = opus）
  │          スレッド構成 → 各精読ファイルの 4 項目（根拠 file:line 必須）
  │          → 主張 vs diff 突合 → テスト対応表 → 人間の判断が効く箇所
  │
  └─ Step 5  レポート出力（下の形式）。ファイルは書かない
```

### レポート形式

→ 2026-10-18 追記で改めた: 下の例は初版の形式。精読の件数の書き方・分割の検討・上限超えの印・読み合わせの案内・精読の解説・締めの形式は `code-review/references/review-guide-format.md` が正本

```
## 読み順ガイド: PR #<N> <title>（<core_files> files / <core_lines> lines / size_tier）

### まず全体
- この PR がやったこと（PR 本文 + diff から 2〜3 行。本文と diff の乖離があればここに ⚠️）
- スレッド一覧: ① <入口→…→永続化> ② … （精読ファイルがどのスレッドに属すか）

### 読まなくてよい（K 件）
- <path> — <理由 1 行: 生成物 / lockfile / rename のみ / 機械的置換（import 差し替え）>

### 流し読み（M 件）
- <path> — <何が変わったか 1 行>

### 精読（N 件・実装の流れ順）
1. <path>（スレッド ①・入口）
   この PR で: <何をしたか 2〜3 行>
   難点: <非自明な分岐・並行性・境界値・暗黙の前提。無ければ「特になし」>
   見る行: <file:line 〜 file:line> — <なぜここか>
   レビュー観点: <triage-guide の観点名 → この PR での具体的な問い>
2. …

### 主張 vs diff
- 本文の主張「…」→ diff で確認: <あり file:line / 見当たらない>
- diff にあるが本文に無い: <path> — <内容>

### テスト対応
| 変更した振る舞い | テスト | 場所 |
|---|---|---|
| … | あり / なし | file:line |

### 人間の判断が効く箇所（該当があるときだけ）
- 既存の行コメント（解決状態は不明。fetch-pr-context は isResolved を取得しない / design-review F6）: <file:line> — <要旨>
- review が閾値を割った指摘（同一セッションのみ）: <要旨> — <脱落理由>
```

### コスト×精度パイプライン設計（SKILL.md に残す一言）

採用: **1**（ファネル: triage-signals の分類で精読を N 件に絞ってから agent を当てる）/ **3**（段階予算: effort → explorer 0 / 2 / 3 体）/ **4**（モデルルーティング: explorer sonnet・統合 opus）/ **5**（暴走ガード: 体数上限・精読 N の上限）/ **9**（構造化受け渡し: diff はパス渡し、explorer は事実のみ返す）。
捨てた: **2・10**（severity / confidence を付けない。判定ではなく説明）/ **6**（蓄積しない。永続化なし）/ **7**（反証なし。説明文の根拠を `file:line` で強制し、無い主張は書かない）/ **8**（機械層は不要。実行しない）。

## 検討した代替案

| 観点 | 案 A（採用）シグナル絞り込み → explorer 流れ追跡 → main 統合 | 案 B agent なし single-pass | 案 C ファイル単位 fan-out（1 ファイル 1 agent が解説） |
|---|---|---|---|
| 読み順の質 | 呼び出し関係を実際に辿るのでスレッドが正確 | 字面の import から推定。大きい PR で順序が崩れる | 各ファイルは詳しいが**横断の流れが消える**（ガイドの主目的と逆） |
| コスト | explorer 0〜3 体（effort 連動） | 最小 | 精読 N 体 + 統合。案 A の 2〜3 倍 |
| 既存資産の再利用 | triage-signals / explorer prompts / diff-slice をそのまま使う | triage-signals / diff-slice | reviewer 起動基盤に近いが出力契約が違い流用しにくい |
| 失敗モード | explorer が事実を取り違える → `file:line` 根拠で main が検算 | 大 PR で「読めていない」まま書く | agent 間で用語・粒度が揃わない |
| 採否 | **採用**。案 B は案 A の low / medium 分岐としてそのまま含める | 単独では大 PR に弱い | 横断の流れが主価値なので不採用 |

## 設計判断ログ

- [local] 出力はセッション内のみ。ファイルを書かない（ユーザー確定）。理由: 「後で理解する」は「後で再実行する」で足り、永続化は commit / gitignore / マシン間同期の判断を持ち込む
- [local] severity / confidence を付けない。レビュー観点は「この PR で何を見るか」の問いとして書く。理由: 判定を出すと review と役割が重なり、説明の信頼度と判定の信頼度が読み手の中で混ざる
- [local] 反証レイヤーを置かない代わりに、4 項目の各主張に `file:line` を必須にし、根拠を示せない主張は書かない（「難点: 特になし」を許す）。理由: 説明の誤りのコストは指摘の誤りより低く、独立検証の体数に見合わない
- [local] スコアは「分類 + red-flag/surface 代表加点」の 2 要素に絞る（初版）。理由: 精読 N の選抜は分類だけで core が上位に来る粗い判定で足り、fan-in（独自 Grep）や行数帯は重み付き合成を増やすだけで選抜をほぼ変えない。fan-in を独自実装すると triage-signals `## explorer-signals` が既に持つ誤カウント対策（3 文字未満の basename 除外・`-lwF` 固定文字列 word 一致・自己除外）を捨てることになり、common / 短い basename で過大カウントして選抜を歪める（design-review F1）。必要になったら triage-signals の `## explorer-signals` 出力を**再利用**して足す（独自 Grep は新設しない）
- [local] red-flag/surface は per-file に全展開できない。triage-signals の digest は 1 signal につき代表 1 ファイルしか出さないため（`## red-flags` / `## surface` の出力は `<key>\t<hit数>\t<代表根拠1ファイル>`）、加点は代表ファイルにのみ効かせ、全該当ファイルへ配れる前提で設計しない（design-review F2）。全展開が要るなら diff-slice で候補 core の hunk を先読みする段が要るが、初版では持たない
- [local] `🔁 報告閾値を割った指摘` は同一セッションに review レポートがあるときだけ使う。永続化を新設しない。理由: review 側の計測契約（events.jsonl は件数のみ）を変えずに済み、後日は PR コメント経由で同等の情報が取れる
- [local] `--base` モードでは PR 本文・コメント由来のセクション（主張 vs diff / 人間の判断が効く箇所）を「対象なし」と明記して省く。理由: silent skip と区別する（self-review の見出し規約と同じ）

## 未解決事項 (open)

- **精読 N の既定値**: (a) 5 — 1 回で読み切れる量。(b) size_tier 連動（small 3 / medium 5 / large 8）— 小 PR で全件精読になり「絞る」意味が薄れる。現時点の方向性: **(a) 5 固定 + `--top N`**。確定タイミング: 実装後 3 PR で使い、上限に当たる頻度を見て決める → 2026-10-18 追記で畳んだ（上限 5・精読に値するものだけ）
- **スコアの 2 要素で選抜が不足するか**: 初版は分類 + red-flag/surface 代表加点のみ（fan-in・行数帯を落とした / design-review F1・F3）。精読すべきファイルが上位 N から漏れる回が出たら、triage-signals `## explorer-signals` の再利用で fan-in を足す。現時点の方向性: **2 要素で開始**。確定タイミング: 実装後 3 PR で、漏れ（後で「これは精読に入れるべきだった」と気づいた回）の頻度を見て決める

2. 検証方法:
   - 機械層: `bash .claude-plugin/scripts/machine-layer.sh`（allowed-tools ペア一致 / `skill-hop-cmd` / トリガー必須 / references 参照整合。agent-sync warning は 2026-10-31 に外した / #347）

## 追記（2026-10-18）: 読み合わせ（--walkthrough）と精読数

実装後の使われ方を受けて、次の 4 点を決めた。手順は `code-review/skills/review-guide/SKILL.md` の Step 2・5〜7、形式の正本は `code-review/references/review-guide-format.md` の「精読の解説」「読み合わせの締め」。

### (a) 想定していなかった使い方が主になった: コミット前の読み合わせ

- 設計時に想定した用途は、自分の PR の後日理解と、他者 PR に review を回した後の学習だった（背景 / 確定した前提 10）。実際に主になったのは**コミット前**の使い方で、利用者は毎回次の流れを手で指示していた: self-review → review-guide → 概要を確かめる → 精読を 1 件ずつ解説させる（難点がなぜ難点になったか / レビュー観点はまず AI が確かめる / 直す所があればその場で直し、以後の精読はそれを折り込む）→ 全精読の後に精読の外の気になる点 → self-review をもう一度 → commit
- `--walkthrough` はこの流れを手順にしたもの。Step 5 でレポートの末尾に案内を出してターンを終え（概要を確かめる間を取る）、Step 6 で 1 精読を 1 ターンで解説し、Step 7 で締める。解説は editor を開かずに読めるように書く（置き場所・関連ファイル・変更したコードの引用を解説の中に入れる）。レビュー観点の問いは並べるだけにせず、コードを読んで「問題なし / 直すべき / 判断が要る」で答える。解説への要望と入れた修正は以後の精読に持ち越す
- 呼び出し元は issue-workflow の軽量フロー（self-review の後に読み合わせを通す）と feature-dev の Phase 7（読み合わせとして呼ぶ）。どちらも `code-review:review-guide` を名前で呼び、パスで参照しない（プラグイン間の依存禁止）

### (b) 非ゴール「コード修正（Edit / Write を持たない）」を改める

- **読み合わせの中だけ Edit を持つ**。Write は持たない（ファイルを新規作成しない）。commit・push もしない
- 直してよいのは、作業ツリーが diff の対象そのもの（base モード、または手元の HEAD が PR head と同じ PR モード。SKILL の `FIX_OK`）で、かつ直し方が 1 つに決まり（仕様・設計の判断が要らない）、diff の範囲で閉じる修正だけ。直し方が複数ある / 仕様の判断が要る / diff の外へ広がる / 新しい仕組みが要る / 他者の PR を別のブランチから読んでいる、のどれかなら直さずに 1 問だけ聞く
- 理由: その場で直せば、利用者は解説と修正を並べて確かめられ、以後の精読もその修正を前提に進められる。別の skill に渡すと読み合わせの流れが切れる。一方で判断を含む修正まで入れると、利用者が読んで理解する前にコードが変わるので、直し方が 1 つに決まるものに限る。作業ツリーに限るのは、他者の PR を読んでいる回に手元の別のブランチを書き換えないため

### (c) 未解決事項「精読 N の既定値」を畳む

- **上限 5**（`--top N` は 1〜5 の範囲で上限を下げる）。上限は読み手の負担の上限であって目標ではなく、**精読に値するものだけ**を取り、数合わせで埋めない。値するかの線は「流し読みの 1 行では、読み手がこの変更の正しさを判断できない」か（SKILL Step 2）。実装の精読に対応するテストは、その精読の関連ファイルとして解説に畳む
- 精読に値するものが上限を超えたら、score の上位 N 件（既定 5）を精読にし、残りは流し読みに「精読候補・上限超え」の印を付けて置き、「まず全体」に分割の検討を出す。上限を広げて全部を精読にはしない — 1 回の読み合わせで読み切れる量を超えていること自体を利用者に渡す（分けるかどうか、どの単位で分けるかは呼び出し元・利用者が決める）
- **横断の精読も上限に数える**。GitHub issue #294 で横断を足したときは数えなかったが、読み手の負担は項目の数で決まるので、数えないと上限 5 のまま 6 項目を読ませることになる
- 理由: 読み合わせは 1 精読 1 ターンなので、数合わせで足した精読はそのまま利用者のターンを使う。size_tier 連動の案（未解決事項の (b)）は採らない。大きい diff で上限を上げると読み切れない量を精読に並べることになり、分割の検討を出す方が次の一手につながる

### (d) 2 回目の self-review の判断は締めの 1 行で呼び出し元に渡す

- 締め（Step 7）が `self-review 以降の変更: あり | なし | 不明（理由）` の 1 行を出し、呼び出し元はこの値で self-review をもう一度回すかを決める。3 つの値は言い換えない契約。review-guide 自身は self-review も commit も起動しない（次の一手は呼び出し元か利用者が決める）
- 判定は、base モードで diff を今の作業ツリーで取り直し、`detect-recent-review.sh` の明細のうち最も新しい self-review の行で決める: `[完全一致]` → なし / `[ファイル集合のみ]` → あり / self-review の行が無い → 不明。PR モードは「不明（PR モード）」
- diff は 3 本（コミット済み・staged・unstaged）を連結したバイト列で比べるので、中身が同じでも self-review の後の commit や `git add` でファイルの並びが変わると「あり」に倒れる（1 ファイルの add / commit だけなら変わらない）。逆に、self-review の後に変更ファイルの集合が変わるとどちらのキーも一致せず「不明」になる。2 回目を勧める側に倒れる誤りなので、見分けるキーを足さずにそのまま出す
- 2 回目の self-review は「修正確認の再レビュー」（`--rereview` / GitHub issue #300 の分類）ではない。読み合わせで入れた修正は前回の指摘への対応ではないので、引数は base だけにし、`--focus` / `--rereview` / `--embed` を付けない
- 2 回目の self-review は重複検出（self-review 1.4）で `[ファイル集合のみ]` に一致する（読み合わせの修正は diff の範囲で閉じるので、触ったファイルの集合は変わらない）。質問文が一致の強さを問わず「同一の diff が直近にレビュー済みです」と出していたので、明細のラベルで書き分けた（self-review 1.4 と、同じ質問を持つ review 2.4 の両方。その文は `[完全一致]` のときだけ。`[ファイル集合のみ]` だけなら「同じファイルを触った変更が直近にレビュー済みです（…。中身が同じとは限らない）」）

## 追記（2026-10-19）: 代表ファイルの扱い・締めの次の一手・答える側

### (e) red-flags・surface の代表ファイルを精読の条件から外す（GitHub issue #303）

- Step 2 の「値する」に「red-flags・surface の代表ファイル」があり、score の +2 と合わせて代表ファイルが無条件で精読に入っていた。signal は正規表現なので、テストデータの列名や story の値にも当たる。実例では、数量を表す見出しの文字列に money-numeric が当たった story が精読の先頭候補になり、修正の主題の View が上限 5 から流し読みに押し出された。その精読は「難点: 特になし」しか書けなかった
- 代表ファイルは**候補**に留め、+2 は見る順を上げるだけにする。精読に入れるかは、hunk を見て signal が指す処理（書き込み・数量の計算・認可・危険な呼び出し）をこの diff が変えているかを確かめ、変えていれば「値する」の線で決める。当たったのが文字列・テストデータ・コメントだけなら流し読みに回し、外した理由をその行に書く
- 上限で切るときは、加点だけで上位に入った代表ファイルと押し出される core を比べ、流し読みに落としたときに正しさを判断できなくなる方を残す
- signal の正規表現を直す案は採らない。triage-signals の digest は review / self-review の動的ゲートと共有で、review-guide の都合で狭めると review 側の recall が落ちる

### (f) 締めの次の一手に、回し直すかの判断を添える（GitHub issue #304）

- (d) の `self-review 以降の変更: あり` は「差分がある」という事実で、回し直す価値の判断ではない。値から次の一手を機械的に決めていたので、閾値未満の指摘の直しとテストで並びを固定したブロックの移動だけの回でも「self-review をもう一度」を出し、利用者が「self-review はいるか」を聞き直した。回し直しても要るのは前回と同じ閾値未満の候補が中心で、手間に見合わなかった
- `あり` でも、self-review の後の変更をすべて挙げられ・どれも解説で確かめ・実行時の挙動を変えないなら、次の一手を `決定的な検証`（関連テスト・typecheck・lint・宣言オラクル）にする。判断の正本は `review-guide-format.md` の「回し直すかの判断」
- `self-review 以降の変更:` の値は (d) の契約のまま残し、`次の一手:` の先頭（`self-review をもう一度` / `決定的な検証` / `コミットへ`）を 2 本目の契約にした。呼び出し元（軽量フロー・feature-dev Phase 7）は `あり` のとき、この先頭が `決定的な検証` なら self-review の代わりに決定的な検証だけを回す。行が無い・別の値なら従来どおり self-review に倒す
- 同じ判断を feature-dev の Phase 6.9 にも入れた。こちらは `review-snapshot.sh diff` で差の中身を読めるので、条件のうち「挙動を変えない」だけで推奨を決める（SSoT pin で正本に追随する）
- 判断を値の計算（`detect-recent-review.sh`）に寄せる案は採らない。挙動を変えたかは diff の字面から決定的には決まらず、読み合わせで中身を確かめた review-guide 自身が判断する方が材料が揃っている

### (g) 読み合わせの答える側を直す（トートロジーの懸念）

- 利用者から「AI 自身が難点・レビュー観点を確かめる形にしてから、判断を仰ぐ・修正が出る頻度が減った気がする。問いを作ってそのまま確かめていないか、利用者が明示的に確かめられる点を出していないのではないか」という懸念が出た。手順の監査と、recall fixture 3 種 × 2 回の再現（独立の判定役と、同じ問いを別のコンテキストで確かめ直す回を付けた）で確かめた
- 分かったこと: 問い 42 件のうち 16 件は変更行を読み直せば答えが決まる言い換えで、難点の本命を狙った問いは難点の結論を問いの形にしただけだった（新しい事実を生まない）。弱いのは問いを作る段より**答える段**で、手元で決まらない問いまで「問題なし」で閉じ（答えに「未確認」の出口が無い）、読解だけの答えを実行したかのように書き、その場で直した本命の確かめ方と副作用を出さず、「判断が要る」の選択肢から「このまま」を外し、1 問の上限で聞かなかった問いを捨てていた。一方、仕込んだ欠陥は 4 回とも難点の段で見つけて直しており、誤検出も無かった（問題は見落としではなく、利用者に確かめる入口を渡していないこと）
- 直したこと: 答えの値に `未確認`（何が分かれば・どこを見れば決まるか）と `直すべき（未修正）` を足し、未確認は締めに集める / 何で確かめたか（走らせたコマンドか読解のみか）を精読ごとに 1 行書く / 挙動を変える修正に確かめ方と副作用を添える / 「判断が要る」に `このまま` を必ず入れる / 1 問の上限で聞かなかった問い・答えが返らなかった問いを「持ち越した確認」として締めに持ち越し、締めでも 1 問ずつ聞く / 難点の言い換えだけの問いは書かず、答えの対象から外す
- 線の引き方: 答えしだいでコードを変えるかが分かれる問いは、仕様が未決でも「判断が要る」（`このまま` を含む）。未確認は、答えが分かっても直すかどうかに直結しない事実で、リポジトリと手元で走らせられるものからは決まらないものに限る。最初の版はこの線が無く、再現では未確認が判断を吸い（「判断が要る」が 0 件の回があった）、読めば決まる問いを未確認に逃がす回もあった
- 締めで確認をまとめて聞く形は採らない。最初の版は持ち越し・未確認を一覧にして「上の確認への答えがあれば」とまとめて聞いていたが、利用者は確認をまとめて出されると判断しにくい（確認は 1 問ずつの方針）。一覧は見えるように出し、聞くのは 1 問ずつにした
- 「読解のみ・未実行」を答えの行ごとに付ける形も採らない。再現では全行に付いて情報を失い、走らせられる typecheck を「走らせられない」と書く回もあった。精読ごとに 1 行にし、走らせなかった理由は事実で書く
- 効き目（同じ fixture をそれぞれ 6 回。旧手順 → 1 回目の直し → 上の最終形）: トートロジーの判定は partial 6 回 → none 2・partial 4 → none 3・partial 3。利用者に渡った確認点は 2〜6 件 → 6〜11 件 → 5〜11 件で、前回見落とした修正の副作用（共通ハンドラを通すと別のエラーもログに出る）・確かめ方（戻り値では前後を区別できない）・`このまま` の選択肢が渡るようになった。最終形では、未確認と判断の線・答えが返らなかった問いの持ち越し・締めで 1 問ずつ聞く・`このまま` の利点と欠点が 6 回ともおおむね守られた。仕込んだ欠陥は毎回直し、誤検出は無かった
- 残ったこと: 同じ確認・同じ事実が最大 6〜9 回繰り返された（判断が要るの答え・確認したいこと・持ち越し・締めの一覧・締めの問いのそれぞれで選択肢を書く構造のため）。最終形の後に「同じ事実・同じ問いは 1 か所に書く」「確認したいことは判断が要るを指すだけ」「持ち越しは新たに持ち越したものだけ」「締めの一覧に聞く 1 問を載せない」を足したが、これは再現していない。走らせられる typecheck を走らせずに読解で答える回も残った（明記はするようになった）。問いの質（自己言及と外部基準が半々）は変わっておらず、変わったのは答えの渡し方
- 採らなかった案: 本命の答えを別コンテキストの検証役に当てる（原則 7 の反証を読み合わせに入れる）。体数とターンの待ちが読み合わせの 1 精読 1 ターンに見合うかを、上の直しの効き目を見てから決める。利用者の体感には、同じ時期の self-review の MINOR 既定化・#304・精読数の削減も重なっていて、どれが効いたかは実際の読み合わせの transcript で比べないと決められない

## 追記（2026-10-20）: 読み合わせの後の変異テスト

### (h) 締めに変異テストの要否を足す（GitHub issue #307）

- 判断は締めの 1 行（`変異テスト: <提案する / 不要 / 道具なし> — <理由>`）に置き、呼び出し元の 2 つ（軽量フロー・feature-dev の Phase 7）は先頭の語と、`提案する` に添えた回し方・所要の目安だけを読む。行は契約の 2 行（`self-review 以降の変更:` / `次の一手:`）の前に置き、既存の 2 行の値・文言・末尾の位置は変えていない。判断の正本は `review-guide-format.md` の「変異テストの提案」で、feature-dev が SSoT pin を掛けている「回し直すかの判断」の後ろに同じ `##` の節として足した（pin 先の節は変わらない）
- 要るのは、core の変更が分岐・境界・検証ロジックを触り、かつその振る舞いがテスト対応表で「あり」のときだけ。issue の判断材料の候補では対応表の「なし」を提案の理由に挙げていたが、テストの無い振る舞いを変異させても全部生存すると最初から分かっているので、`不要` の理由にした（先にテストを足す）。変異テストに価値があるのは、テストがあるのに検証していない経路を出せるとき
- 道具は宣言 `.claude/mutation-test.sh` が先で、無いときだけルートの設定ファイル（Stryker / mutmut / cargo-mutants）から推測する（`scripts/detect-mutation-tool.sh`）。PATH は見ない（機械ごとに結果が変わり、使っている印にならない）。道具が無いプロジェクトでも導入は提案しない — 道具の選定・設定・CI への組み込みまで広がり、締めで決める範囲を超える
- 宣言の契約は `git diff <ref>` に出る変更が対象（未追跡のファイルは対象外。review-guide の diff と同じ）。exit 0 は「実行した変異に生存なし（上限・タイムアウトで未実行が残った回を含む）、または未計測（対象行・変異が 0 個）」を表し、どれかは stdout で見分ける（未計測の回は集計の行が出ず、未計測と分かる 1 行が出る）。exit 1 は生存ありか途中で止まった回で、途中で止まった手がかり（中断の FATAL と実行済みの件数）は stderr に出るので、stdout と stderr の両方で見分ける。手がかりを出すのは宣言の側で、語は宣言が決める（正本はこの repo の mutation-test.py の語を例に挙げる）。この repo の mutation-test.py は、対象行が無いときも、変異が 0 個のときも、上限（既定 25 個）やタイムアウトで未実行が残っても生存が無ければ exit 0 を返すので、exit 0 だけで「生存 0」とは読ませない（呼び出し元は、生存 N 件・一部未実行・未計測・判定不能に書き分け、全件を実行して生存が無い回だけを生存 0 とする）
- review-guide は回さない。主な理由は所要時間（変異 1 個ごとにテストを 1 回回す。この repo の宣言では 10 分を超える）で、道具によっては（この repo の mutation-test.py など）作業ツリーのファイルを書き換えながら回る。呼び出し元は `提案する` のときだけ通常のメッセージで聞き、承認の返信があってから回す。feature-dev も `AskUserQuestion` を使わない（無操作の自動続行を承認と取り違えないため）。回す前と後で `git status --porcelain` を突き合わせ、道具の出力をコミットに混ぜない
- この repo は mutation-test.py を `--strict --related-first` で呼ぶ宣言を置いた（宣言が無いと mutation-test.py は既知の道具ではないので `道具なし` になり、dogfood できない）
- 採らなかった案: 判断を呼び出し元 2 か所に書く（同じ判断が 2 か所に分かれる）/ review-guide の中で回す（読み合わせの 1 ターンに長い実行が挟まり、承認なしの実行にもなる）/ 道具の導入を提案する / mutmut の `--paths-to-mutate` で範囲を絞る（mutmut 3 の `run` はこのオプションを持たず、設定の `paths_to_mutate` も `source_paths` に改名された。`run` が受ける mutant 名のワイルドカードで、変更したモジュールに絞る形にした。行範囲では絞れない）/ mutmut の設定の `only_mutate` で絞る（利用者の設定ファイルを書き換えることになる）/ Stryker を素の `npx stryker` で回す（TTY の無い実行では npx が確認なしで registry から取得するので `npx --no` にした）/ 推測した道具の回し方で、パスの `'` を `'\''` に置き換えて引用する（引用の組み立てをモデルに任せることになり、誤ると利用者が承認したコマンドの中で別のコマンドが走る。`'`・改行・制御文字を含むファイルは回し方から外す形にした）

## 追記（2026-10-27）: 読み合わせの必須化と `--hide-guide`

- feature-dev の Phase 7 は読み合わせを「出す / 出さない」で選ばせ、「出さない」で読み合わせごと飛ばせた。精読を選び、レビュー観点に答え、直せるものを直す工程そのものがコードの質を上げるので、飛ばせないようにした。利用者に選ばせるのはガイドと解説を表示するかだけにした（issue-workflow の軽量フローはもともと必須で、表示の選択だけを足した）
- 表示しない回は `--hide-guide` で呼ぶ。`WALKTHROUGH=1` を含み、省くのは表示とターンの区切りだけ。全精読を 1 ターンで通し、精読の途中で聞くはずだった問いは持ち越した確認に積んで締めで 1 問ずつ聞く
- 利用者が解説を見ない分は締めの前置き（精読ごとの結果・入れた修正の詳細）で渡す。「回し直すかの判断」の条件 2（解説で確かめた）は、前置きに変更前後を出した変更を同じに扱う。表示するかで 2 回目の self-review の有無を変えないため
- レポートの冒頭・末尾にしか置き場の無い注記（精読の上限を寄せた・`FIX_OK=0` の理由・`/guide-diff`）と、PR モードの「人間の判断が効く箇所」は開始行に添えて出す。省くのは読み物で、判断に要る情報ではない
- 採らなかった案: 表示しない回は工程を軽くする（読み合わせの質の効果を捨てることになり、要求に反する）/ 表示しない回は review-guide を呼ばず self-review だけにする（同上）/ 呼び出し元に非表示回の進め方を書き写す（正本が 2 つになる。呼び出し元は `--hide-guide` を付けることと締めの契約の行だけを持つ）
