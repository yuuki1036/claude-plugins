# ADR-20261108182901: AI-DLC v2 の思想は採り、実装は段階的に入れる（エンジン化・プラグイン統合・依存の解禁はしない）

## ステータス

accepted（2026-11-08）

## コンテキスト / 背景

AI-DLC v2（[awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows)）は、決定的なエンジンが工程の順序・遷移・承認の記録・完了の判定を持ち、LLM には 1 手ずつ型付きの指示を渡す。思想は「人の判断を少しずつ機械の検査へ移し、移せた分だけ人の出番を減らす」で、仕様の原則 7 は一度に全部を入れ替える導入を否定している。

この repo は「決定的 hook > Skill > CLAUDE.md」の原則（`docs/rule-placement.md`）を持つ。一方で工程の順序は SKILL.md の散文が持ち、スクリプトにしているのは局所だけ。両者の違いはこの点が最も大きく、エンジンへ作り直すか（あわせてプラグインを統合し、依存の禁止を外すか）を判断する必要があった。

根拠の数値は `docs/session-reports/2026-11-08-aidlc-v2-evaluation.md` にある。要点:

- CHANGELOG の修正 360 件のうち、エンジンで防げる手順落ちは 32 件（8.9%）。台帳とゲートで防げたのは 3〜7%。多いのは保守 30%・判定基準の誤り 24%・スクリプトのバグ 23%
- AI-DLC 自身も、1 人が対話で使う既定の設定では守りのほとんどを外している（11 scope 中 10 で `guard_policy: off`）
- プラグイン間の依存を解禁しても、ネイティブの `dependencies` は依存先のパスを渡さないので複製は残り、任意の連携 21 件が強制インストールに変わる

## 決定

1. AI-DLC v2 の思想（人の判断を機械の検査へ段階的に移す）を採る。物差しは「人の介入点」とし、多いところから機械へ移す（計測は #415）
2. 実装は原則を 1 つずつ既存のプラグインへ当てはめる形で入れる。最初に当てはめるのは次の原則:
   - LLM に数えさせない・照合させない。1 つの規則に持ち主は 1 つ（#425）
   - エージェントへの指示をその段の中身に絞る（#426）
   - 段と段の成果物をファイルで受け渡す（#427）
   - 人の修正を事後条件・guardrail の候補にする（#430）
3. 次の 3 つはしない:
   - 工程の順序・遷移・承認の記録をエンジンが持つ形への全面的な作り直し
   - プラグインの統合
   - プラグイン間依存の禁止を外すこと
4. 効くかが未確認の機構は、観測で判定できる着手条件を付けた実験として入れる（#428 SubagentStart・#429 receipt 照合）

## 影響 (Consequences)

- **良い影響**: 今の 18 プラグインの構成と、任意の連携（入っていなければ黙る）を保ったまま、原則ごとに効果を測って入れられる。エンジンの保守（AI-DLC は `core/tools` だけで 235,589 行）を背負わない
- **悪い影響**: 工程の順序は散文のまま残るので、手順落ち（8.9%）は散文の対策と局所のスクリプトで防ぎ続けることになる。承認の正当性（何を承認したかを指紋で縛る）や監査は持たない
- **トレードオフ**: エンジンが防げる 1 割に満たない型の失敗と、作り直しと保守のコスト・任意の連携の強制化を比べ、後者を避けた

## 適用方法 (Enforcement)

決定そのもの（作り直さない・統合しない・依存を解禁しない）は、機械では強制しない。新しいプラグインや依存を足す判断は、`harness-keeper:component-addition-advisor` と CLAUDE.md の「プラグイン間の依存禁止」が扱っていて、検出の対象が「やらなかったこと」なので lint にできない。

段階的に入れる原則の側は、issue ごとに機械で守る形にする:

- 判定基準の持ち主を 1 つにする: スクリプトに寄せ、散文は値を写さず SSoT pin で正本とのずれを検出する（#425）
- 本文の大きさ: `validate_plugin_quality.py` のコンテキスト予算の検査で SKILL.md の上限を強制する（#426）
- 実験: 着手条件と打ち切り条件を観測で判定し、満たさなければ close する（#428・#429）

## 検討した代替案

- **エンジンへの全面的な作り直し**（`dlc` プラグイン 1 つに feature-dev・bdd-spec・design-doc・adr-keeper・spec-advisor・code-review と issue-workflow の開発部分を統合し、python のエンジンが state と journal を持つ）: 防げる型の失敗が 1 割に満たず、代表的な事故 8 件にも台帳でなければ防げなかったものが無かった。原則 7 も一度に全部を入れ替える導入を否定している
- **プラグイン間依存の禁止を外し、必須の連携だけネイティブの `dependencies` で宣言する**: 共有コードの複製（`safe-hook.sh` の 14 個など）が残る。複製の同期だけの版は約 3% と小さい。任意の連携 21 件が強制インストールに変わる
- **AI-DLC の守りの機構を個別に入れる**（134 種の監査イベント・Guard Policy・11 プロファイルと composer・Stop での強制続行・HUMAN_TURN・mob 型の agent・learnings ritual・出典タグの sensor・traceability）: どれも前提がチーム・無人実行・監査で、1 人が対話で使う使い方では AI-DLC 自身が既定で外している。HUMAN_TURN は hook の入力で人と他のセッションを区別できない。learnings ritual は Claude Code の auto memory が同じ役をしている。出典タグの検査は ADR-20260817120000 で却下済み
- **何も採らない**（評価の初版。失敗を防ぐ物差しだけで測った）: 物差しが AI-DLC の目的（介入を減らす）と違い、思想に対する反論になっていなかった。人の介入点を数え直すと、続行・承認だけの発話が約 35% あり、移せる余地があった

## 見直す条件

この決定は、利用者が 1 人で、対話で使う前提に立っている。次のどれかに当たったら supersede して判断し直す:

- チームで使う（複数人が同じ工程を進める）
- 無人で回す（承認を人が見ないまま工程を進める）
- 承認の正当性や監査の記録が必要になる
- 段階的に入れた原則の後に測り直しても、手順落ちの割合や人の介入が減らない
