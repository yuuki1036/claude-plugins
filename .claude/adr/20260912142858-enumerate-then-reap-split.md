# ADR-20260912142858: 破壊的な一括操作は列挙と実行を別プロセスに分ける

## ステータス

accepted（2026-09-12）

## コンテキスト / 背景

複数対象をまとめて消す・閉じる・書き換えるスキル（`dev-workflow:worktree-gc` の設計時に顕在化。既存では `issue-workflow:maintain` の棚卸し、`issue-workflow:issue-maintain` の削除検出、`issue-workflow:discover` の起票が同型）では、「候補を判定して表に出す」と「承認を受けて実行する」の 2 つが必要になる。

これを 1 プロセスで書くと、実行時に判定をもう一度走らせることになる。判定は git の状態・PR の状態・生存プロセスといった**外部の可変状態**に依存するため、表を出した時点と実行時点で結果が変わりうる。ユーザーは表を見て承認するので、**表に出ていないものが消える**経路が構造的に開く。CLAUDE.md の AskUserQuestion 例外（起動＝実行確定なスキルでは止まらない）は「操作対象が git 管理下で復元可能」を前提にしており、worktree 削除・DB drop のような不可逆操作はこの前提を満たさない。

## 決定

破壊的な一括操作を行うスキルは、次の 2 つを**別プロセス**に分ける。

1. **列挙**: 副作用を持たず、1 対象 1 行の機械可読形式（JSON Lines 等）を stdout に出す。各行は判定結果（`verdict`）と根拠（`reasons`）を自分で持つ
2. **実行**: 列挙の出力行を stdin で受け取り、**判定を再実行しない**。`verdict` が実行対象でない行を受け取ったら exit 2 で拒否し、対象が実在しない行は SKIP + WARN に落とす

オーケストレーター（LLM）は列挙の出力行を**選ぶ**ことはできるが、**書き換えない**。承認 UI に出した表と、実行プロセスが受け取る行は同一の実体である。

## 影響 (Consequences)

- **良い影響**: 承認した内容と消えるものが入力契約で一致する。列挙は副作用が無いので使い捨てリポジトリでそのままテストでき、実行は stub を置いて exit code の契約だけ検証できる（このリポジトリの `.claude-plugin/scripts/tests/` の 2 系統にそのまま乗る）。部分承認（一部の行だけ実行）が引数設計なしに表現できる
- **悪い影響**: スクリプトが 2 本になり、両者が共有する行フォーマットがもう 1 つの正本になる。列挙から実行までの間に状態が変われば「実在しない行」が出るので、実行側に SKIP 経路が要る
- **トレードオフ**: プロセス数と入力契約の維持コストを払って、「表に出していないものが消えない」ことの機械的な保証を買う。単一プロセス + `--dry-run` / `--apply` の方が小さいが、その構成では 2 回の判定が一致する保証がどこにも無い

## 適用方法 (Enforcement)

**機械強制は部分的にしかできない。** 決定的に検証できるのは実行プロセス側の入力契約だけで、「列挙と実行を分けたか」という設計レベルの遵守は自然言語判断になる。

- **できる（テストで強制）**: 実行プロセスが `verdict` 非対象の行を exit 2 で拒否すること、実在しない対象を SKIP + WARN に落とすことは、stub を置いた CLI テストで検証できる。破壊的スクリプトを新設したらこの 2 ケースをテストに含める
- **できる（列挙側）**: 列挙プロセスが副作用を持たないことは、使い捨てリポジトリで実行前後の `git status --porcelain` と対象ディレクトリの状態を突き合わせて検証できる
- **できない（設計判断）**: 「この操作は破壊的な一括操作にあたるので分割すべき」の判定は対象ごとの文脈依存で、grep や schema では拾えない。`claude-meta:component-addition-advisor` と `/code-review:self-review` の観点として扱う
- **昇格の余地**: 破壊的スクリプトの命名規約（`scan.sh` / `reap.sh` のような対）を決めれば `validate_plugin_quality.py` で「片方しか無い」を検出できるが、現時点では事例が 1 件なので規約化しない（事例が 3 件を超えたら再検討する）

## 検討した代替案

- **単一プロセス + `--dry-run` / `--apply`**: 小さく書けるが、2 回の実行で判定が一致する保証が無い。部分承認を引数で表現すると、承認した内容と `--apply` が消す内容の対応をユーザーが目で追えなくなる
- **単一プロセス内で列挙 → 承認 → 実行を完結**: 状態のずれは消えるが、承認 UI を呼ぶのはオーケストレーター（LLM）側なのでスクリプト内から承認を挟めない。スクリプトに対話を持たせると CLI テストが書けなくなる
- **列挙結果をファイルに保存して実行側が読む**: stdin と実質同じだが、古いファイルを渡す事故が増える。ファイル経路が要る規模なら列挙側の出力をリダイレクトすればよく、契約としては stdin で足りる
