# テストの規律（Phase 5 Normal Mode）

Phase 5 でテストを書くときの規律。プロジェクトにテスト基盤（テストランナーと既存のテスト）があるときだけ使う。翻案元: [mattpocock/skills](https://github.com/mattpocock/skills) の tdd（`skills/engineering/tdd/SKILL.md`・`tests.md`・`mocking.md`）。Copyright (c) 2026 Matt Pocock / MIT License。許諾文は repo 直下の NOTICE。

> 役割分担: ここに置くのはフレームワークに依らない規律だけ。スタック固有のテスト戦略（Vitest / RTL / Playwright、Next.js の Server Component など）は別プラグインの提案（GitHub issue #89）の領分で、ここには書かない。

## 良いテスト

テストは**公開された interface を通して振る舞いを確かめる**。実装の細部は確かめない。実装を丸ごと書き換えても、テストは変わらないのが正しい。良いテストは仕様として読める —「有効なカートなら購入できる」は、何ができるかをそのまま言っている。

- 呼び出し側が気にする振る舞いを確かめる
- 公開 API だけを使う
- 名前は WHAT を書く（HOW を書かない）
- 1 テスト 1 つの論理的な主張

## seam — テストを置く場所

**seam** は振る舞いを外から観測できる公開の境界で、テストはそこに置く。内部には置かない（語彙は `module-design.md`）。

- **置く seam は Phase 4 の設計で決めたもの**（architect の blueprint の「Test Seams」と Phase 3 の設計契約）。実装中に新しい seam を足したくなったら、設計の変更として扱う
- 既存の seam を新しい seam より優先し、**できるだけ高い位置**に置く。seam は少ないほど良い
- 全部はテストできない。seam を先に決めるのは、テストの手間を重要な経路と複雑なロジックに寄せるため

## アンチパターン

- **実装に結合したテスト**: 内部の協調オブジェクトを mock する・private メソッドを直接テストする・呼び出し回数や順序を assert する・interface を迂回して確かめる（DB を直接引く等）。見分け方は「振る舞いを変えないリファクタで落ちる」
- **同語反復（トートロジー）**: 期待値をコードと同じ計算で作り直している（`expect(add(a, b)).toBe(a + b)`、同じ手順で作ったスナップショット、定数を自分自身と比べる）。構成上必ず通り、コードと食い違えない。**期待値は独立した正解から取る** — 既知のリテラル・手で解いた例・仕様
- **水平分割**: テストを全部先に書いてから実装を全部書く。まとめて書いたテストは想像した振る舞いを確かめることになり、形しか見ず、実際の変化に鈍くなる。**縦に切る** — 1 テスト → 1 実装を繰り返し、各テストを前のサイクルで分かったことに合わせる

## mock はシステム境界だけ

mock するのは外部 API（決済・メール等）・時刻と乱数・（ときに）DB やファイルシステムだけ。DB はテスト用 DB を優先する。自分のクラス・モジュール・内部の協調オブジェクトは mock しない。

境界は mock しやすく設計する: 依存は中で作らず**受け取る**。汎用の fetch 1 本ではなく、**操作ごとの関数**を持つ SDK 形にする（mock ごとに返す形が 1 つに決まり、テストの準備に条件分岐が要らない）。

## ループの規則

- **赤が先、緑が後**。落ちるテストを書いてから、通るのに足りるだけのコードを書く。先のテストを見越した実装や思いつきの機能を足さない
- **1 回に 1 切れ**。1 seam・1 テスト・最小の実装で 1 サイクル
- **リファクタはループに含めない**。レビュー段（Phase 6）の仕事
