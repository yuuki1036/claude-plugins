# Grill プロトコル

コミット（実装・設計確定）の前に、プランや設計を **1 問ずつ容赦なく質問して詰める**ための対話規範。Frederick Brooks『The Design of Design』の design tree（コードに落とす前に設計木の全分岐を歩く）と、Matt Pocock の "grill-me" skill に由来する（翻案元: [mattpocock/skills](https://github.com/mattpocock/skills)、Copyright (c) 2026 Matt Pocock / MIT License。許諾文は repo 直下の NOTICE）。

> 狙い: plan mode が「共通理解の前にプラン文書を吐く」問題を防ぐ。一括の質問リストではなく、design tree の依存を 1 分岐ずつ解きほぐして合意に到達する。

---

## 3 原則

### ① 事実は自分で調べ、決定はユーザーに委ねる

質問候補を「事実」と「決定」に分ける。**事実は自分で調べて解決し、質問リストから落とす。決定はユーザーに聞く**。

- **事実**（今どうなっているか）: codebase exploration の結果 / `Grep` / `Glob` で確かめられるもの。調べて答えが出たら聞かない
- **決定**（これからどうするか）: 自分で解決してよいのは、**明示的な決定記録**（ADR・Issue の決定事項・BDD spec・knowledge の決定）がその問いに直接答えている場合だけ。コードに前例があるだけの決定は自分で決めない — 前例は推奨（原則③）の根拠にとどめ、推奨を添えて聞く
- 落とした問いは「調査で確定した前提」として最後に提示する（黙って仮定しない）
- ユーザーの時間は「コードを読めば分かること」ではなく「ユーザーしか知らない意図・優先順位」に使う

### ② 1 問ずつ、依存順に

残った問いを **design tree の依存順**（上流の決定が下流を制約する順）に並べ、1 問ずつ確認する。

- 上流の問いを先に解くと、下流の問いが消える / 選択肢が絞られることが多い
- 各回答のあと、残りの問いを再評価する: 前の答えで解消・変形した問いは畳み、新たに見えた分岐は挿入する
- 一括リストはこの依存構造を潰してしまう（だから使わない）

### ③ 各問いに推奨回答を添える

各質問には必ず **推奨案を先頭に置き `(Recommended)` を付け**、1 行で理由を添える。

- `AskUserQuestion` の最初の option を推奨案にする（リポジトリの AskUserQuestion 規約に整合）
- ユーザーが「おまかせ」と言えば推奨案で確定して進む。**無操作で自動継続した回答（`askUserQuestionTimeout`）は「おまかせ」と区別し、確定させずに未決として残す**
- ユーザーが「分からない」「他の人が決める」と答えた問いは、推奨で埋めない。未決のまま、**いつ・どこで・誰が確定するか**を残す
- 推奨があることで「説明を読んで考える」コストが減り、grill が速く進む

## 採用する決定の前提を問う

ある決定を採ったら、その前提を問う後続の問いが生まれる。Issue・spec・living spec から引き継いだ決定は、書かれているだけでは契約にしない。次の 4 つを必ず候補に入れる:

- **設計システムとの対応**（UI を含むとき）: 各 UI 要素は設計システムのどのコンポーネントに当たるか。プロジェクトの必読 doc が指定するコンポーネントと設計は一致しているか
- **前提の成立**: 引き継いだ決定が置いた前提（「ダイアログのタイトルが既にエラーを伝えている」等）は、今回の実装コンテキスト（コンテナ・画面種別・呼び出し経路）でも成り立つか
- **標準規約との衝突**: 引き継いだ決定は、必読 doc やプロジェクト規約とぶつからないか
- **説明とコードの食い違い**: ユーザーの説明がコードの実態と食い違っていたら、該当箇所（file:line）を示してどちらが正しいかを聞く（どちらかに黙って寄せない）

前提が崩れている・規約と衝突している問いは、原則①の「自分で解決する」対象にしない。どちらを採るかはユーザーに聞く（推奨は、決定側が理由を明示して規約を上書きしていない限り規約に従う案）。

> 実例: Issue の決定「Alert で囲まない」はダイアログのタイトルがエラーを伝える前提だったが、実装はタイトルの無いサイドパネルだった。必読 doc は「エラー寄りの警告は `<Alert>`」と定めていたが読まれず、決定が無検証のまま設計の契約（feature-dev では architect への入力）になり、人間レビューで初めて見つかった（GitHub issue #233）。

## 過剰質問を避ける（proportionality）

grill は relentless だが、無意味な質問の量産ではない。次のときは圧縮してよい:

- 残った問いが 1〜2 個かつ方向性が明確 → 1 回の提示にまとめる
- 影響が小さく後から安全に変えられる判断 → 推奨で進めて確認を 1 行添えるだけにする

「事実は自分で調べる（原則①）」と並ぶ、grill の自己抑制ルール。writing-polish の over-correction 抑制と同じ思想。
