# comment-rule — コードコメントの規約（正本）

コードコメントの評価軸の正本。**軸は下の delimiter 区間に書かれた 2 つのみ。** 区間を消費サイトに複製して埋め込む。

- 消費サイト:
  - `CLAUDE.md`（書く側の規約）
  - `code-review/references/prompts/focus/comment-polish.md`（見る側。reviewer に渡すプロンプト本文なので**区間はフェンスの中**にある）
- 同期検証: `validate_plugin_quality.py` の comment-rule 同期チェック（Critical）。マーカー行（`COMMENT-RULE:START` / `END`）に挟まれた区間を **dedent 後に比較**する
- 変更手順: この正本を編集 → 全消費サイトの区間に同じ内容を反映 → `/quality-check` で同期確認
- **軸を増やさない。** 3 つ目が要ると思ったら、それは 2 軸のどちらかの具体化か、コメント規約ではない別の検査（実装との一致 = `code-review/references/prompts/focus/comment-accuracy.md` の担当）である

## 内容判定を機械化しない理由

決定的検査の候補を実測して全滅した。母集団は git 追跡下の同梱スクリプト（`.sh` 65 本 / `.py` 32 本）の `#` コメント 3,986 行 と複数行文字列 3,042 行:

| 候補 | ヒット | 真陽性 | 内訳 |
|---|---:|---:|---|
| 冗長な語尾・前置き（「するための処理」「を行う処理」「この関数は」「を行います」） | 0〜1 | 0 | この型のフィラーがそもそも存在しない |
| 無地の区切り線 | 24 | 0 | 全て `safe-hook.sh` の見出しバナー（正本の byte-identical 複製を跨いで重複計上される） |
| ファイル内の完全重複 | 15 | 0 | 同上のバナー上下 2 行と、折り返した説明文 |
| コードの再述 | — | — | 正規表現で拾える形にできなかった（機械化できない） |

フィラー表現は事実上存在しない一方、コメントは実測値・却下案・ハマりどころを書くのが標準で、`実測` の語だけで 246 箇所ある。行数や語尾で弾く lint は必ず偽陽性側に落ちる（`docs/rule-placement.md` の却下 3 事例と同型）。

**機械層が強制するのは「規約が届く経路」であって内容ではない。** 内容は書く時（CLAUDE.md 常駐）とレビュー時（`/code-review:self-review` のコメント推敲）の 2 回の独立判断に載せる。

コードコメントは次の 2 観点だけで評価する。**他の軸を足さない**（「what ではなく why」のような二分法も使わない）。**適用範囲はコード内コメント（`//` `#` `/* */` と docstring）に限る** — md 散文（doc / SKILL.md / README / CHANGELOG）は対象外。

観点 1 — **読み手にとって必要な情報のみか**:
- コードを読めば即座に分かることを言い換えているだけではないか（`count++` に「カウンタを増やす」等）
- その行が無いと読み手が困るか。困らないなら書かない / 消す
- 主語・目的が曖昧で、結局何を伝えたいのか読み取れない記述になっていないか

観点 2 — **冗長表現の排除**:
- 同じ内容を 2 回言っていないか（1 コメント内 / 直前直後のコメントとの間）
- 前置き・修飾が長く結論が後ろに来ていないか
- 1 語で足りる箇所を句で書いていないか

**上の 2 観点に該当しないことを理由に、削除・短縮を求めてはならない。長さは違反の根拠にならない。** 非自明な why / TODO・FIXME の背景 / regex・算術・境界条件の意図 / 外部制約（API 仕様・互換性・既知バグの回避）への言及 / 実測値・却下した代替案・ハマりどころの警告は、長くても観点 1 を満たす。**判断に迷ったら残す側に倒す。**
